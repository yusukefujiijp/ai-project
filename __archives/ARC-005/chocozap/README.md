## 1. 日付と保存場所

日付が分かる記録は `chocozap/records/YYYY/YYYY-MM-DD.md` に一日一ファイルで保存する。同じ日の複数来館はファイル内で分ける。未作成の日付や年のファイル・フォルダは、実際に保存する記録ができた時に作る。

日付未確認の来館は `chocozap/records/undated/<visit_id>.md` へ保存する。日付未確認は「今日」「最新の運動」と同義ではない。初回記録の保存日から実施日を逆算しない。

日付の規則：

- `workout_date` は運動した日。日付運用の基準は `Asia/Tokyo`。本人の明示する現地日付・時差等の事情があれば、その根拠を保持する。
- 「今日」「昨日」は信頼できる発言時点から解決する。古い会話の相対日付を、読み出した今日で解釈し直さない。根拠がなければ未確認とする。
- 日をまたぐ同じ来館は原則として開始日のファイルへまとめる。分かっている実際の観察日時は個別に残す。開始日や来館の対応が不明で判断を変える時だけ確認する。
- `created_at` は記録を作成した時点であり、運動時刻ではない。保存・変更の時点はGitのコミット履歴でも辿れる。未知の発言時刻や実施時刻を生成しない。
- 遅れて記録した日や過去記録を訂正した日は、Gitの更新順と実施日順が異なる。「前回」は実施日・来館の文脈から解決する。
- 日付が判明した未確認記録は、対象日ファイルの現在内容と統合する。来館・観察のIDと元の出所を保持し、旧住所のリンクを更新する。旧ファイルを残す必要がある場合は、移動先を示す案内だけにして二重原本を作らない。 移動案内（`kind: record-redirect`）は観察として数えず、`canonical_path`または本文リンクから正本を読む。undated内に案内があることだけで、現在も日付未確認とは判定しない。

## 2. 記録の最小構成

Markdownに次の小さなfrontmatterを添える。`workout_date` は `YYYY-MM-DD` または `null`。`timezone` は日付解釈の基準であり、実際の来館時刻が既知であるという意味ではない。

```yaml
schema: chocozap-record-v1
workout_date: null
timezone: Asia/Tokyo
created_at: "<実際に記録を作成したISO 8601日時>"
recorded_by: "<整理・記録した主体>"
```

これは形式の説明であり、仮の日時や山括弧の文字列を実記録に保存しない。

本文では、来館ごとに安定した `visit_id` を付け、観察をその来館内のIDで区別する。IDは既存記録と重ならないものにし、日付訂正や移動でも保持する。連番を、未確認の実施順や来館時刻の証明にしない。

各観察に必要なのは、報告の種類、機械、本人が表した使い方、値と単位、出所である。分かっている周回・時点・感覚は添える。同じ情報が複数行に共通する場合は来館や報告のまとまりで宣言できる。

- 種類：Sweet Spot申告、新しい観察、同じ条件の再確認、訂正など。
- 使い方：片手／両手・片足・縦／横などの原語を保つ。左右・握り方・回数・セット数を未報告から補わない。
- 出所：本人の該当発言を短く引用するか、取得できる原文への正確な参照を付ける。AIの整理や解釈は区別する。会話URLやメッセージIDが取得できない場合は作らない。
- 訂正・参照：対象の観察IDを示す。相手が曖昧で結果を変える場合だけ確認する。
- 未確定：実施日・周回・完了等の不明は不明のまま残す。Sweet Spot申告を、運動量や周回完了の報告に変えない。

Humanにこの形式の入力を要求しない。短い機械別報告や自然なFeedbackをAIが整理する。本人の言葉と構造化した欄が食い違えば、出所に戻って訂正する。別々に編集する二つの正本は作らない。

## 3. 変化を読む

保存する中心は元の観察と訂正である。二周目の一覧、前回との差、傾向の説明は、必要な時に正本から組み立てる。比較を資料として残す場合も、対象日・観察ID・参照した版を示した派生分析として扱う。

まず訂正関係を解決し、比較する機械・使い方・周回や時点の対応を確認する。

- **誤記訂正**：対象の現在有効な値を直す。元の報告と訂正の関係を保持し、訂正自体をSweet Spotの変化として数えない。
- **新しい観察**：一周目と二周目、前回来館と今回など、異なる時点の報告を両方保持する。後の値で前の観察を消さない。
- **同じ条件の再確認**：「今日も同じで合った」等は、その参照元を示した新しい観察として残す。
- **未報告**：同じだった、実施しなかった、失敗した、ゼロだった、のいずれにも置換しない。
- **比較条件の違い**：片手と両手、縦と横、機種や重量表示の違いを混ぜない。対応が不確かなら、その範囲で説明し、同等条件での数値差を断定しない。
- **増減の解釈**：対応する観察の差は示せるが、重量だけで成長・後退・身体状態・理論の有効性を認定しない。本人の感覚と原因についての仮説を区別する。

一周目から二周目への変化と、来館を跨ぐ変化は、異なる問いとして扱う。実施日未確認の記録同士には、根拠のない前後関係や日数を与えない。

## 4. 継続保存の範囲と手順

2026-09-24の本設計の実行承認には、YusukeJPの本Sweet Spot運用で報告された機械別条件・訂正・Feedbackを継続保存する方針を含む。この方針が現在の運用へ適用されることと、有効な保存権限・GitHub接続を確認できるAIは、その範囲の更新ごとに同じ許可を聞き直さない。

このREADMEは各Hostの権限を追加しない。現在のHumanの訂正・STOP・保存しない指定・Plan-onlyが優先する。設計相談、引用、仮例、推奨値は本人の実記録へ入れない。呼び出しだけで未報告の当日データを生成しない。ChatGPT長期メモリを転記せず、保存対象の発言・確認できる記録だけを使う。

保存時は次を行う。

1. 対象来館と日付、保存先を解決し、対象ファイルの最新内容とSHAを読む。新規パスなら親ディレクトリ等から存在を確認する。
2. 本人の報告と既存記録を照合し、必要な差分だけを反映する。他AIやHumanの追記を保持する。
3. 同じ処理の再試行では、出所・観察ID・直前の保存結果から既反映か確認する。同じ文字列でも、新しい時点の再申告なら別観察である。文字列一致だけで消さない。
4. 実質的な変更がなければNO_CHANGEとする。同じパスへの書込みを並行実行しない。SHAやブランチが競合したら再取得して整合させ、古い全文で上書きしたりforce更新したりしない。
5. 何をなぜ変えたかが分かるコミットで保存し、保存先を再取得する。パス、内容、対象日・来館、必要なEOF、保存された版を照合してから保存完了を伝える。

記録を受け取ったことと、GitHubに保存できたことを分ける。保存できない時も会話で確認できる条件から二周目を支援できる。未保存の範囲を明示し、次に保存を再試行できる時点で最新ファイルと差分を確認する。会話にしかない記録の恒久保持や、接続のないAIによる保存を保証しない。

この運用は、会話で報告を受けた時に使う保存手順である。常駐処理、定刻ジョブ、アプリからの自動データ収集を設置したという意味ではない。

## 5. 読み出し・バックアップ・他AIへの入口

スキルを使えるAIは、その本文から意味を復元する。保存や過去記録が必要な場面でこのREADMEを読み、対象の記録だけへ進む。既に確認済みの本文と案内を相互に再読し続ける必要はない。

- 「今日の二周目」：該当来館の観察と訂正から条件を組み立てる。現在の身体の感覚による調整余地を保つ。
- 「前回と比べて」：対象の実施日・来館・使い方を合わせ、元の値、今回の値、対応の根拠を示す。
- 「最近の傾向」：必要な日付範囲を読む。記録のない日を未実施や同条件継続と見なさない。
- 「前回」などの対象が複数ある場合：既知の会話から解決し、それでも比較結果を変える曖昧さだけ確認する。
- 記録が見つからない場合：存在しない、取得に失敗した、アクセスできない、を区別する。見えない履歴を記憶として補わない。

日付別ファイルへの永続保存とGitの変更履歴を、初期のバックアップとする。過去版を復元する際は、対象のコミットを読み、現在との差分を確認する。古い版を読むことと、現在の正本へ復元変更を書き込むことは別の操作として、現在の依頼に従う。リポジトリ全体を別媒体へ複製するバックアップは、この運用では実装していない。

他AIへは次の入口と現在の依頼を渡せる。

```text
次のchocoZAPの案内を読み、必要な日付・来館の記録を参照して、今回の依頼に適用してください。
https://github.com/yusukefujiijp/ai-project/blob/main/chocozap/README.md
```

読み取りだけの依頼から保存を開始しない。GitHubの正本にアクセスできること、Skillが導入されていること、保存権限があること、運動の実成果はそれぞれ別に確認する。
