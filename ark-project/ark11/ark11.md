# Ark11: Foresight Waiting Trap

## 1. Project Identity

Ark11は、未来に自然発生するFog / Low-Cognition Eventを平常時に先読みし、判断能力が低下する前に必要なContext・介入手段・最初の一手を事前配置して待ち構え、Event発生時には再判断を最小化して一手を通し、そのRealityから再現可能なMethodを成熟させるField Projectである。

Ark11の目的は、HumanをProtocolへ従属させることでも、Waiting Trapを大量生産することでもない。

```text
Predict
→ Preload
→ Wait
→ Trigger
→ One Move
→ Reality Capture
→ Review
```

Rootは主イェシュア・ハマシア、主イェシュアの聖なる血潮、Teshuvah、信仰と祈りである。AI、Workout、口腔ケア、Project、Field、Thread、Query、Protocol、MarkdownはKeli / Fruitであり、Root・王座・救いではない。

## 2. Seed / 一文定義

### 2.1 Foresight Waiting Trap

> **Foresight Waiting Trapとは、未来に自然発生するFogやLow-Cognition Eventを平常時に先読みし、判断能力が低下する前に必要なContext・First Move・介入手段を事前配置して待ち構え、Event発生時には再判断を最小化して一手を通し、その瞬間のRealityを捕捉・Reviewする方法である。**

### 2.2 A/B Cross-State Architecture

> **A/B Cross-State Architectureとは、高認知のAで未来の低認知Bに必要なContext・Prepared Mainline・Minimum Victory・Stop条件を事前Compileし、Bでは再判断を最小化して状態適合した一手だけを通し、回復後のAがRealityをReviewして次回を改善する状態間協働設計である。**

### 2.3 低・超低認知状態 自由入力待機Field

> **低・超低認知状態 自由入力待機Fieldとは、高認知状態でDedicated Threadへ必要Contextを事前Compileして`armed_and_waiting`へ移し、後日そのThreadへ届く低認知・超低認知状態の不完全・断片的・誤変換的・非定型なHuman入力を失敗として退けず、特定Keywordを要求しないB状態Event Signalとして受理し、AI側が解釈負荷を引き受けて質問と選択肢を最小化し、その瞬間に通せる一手へ接続するArk11のReality Test Fieldである。**

### 2.4 Thread-State Trigger

> **Thread-State Triggerとは、Future Humanが正しい起動語を入力できることへ依存せず、Dedicated ThreadがB状態Eventを待つ`armed_and_waiting`にあるという事前ContextをPrimary Triggerとし、その後に届く自由入力を原則としてB状態から渡されたReality Fragmentとして解釈する起動設計である。**

### 2.5 Pattern-B Workout-First Mainline

> **Pattern-B Workout-First Mainlineとは、B状態で次手生成や行動開始が困難な局面において、Stop・Safety・身体Realityを上位Guardとして保持しながら、AIが分析・比較・再審議を増やさず、Humanへ現在の一手だけを渡してFull / Short / Recoveryの可変深度Workoutへ接続し、Digitalまたは認知上の停滞から身体Realityへ盤面を移すHuman-Sealed Prepared Routeである。**

### 2.6 Ark11 Project Deployment Rail

> **Ark11 Project Deployment Railとは、短いProject BootloaderだけをChatGPT Projectの`instructions（指示）`へ常駐させ、そのBootloaderを継承した新規ThreadへStart QueryのHuman Copy & Paste Surfaceだけを投入し、GitHub上の長文`INSTRUCTIONS.md`をRuntime SSOTとして全文復元・検証した後にDedicated Threadを`ARMED_AND_WAITING`へ移す、RepositoryからProject、Thread、Live Fieldへ至る二段Copy & Paste起動方法である。**

## 4. Architecture Ontology

```text
Repository Authoring Layer
└─ GitHub Document Set / Runtime SSOT
   ↓
Project Deployment Layer
└─ Short Project Bootloader in instructions（指示）
   ↓
Dedicated Thread Boot Layer
└─ Query Copy Surface / Arrival / Full-Read / Consistency
   ↓
Live Runtime Layer
└─ Armed and Waiting / Future Free Input / One Move / Review
```

| Entity | Owns |
|---|---|
| Project | Root Guard、Mission、Field間の秩序 |
| Field | 検証仮説、Prepared Mainline、Evidence Boundary |
| Project Bootloader | GitHub Runtimeの所在、起動条件、Hard Stop |
| Dedicated Thread | 待機状態、Live Event Context、会話Runtime |
| Start Query | Repository Binding、Full Read、Boot、Armed Transition |
| GitHub `INSTRUCTIONS.md` | 長文Runtime SSOT、Free-Input Interpretation、Live Contract |
| Future Human Input | その瞬間にHumanが渡せたReality Fragment |
| AI Response | Reality解釈、分岐圧縮、現在の一手 |

### 4.1 Status Separation

```yaml
field_status:
  meaning: "Field Architectureが運用対象として有効か"

dedicated_thread_status:
  meaning: "実在する専用ThreadがBoot済みか"

live_event_status:
  meaning: "Natural B Eventが実際に始まったか"
```

Field設計が有効でも、Dedicated Threadが未作成なら`thread: armed_and_waiting`とは記録しない。

### 4.2 Bootloader / Runtime Separation

Project `instructions（指示）`で長文Errorが発生したことは、Runtime内容を削るべきだという意味ではなく、配置先の責務が混線していたことを示すBottleneck Evidenceである。

```yaml
short_bootloader:
  target: "ChatGPT Project instructions"
  contract:
    id: "ARK11_PROJECT_BOOTLOADER"
    version: "v003-candidate"
  owns:
    - "Repository / Ref / Query / Runtime locator"
    - "Load order"
    - "Full-read before execution"
    - "Failure hard stop"

long_runtime:
  target: "GitHub INSTRUCTIONS.md"
  owns:
    - "Field Registry"
    - "Interpretation Contract"
    - "One-Move Runtime"
    - "Workout First Mainline"
    - "Evidence and Status Discipline"
```

Bootloaderを短く保つことはContextを捨てることではない。長いRuntimeへ確実に到達させるため、常駐層をPointerとGuardへ純化することである。

## 7. Free-Input Resilience

### 7.1 Valid Input Surface

次のすべてを有効な入力候補とする。

- `Help me!`
- `どうしよう`
- `動けない`
- `何すればいい`
- `眠い`
- `無理`
- 状況説明だけ
- 感情だけ
- 行動報告だけ
- 文法的に崩れた断片
- 音声入力の誤変換
- 通常なら意味を一意に確定できない一言

例は閉鎖リストではない。

### 7.2 Input Quality Is Evidence

不完全入力はProtocol Failureではない。

> **B状態から送信できた不完全な入力そのものがField Realityである。**

AIは受信内容を内部的に次へ分ける。

```yaml
input_interpretation:
  explicit_reality: "Humanが実際に書いた内容"
  reasonable_inference: "文面とThread Contextから合理的に読めること"
  unknown: "まだ確認できないこと"
  current_move: "Unknownが残っていても安全に通せる現在の一手"
```

InferenceをConfirmedへ昇格させない。一方、完全理解までHumanを質問Loopへ置かない。

## 10. Prepared Mainline: Workout First

### 10.1 Authority and Priority

Workout Firstは、過去のFog-to-Workout / Pattern-B Evidenceを持つHuman-Sealed Prepared Mainlineである。

しかし、Workoutは救いでもRootでもなく、Future Human Inputと身体Realityを無視して機械的に強制しない。

```text
Priority 1：Human Stop / Correction
Priority 2：Safety / Body Reality
Priority 3：Future Inputに明示されたCurrent Reality
Priority 4：Workout First Prepared Mainline
Priority 5：必要時だけ一問のClarification
```

### 10.2 Route確定とMicro-Step適応

```yaml
stable:
  - "B状態を分析Loopへ入れない"
  - "Workout FirstをPrepared Mainlineとして保持"
  - "Humanへ渡すのは現在の一手だけ"
  - "Fullを強制しない"

adaptive:
  - "Current Micro-Step"
  - "Full / Short / Recovery"
  - "明示された場所・身体状態への適応"
  - "Protective Exit"
```

### 10.3 Strict Entry / Flexible Depth

```text
Entry：Workout First Mainlineへ接続
Depth：Full / Short / Recovery
```

### 10.4 Protective Exit

Humanが体調不良、安全に立てない、運動が危険、Recovery Workoutも困難、運転中など安全上のRealityを明示した場合は、Workoutを救済化せず、Safety / Recovery / Sleep等の最小安全Actionへ切り替える。

AIは身体診断を行わない。

## 11. One-Move Interaction Architecture

### 11.1 Default

AIは全体Routeを内部で保持してよいが、Humanへ渡すのは現在の一手だけである。

```yaml
default_response:
  acknowledge: "短く"
  analysis: "表示しない"
  questions: 0
  choices: 0
  visible_moves: 1
  reply_requirement: "原則不要"
  objective: "Humanを画面外のActionへ送る"
```

文面はFuture Inputへ適応し、固定Macroの完全一致を要求しない。

### 11.2 Minimal Clarification Exception

質問は次の場合だけ許可する。

- Safetyに関わる
- 一手が正反対に分岐する
- HumanのStop / Maintenance入力かLive EventかがMaterialに不明

一度に一問、一語または短答で答えられる形にする。

### 11.3 Micro-Coach Fallback

HumanがOne Move後も画面に残り、`動けない`、`まだ`、`次`等を送った場合だけ、次の一手を一つ返す。

AI対話の継続自体を成功にしない。

### 11.4 AI Self-Termination

> **AI Coachの最高成果は、Humanとの対話を続けることではなく、HumanをPrepared Physical Actionへ送り、AI自身を最速で不要にすることである。**
