# Ark22 Canonical Body Candidate
## 外堀埋め / Outer-Moat Closure & Support Infrastructure

## 0. Thesis / 中心命題

Ark Projectは、Main Missionを完全に整理してから前へ進む方式ではなく、重要なVictoryへ必要な一手を先にRealityへ通し、途中で発生した未整理や周辺課題を後方へ残しながらもForward Motionを維持することでBreakthroughを積み重ねてきた。

このStrategyは有効である。

しかし有効であるからこそDebtが生まれる。

Ark22はそのDebtを理由にMainを停止しない。

Ark22は、MainとSupportを分離する。

```text
Main Line
= Breakthrough / Forward Motion

Ark22
= Support / Closure / Preparation / Return
```

Ark22のPurposeは「綺麗にすること」ではない。

> **Mainを再び軽く、速く、再起動可能にすること。**

---

## 1. Origin / 発見経緯

Ark21:03がChatGPT Work制限によって一時停止した後、Ark21:04ではMain Skillizationを二重化せず、周辺事項を整理・言語化・閉じながらMain復帰を待つ方針が採られた。

その過程で、ChatGPT WorkのReasoning Level、XHigh / Max、Reasoning Capital Allocation等、一見Ark21 Main Themeから外れるがArk Project全体へ高い再利用価値を持つFruitが回収された。

ここから次のUnexpected Success Candidateが生まれた。

> **Mainを直接進めない外堀Workが、Main復帰時の速度を上げる。**

さらにHuman Correctionにより、偶数系Arkは奇数系Main Arkを補助するために確保されているというNumbering Architectureと接続された。

したがってArk22は単発Cleanup Threadではなく、Ark Project横断Support AxisとしてProject化する。

---

## 2. Core Distinctions / 役割分離

### 2.1 Main vs Support

```text
Main
→ 目的を前へ通す
→ Breakthrough
→ Field Reality
→ Canonical advancement

Support
→ Main周辺摩擦を減らす
→ Deferred workを閉じる
→ Future frictionを先に除く
→ FruitをOwnerへ戻す
```

SupportはMainより低位ではない。

役割が異なる。

### 2.2 Cleanup vs Closure

Cleanupは見た目を整えることも含み得る。

Ark22の中心はClosureである。

```text
Cleanup
= tidy

Closure
= future friction no longer materially blocks the owner mission
```

完全な美観や無限整理はClosure条件ではない。

### 2.3 Preserve vs Own

Ark22はFruitを一時的に保持できる。

しかしOwner Arkが存在する場合、そのDomain Truthを奪わない。

```text
Ark22 may preserve.
Ark22 may route.
Ark22 may synthesize.
Ark22 does not silently capture ownership.
```

## 3. Forward-Motion Debt

### 3.1 Definition

> **Forward-Motion Debt / 前進負債**とは、Main Missionの前進を優先したため合理的にDeferredされたSupport Work、未整理、未言語、未検証、未統合、未Handoff等が、将来の再調査・Context Switch・誤Routing・Reworkとして再出現し得る状態を指す。

Debtは失敗の証明ではない。

Forward MotionのCost Structureを可視化するためのOperational Handleである。

### 3.2 Debt Categories

```yaml
debt_categories:
  organization:
    question: "Current address / role / file relationは明確か"

  naming:
    question: "重要Realityは再利用可能な名前を持つか"

  documentation:
    question: "Future Human / AIが重要Fruitを再構成せず読めるか"

  integration:
    question: "関連Fruitは適切なOwner / SSOTへ接続されているか"

  verification:
    question: "Reality確認を必要とするClaimが推測のまま残っていないか"

  handoff:
    question: "Thread / Tool / AIが変わってもCurrent Coordinateを回復できるか"

  decision:
    question: "重要Policyまたは判断保留が次回再議論を強制しないか"

  artifact:
    question: "Draft / Current / Historical / Canonicalの身分が明瞭か"

  preparation:
    question: "将来Main再開前に高確率で詰まるBottleneckを先に除けるか"
```

分類はToolではなくKeliであり、Realityによって追加・統合・削除できる。

## 5. Admission Logic

Ark22へ入れる前に、必ず次を問う。

> **これはOwner ArkのMain Missionを今進めるべきTaskか、それともMainを逸らさずSupport Lineで閉じた方が全体が速くなるPeripheral Frictionか。**

```yaml
admission:
  admit_when:
    - "deferred_from_main"
    - "future_friction_is_material"
    - "support_work_has_clear_closure"
    - "cross_ark_reuse_value_exists"
    - "owner_context_switch_can_be_reduced"
    - "preflight_has_high_acceleration_value"

  do_not_admit_when:
    - "it_is_the_owner_main_task_now"
    - "no_owner_or_value_can_be_identified"
    - "scope_is_unbounded"
    - "pure_cosmetic_cleanup"
    - "new_project_requires_separate_projectization"
```

AdmissionしないこともArk22の成功である。

## 6. Processing Loop

Ark22のDefault Loop：

```text
Receive
→ Fix Current Reality
→ Admission Gate
→ Identify Owner
→ Classify Debt / Friction
→ Choose Smallest Sufficient Closure
→ Execute or Draft within authority
→ Reality Review
→ Return / Preserve / Reject
→ Stop
```

Main Rule：

> **One bounded moat before another moat.**

一件を閉じる前に無関係な外堀を連鎖的に増殖させない。

## 7. Bounded Closure

Ark22の「完全」は無限整理ではない。

Current Itemに対して、

```text
Material friction identified
→ minimum necessary intervention
→ owner can proceed without material rework
→ current item can stop
```

となればClosure Candidateである。

```yaml
closure_not_required:
  - "perfect repository"
  - "all history normalized"
  - "all old files renamed"
  - "all notes converted"
  - "all future risks eliminated"

closure_required:
  - "material problem understood"
  - "owner identified or explicitly unknown"
  - "minimum intervention chosen"
  - "result verified when possible"
  - "remaining uncertainty exposed"
  - "return path clear"
```

## 12. Failure Modes and Corrections

### 12.1 Dumping Ground Capture

症状：
`Mainではない → Ark22`

Correction：
Admission Gateへ戻る。

### 12.2 Cleanup Paralysis

症状：
整理がMainより巨大化する。

Correction：
Smallest sufficient closure。

### 12.3 Perfection Capture

症状：
Repository全体を完全に綺麗にしたくなる。

Correction：
Current Material Frictionのみ。

### 12.4 Owner Capture

症状：
Ark22が他ArkのCanonical Truthを保持し続ける。

Correction：
Return Packetを作りOwnerへ戻す。

### 12.5 Support Mainification

症状：
Ark22 backlogがMain Mission化する。

Correction：
「誰のMainが軽くなったか」を問う。

### 12.6 Endless Taxonomy

症状：
Debt分類の設計が実Item処理より大きくなる。

Correction：
分類を減らし、実Item一件へ戻る。

### 12.7 Historical Reconstruction Trap

症状：
全Historyを再構成しないと整理できないと考える。

Correction：
Current Address First。Historyは必要な場合のみGitへ問い合わせる。
