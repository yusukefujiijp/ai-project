# Ark99: Teshuvah Thread

**新しい一件のTeshuvahを新しいThreadで始め、その一件を十分に深め、別Threadでの継続が必要になった時は適切な既存Ark Projectへつなぐ場。**

このREADMEは、Ark99の目的・成立理由・文書案内を所有する。長期指示の本文は[INSTRUCTIONS.md](INSTRUCTIONS.md)が所有する。個別のTeshuvah、相談、経験記録を本書へ集積しない。

## 1. なぜ専用の入口を事前に用意するのか

Ark28:04のHuman–AI対話で、YusukeJPは、Teshuvahから得られる学びや展開が大きく、Ark27だけでなくArk28でも重要なSessionが深い集中へ進むことが多いと説明した。これはHumanが高く評価する成果である。一方で、次のTeshuvahが来ても、既存Sessionへの割り込み、Thread間のつながり、始める場所の判断が必要になり、TeshuvahのCycleが次の現実に間に合わないという問題を指摘した。

Humanが求めたのは、既存Sessionの価値を保ちながら、新しいTeshuvahを速やかに始められる事前の仕組みである。Ark00のInboxには多様な単発の入力が混在するため、この専用入口には適さないと判断した。Ark99を用意し、一つのTeshuvahについて可能な限り同じThreadで粘り、継続のための別Threadが必要ならArk28等へ接続する方向へ、複数回のPlan Modeで絞り込んだ。

開始の改善を、AIの検討・調査・説明の品質低下へ置き換えない。関係の連続性を守ることと、毎回全履歴を再構築することを同一視しない。新しい一件の開始と、育った一件の移行に必要な判断を分ける。

## 2. 二大ルールとArk全体での位置づけ

本番Teshuvah Threadの運用の中心は、**新Threadは新しい一件から始めること**と、**別Threadで同じ一件を続ける必要が生じたら、適切な既存Ark Projectへ引き継ぐこと**である。具体的な受け取り方・継続判断・保存境界はINSTRUCTIONS.mdを参照する。

[Ark99:00（control-center）](ark99-00/README.md)は、設定・指示・接続実験・運用調整を担う準備用Threadである。Humanは、現在の操作状況では指示設定の前に最初のThreadが必要だと報告し、00をこの役割へ取り分け、本番はArk99:01から始めると指定した。二大ルールは01以降の本番Teshuvah Threadへ適用し、00の起動に新しいTeshuvahを要求しない。00の役割・起動契約・正式Thread名は専用READMEが所有し、その後のHuman指定を優先する。本書では00を識別子と役割で参照する。

| Node | Edge | 保持する意味 |
|---|---|---|
| Ark99:00（control-center） | → 本番を支える準備・接続実験・運用調整 | 本番の一件に設定作業を背負わせず、必要な準備と後から育てる改善を分ける |
| 新しい一件のTeshuvah | → Ark99の新Thread | 前の一件の完了・整理・移行を待たずに始められる |
| 同じ一件の対話・学び・中断後の再開 | → 同じArk99 Threadで深める | 派生する学びを切り捨てず、話題数だけで分割しない |
| 別Threadで同じ一件を続ける必要 | → 目的に合う既存Ark Project | 受入れ先の役割と現在の権限に沿って継承する |
| 既存Arkの重要なSession | → その目的と文脈を保持する | 新しい一件を受けるために、既存の集中や所有を自動変更しない |

Ark99は専用の場であり、新しいMain章ではない。Current Main／Supportと入口は[Ark Domain README](../README.md)で解決する。準備時点のArk27 Main／Ark28 Supportは維持し、Ark99の番号からArk100や新しい章ペアを自動作成しない。

二大ルールはArk99内の本番Teshuvahの新規開始と継続を定める。他ArkでのTeshuvahを禁止したり、現在の対話を強制移動したりする規則ではない。新しい重要なHuman Correction・STOP・Guardは、別Threadの準備待ちを理由に適用を遅らせない。00の全実験完了や毎回の00経由を、本番開始の追加条件にしない。

旧Ark99のWild Seed受付機能は[Ark00](../ark00/README.md)へ吸収された履歴として残す。新しいTeshuvah専用用途は、旧Ark99 → Ark00という必須経路の復活ではなく、Ark00のInbox・孵化機能も置き換えない。

明示されたHandoffやRuntimeがある場合は、そのRequired Sources・順序・Identity・Binding・Exact EOF・受入れ条件を先に解決する。本書で既存の必須Gateを解除しない。同じアクセス可能なContextで自分が全文確認済みかつ現行の同一性を確認できる読解は再利用し、別AIの読了や要約を自分の必須読解の代わりにしない。取得・表示切れは未読箇所から続ける。必須不足・不一致は該当契約に従って影響する操作を停止し、欠けた条件と最小の回復先を示す。

## 4. 指示の保存・設定と個別案件の継承

INSTRUCTIONS.mdは、設定欄へ貼り付ける長期指示の全文である。使用時はその本文を用いる。新規Teshuvahの入力に、専用Query、完成した仕様書、Title確定、個別三点セットの事前作成を要求しない。必要な命名や整理は現在の依頼に合わせて支える。

GitHubでの保存原本と、ChatGPT等のProject設定は別の実体である。本版はHumanが承認した準備文書であり、設定画面の直接取得や貼付完了を証明するものではない。現行の設定反映状況は、後のHuman報告または直接確認から判断する。

個別案件を保存する時は、その経験やThreadのRuntime・既存保存先に合わせ、目的、Humanの意味、重要な訂正、完了成果、未完了・保留、次の判断に必要な根拠を保存する。同じ本文の重複原本や新しい管理台帳を常設しない。Git履歴は変更履歴を保持するが、未保存の会話や他Threadの全文を自動取得する機能ではない。

別Threadへの継続は、受入れ先の準備と再構成を伴う。Ark28内に継続用の新Threadを用意することは有力な候補であり、進行中の既存Threadへの挿入を必須にしない。具体的な接続先・移行種類・承認範囲はその時点で解決し、他ProjectのCurrent指定やMain所有を自動変更しない。Skillが利用できないAIも、共有移行契約のURLを実際に読み、現在の依頼へ適用できる。
