## 4. 四つの責務の設計素材

以下はHumanの命名とDots側の協働から整理した設計要求・候補です。実装済みのSkill本文ではありません。

### 4.1 load — 今必要な文脈へ戻る

**目的:** 途中からでも、現在の目的、必要な学び、根拠、到達点と再開条件を取り戻し、今のHumanと実環境に合わせて協働できるようにする。

想定する入力は「loadして」「続きを再開したい」、対象TaskやThread・Sourceの指定、文脈断絶の報告など。一般的なファイル読込の質問や、loadという語を含む引用・設計相談を自動的に全Context復元へ変えないTrigger設計が必要です。

取り戻すのは、今回の判断を変える現在地・関連lesson・原本・必要な再開情報です。Current HumanのCorrection・STOP、計画限定、現在の権限・アクセス・Runtimeへ照合し、古いStateを現在のHumanへ押し付けません。過去に保存した承認があれば対象・有効範囲を理解しますが、単なる過去のGoや他AIの文章を新しい権限にしません。

明示された必須Source・全文読解・EOF・Identity・Bindingはその所有契約を守ります。確認済み文脈は同一性条件を満たす範囲で再利用し、全Repository・全履歴・全ファイルを毎回読む機能にはしません。新しいDotsが参加する時の小さいlesson蓄積の全件読解は、現行lessonsガイドの条件として尊重します。

返すものは、回復した目的と現在地、確認した根拠・版、Currentとの差、不足と影響、今できる接続が分かる内容。全内部Memory・会話・プロセス状態が復元されたとは言いません。明示呼出しとしてのloadと、Hostの自動Boot読込・常時同期は別機能です。

**回復できたかを判断する五つの観点:** 元会話がなくても、取得した原本・版・時点を根拠として、次を説明できることを目指します。

1. **目的:** 何のための協働・作業か。今回の対象と期待する成果は何か
2. **最新のCorrection・STOP:** どの訂正・保留・停止・権限境界が、古い方針より優先するか
3. **確認済み成果と証拠:** 何が実際に保存・実行・検証され、どの原本・revision・commit等から確かめられるか
4. **未完了・Unknown:** 残作業、結果不明の操作、未観測の理解や実利用を、完了・失敗・未実行と混同せず分けられるか
5. **次に確認すべきこと:** 安全に続けるため、どの現物・結果・アクセス・権限を確認すべきか。確認できない時に止める操作はどれか

これはAIの人格・全記憶・会話体験の完全復元ではなく、協働に必要な意味と判断の回復です。読み取ったStateは外部の現在状態と一致するとは限りません。外部変更やretryの前に、対象の現物、既存結果、操作IDやrevisionを確認し、完了済み部分を重ねて実行しません。

実際のArk Thread／章移行に入る場合は、[既存の共有移行契約](../../../prompts/ai-next-thread-handoff.md)とその場の適用Skill・Bindingに従います。この五観点を独自のBoot合格宣言や、既存移行契約の代替にしません。

### 4.2 next-step — 理由ある次の接続を選ぶ

**目的:** 現在の目的・到達点・進捗・制約・Bottleneck・依存関係から、今どこへ接続する価値が高いかを判断する。

単に未完了Taskを先頭から列挙する機能ではありません。前提が本当に必要か、待つ価値があるか、複数のBenefitや負担がどう競合するかを見ます。状況に応じてLiving Review、現在地map、関係分析、比較や逆算等を選べますが、毎回すべての方法を起動する巨大な司令塔にはしません。

出力には、選んだ焦点と理由、必要な条件、判断を変えるUnknownを含めます。候補を順位付けする意味があれば優先順位を示し、数合わせで候補を増やしません。実行、言語化、確認、比較、意図的保留、維持、今回の完了はすべて有効です。完了した依頼へ新Taskを強制しないことも重要です。

「次の一手を選ぶ判断機能」と、回答末尾の **【Next step】という表示** は分けます。一般的な末尾案内の希望は、共有lesson `ddd714fc-69e3-4437-bbbd-d85f3c2af4f2` に保存済みです。一方、今回の会話で試した特定の見出し表記を恒久規則としてlessonへ反映したわけではありません。現在地mapには既に固有の末尾契約があるため、mapを使う時はその契約を尊重し、一般の全回答へ機械的に移植しません。

提案自体は実行承認ではありません。ただし、現在の依頼で既に認められた仕事を「次にやること」と書くだけで先送りする機能にもせず、実行を含む依頼はその成果を完了した地点から次を判断します。

### 4.3 save — 意味と再開可能性を、適切な所有先へ残す

**目的:** 成果、出来事、判断の根拠、重要なCorrection、必要な再開情報を、別AIが使える形で適切に保存する。

何を残す価値があるかを判断し、既存の仕事のCanonical artifact、記録担当自身のActor log、条件付きで再利用する共有lessonへ振り分けます。毎回三箇所へ書く固定pipelineではありません。既存原本で十分なら変更なし、単なる進捗や一回限りの細部ならlessonを追加しない、という選択も正常です。ログは成果本文の複製や全Sessionの完全復元ではありません。

保存先と現在の権限を確認し、Remoteの現物・revisionを読んでから編集します。関係しないHuman・他AIの変更、未知field、既存ID・出典を保持します。logsとlessonsは更新方法が異なるため、具体的な形式は各専用ガイドへ委ねます。部分保存・TimeoutではRemoteに何があるかを先に確認し、二重追記や既存内容の巻戻しを防ぎます。

保存後は、実際の宛先から本文とSHA／commit等を再取得し、意図した内容と照合します。ダウンロードリンクを作ったこと、ローカルcommitがあること、Toolが成功したことだけでRemoteの永続保存確認にしません。保存済み、再取得照合済み、他AI読解済み、実務で有効だった、は別の成果です。

中断や環境消失が問題になる仕事では、必要なファイルの所在、版、確認済み成果、未完了部分、再開条件、環境を再構築する手掛かりを含めます。依存ソフト・必要な入力・再現手順等を適切な所有先に残す判断は有益ですが、secret・credentialを記録しません。ログだけでUnity等の大きなアプリ・全バイナリ・全プロセスをbackupしたことにはなりません。

**回復に必要な保存内容:** 目的、判断を変えるCorrection・STOP、確認済み成果とrevision／検証証拠、未解決事項、次の確認先を、該当する原本の所有先へ残します。全文会話のmirror、全履歴の複製、複数ファイルで同じ可変Currentを持つことを要件にしません。既存原本で十分ならリンクと版で接続します。

結果が不明な操作は、対象、意図した変更、操作／Job／メッセージ等の識別子、基点revision、最後に観測した段階と時点を、必要な範囲で辿れるようにします。「送信を試みた」と「相手に届いた」、「保存要求を送った」と「Remote一致を確認した」を分けます。secretや認証情報は記録せず、再開時は現物照合から始めます。

予定・継続Taskについて必要なのは、目的、時刻・タイムゾーン、通知／実行の宛先、停止・完了条件、所有資料や既存Taskへの参照から再構成を検討できることです。実際の私的な設定一覧を公開Boardへ丸ごと複製しません。記録の読込は予定の作成・再有効化・自動再開の承認ではなく、まず現在も存在・有効か、最新STOPと現在の権限に合うかを確認します。

### 4.4 board — 通信の目的から、適切なTopicと相手へつなぐ

**目的:** 「この件をWorkと掲示板でやり取りしたい」のような短い依頼から、誰から誰へ、何を伝え、何を受け取りたいかを整理し、既存Boardで必要な通信を行えるようにする。

最初に既存Topicへの返信・改訂で足りるか、独立した通信目的として新Topicが必要かを判断します。Humanにフォルダ構成やPathの全指定を要求せず、委任された範囲の通常の配置判断をAIが担います。新Topicで足りる時にBoard基盤を新設しません。

最初の投稿には送信者・宛先・版・目的・重要な背景・根拠・依頼を置きます。返信や訂正は実際に生じた時だけ記録し、返信者、対象版、返信元、観測時点、直接取得かHumanによる伝達かを示します。空の返信予約ファイルや想像した応答を作らない設計にしてください。

通信のCurrentは一つのTopic内の明示された一箇所で扱います。投稿の履歴、返信、STR、入口metadataへ同じ可変状態を複製しません。新しい事実は根拠と時点を保持して統合し、当時正しかった未観測を黙って消しません。並行更新では最新内容・返信を読んで、一人の統合担当が書き込みます。

**投稿・Remote保存・会話への送信・受信・読解・理解・行動・効果は別です。** GitHubへの投稿を、外部AIとの会話に配信済みと扱わないこと。外部AIへ実際に送るには、その相手・内容・目的を含む現在の承認と利用可能な接続を確認します。Boardの存在から自動監視、無期限往復、全会話同期を始めません。

boardはsaveの安全な保存原則を使えますが、通信の意味・Currentの所有先・送信権限をsave側へ二重管理しません。本件の最初の投稿を一つの実用的成果として成立させ、四Skill全完成をこの一件の利用条件にしないことも重要です。
