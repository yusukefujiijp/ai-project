# SQLite Correction

**Humanの訂正から、影響を受ける提案の再確認候補を、原文・出典・適用条件とともに取り戻す実験です。** 同じ構造化内容を、JSONLを読む方式とメモリ内SQLiteで比較します。SQLiteの本採用、Ark全体への導入、実生活での効果は示しません。

## 一箇所に閉じる構成

- [fixture.jsonl](fixture.jsonl)：原文と関係を含む合成原本。6 Node・4 Edgeの10行です。各行の`synthetic: true`、架空の話者、case IDにより、実際のHumanの経験と区別します。
- [run.py](run.py)：Python標準ライブラリのみを使う一件専用の実行コード。入力は同じフォルダのfixtureだけです。外部通信、インストール、他のRepositoryファイルの走査、出力ファイルの作成は行いません。
- [check_relation_swap.py](check_relation_swap.py)：基準と、実行中だけE3の始点を付け替えた入力を比較します。元のfixture・runnerと、その7つの期待値照合を保持します。
- [check_snapshot_version.py](check_snapshot_version.py)：C1.textだけが異なるV1・V2で、検索の成立と、検索前に固定した要求版V2への一致を別々に確かめます。派生入力はメモリ上だけに置きます。
- 本README：目的・結果・意味の限界・再開・撤去を所有します。

GitHubはコードと合成原本の保存先です。SQLiteは実行環境の`:memory:`内に構築し、読み込み後は`query_only`で問い合わせ、終了時に接続を閉じます。永続DB、常設サービス、GitHub Actions、Automation、既存のRecall／Task運用への接続はありません。

## ケースと問い

すべて架空です。Day 1・Day 2も合成時点であり、実際の日付やHumanの状態ではありません。`occurred_at`と`recorded_at`は、このケース内の出来事と記録の順序を保持する文字列です。

問いは「C1の訂正によって、どの提案を再確認する必要があるか。原文と理由も示してほしい」です。runnerはC1への固定問い合わせを実行し、自然言語からSQLを生成しません。

| Node | Edge | 原文・意味・適用範囲 |
|---|---|---|
| S1：Humanの原文 | I1の根拠として参照される | 「今日は静かな作業がよい」。Day 1だけの希望 |
| I1：AIの解釈 | I1 → S1：based_on | 「このHumanは常に静かな作業を好む」。未採用の一般化 |
| P1：提案 | P1 → I1：depends_on | 静かな作業を今後の標準候補にする未採用案 |
| P2：派生提案 | P2 → P1：depends_on | 次回も静かな作業を最初に提案する未採用案 |
| C1：訂正 | C1 → I1：corrects | 「その日だけの希望だった」。I1を訂正し、S1の当日の希望は消さない |
| U1：別提案 | 今回の依存経路に含めていない | 別目的の静かな曲選び。語が似るだけで対象へ含めない |

関係の根拠は合成ケース作者の明示設定です。`based_on`はAIが根拠として使った関係を表し、出典がその主張を正当に支持するとの認定ではありません。これらは既存Arkの共通Schemaや実データではありません。

## 比較する処理

ファイル方式はJSONLの関係をPythonで辿ります。SQLite方式は同じレコードをメモリ内のNode・Edgeテーブルへ入れ、再帰CTEで依存関係を逆向きに探索し、根拠の原文を取得します。出力の`depends_on_path`は提案から前提へ向かう、元の関係方向です。

両方式の候補、経路、原文、訂正、時点、適用条件、関係の根拠、行番号とIDを含む出典参照を比較します。全取得内容が一致するかに加え、既知の期待候補・経路・文脈の集合を確認します。共通のJSONL読込と出力整形を使っているため、二つの完全独立した検証系ではありません。

期待結果はP1・P2、前提I1、原文S1、訂正C1と4関係です。U1は今回の登録経路からは到達しません。P1・P2の誤り確定、取消し、採用、実行は行いません。


## 追加比較：存在するIDへの誤った関係

問いは「存在するID同士を誤って結んだ場合、入力検査、二方式の検索、既知の正解との照合は、それぞれ何を検出できるか」です。基準の既知の正解P1・P2を固定し、結果に合わせて変更しません。

基準の10行をそのまま使う条件と、メモリ上のコピーだけで9行目のE3.fromをP2からU1へ変更する条件を、一組として比較しました。E3の種別・方向・変更前の値を確認し、他のfield、他の入力行、6 Node・4 Edgeを保持しています。E3.scopeの「P2 uses P1 as a premise」とU1の原文・scopeもそのままです。そのため、付替え後の構造と説明には意図した不整合が残ります。

追加スクリプトは、標準ライブラリの一時的な読取差替えにより、元の`run.main()`へ各入力のバイト列を渡します。ファイルを書き換えず、既存の読込、両方式の検索、7つの期待値照合をそれぞれ一回ずつ実行します。通常の基準が成立しない場合は付替えへ進みません。読取差替えは呼出しの終了時に解除されます。

出力中の出典には、基準パス・行・IDに加え、入力variantとhashを付けます。付替え後のE3を保存済みfixtureの内容と誤認しないためです。結果ファイル、DBファイル、派生fixture、bytecode cacheを保存する処理はありません。SQL接続は既存処理の`:memory:`だけを使います。

### 判断に使えることと限界

この一件では、存在するIDへの誤った関係を入力検査とSQLite処理が受け入れ、二方式が同じ誤登録に従いました。一方、元の実験にある固定した期待値照合は、その結果の不一致を検出しました。「SQLite単体で意味を判定しない」と「比較全体が見逃す」を区別できます。

AIの設計上の見立ては、原文・関係の採用理由・適用条件を取り戻し、検索結果の外にある根拠でも評価できるようにすることです。SQLiteの不採用を導く結果ではなく、任せられる照会処理と、その入力関係の妥当性を確かめる仕事を分ける根拠です。

基準も付替えも一つの手作り合成ケースで、共通parser・出力整形を使います。期待値はケース作者が定めたものであり、AIが未知の自然言語から正解を発見した証拠ではありません。誤った説明文まで一貫した場合、欠落した関係、撤回、別時点、実データ、別AIの理解、Humanの価値評価、実生活効果は未確認です。

## 追加比較：検索の成立と指定した原本版への一致

問いは「古い合成原本から検索が正常に成立した時、要求された版を使ったと誤認せず区別できるか」です。実験IDは`SQLITE-CORRECTION-SNAPSHOT-VERSION-001`。既存の検索と7項目の期待値照合は変更せず、指定版の照合を別に追加しました。

### 検索前に固定した版と期待結果

- **V1**：保存済みfixture.jsonlの正確な3,226バイト。変更しません。
- **V2／今回の要求版**：メモリ上のコピーで、5行目C1.textの末尾へ「次の相談では、その日の希望を確かめてください。」を空白・改行なしで追記した3,295バイト。
- V1のhashとC1の変更前の種別・話者・原文を確認します。C1行だけをキー順保持・UTF-8・`ensure_ascii=False`・compact separatorsで再シリアライズし、他のfield、他の行、全関係、6 Node・4 Edge、末尾LFを保持します。
- V2のバイト列とSHA-256を検索前に算出し、要求hashを新スクリプトの定数として固定しました。実行時にも、検索に入る前に再構成した不変のbytesがその固定hashと一致することを確認します。照合対象V1に合わせて要求hashを書き換えません。
- 予測は、両版とも既存の検索・7項目が成立し、両方式の候補はP1・P2。別の版判定は、要求V2／入力V2が`MATCH`、要求V2／入力V1が`MISMATCH`、要求版情報なしが`UNKNOWN_REQUIREMENT`です。実測を見て期待値を変更していません。

これは合成原本の版差を作る設定です。追記文は実際のHumanの発言でも、現在の行動命令でもありません。合成時点のoccurred_at・recorded_atも変更しないため、実世界での訂正履歴・有効期間の更新を実装した例ではありません。

### 方法と実行

```sh
python -B sandbox/sqlite-correction/check_snapshot_version.py --base-source-commit b45bb32387473a71691b402c4c4ed65716e03d31
```

上記commitは今回取得・照合した基準のfixture・run.py・check_relation_swap.pyの版です。新スクリプトの保存先commitや、実行時の最新mainを自動認定する引数ではありません。別の取得版から実行する場合は、取得者が確認した版を渡します。未指定時はnullとなり、バイト列はhashで特定します。固定した基準fixtureと異なる入力なら、要求版を追従変更せずエラーで止まります。

新スクリプトはcheck_relation_swap.pyの`observe()`を再利用し、元の`run.main()`へV1・V2をそれぞれ一度渡します。各回にファイル検索とSQLite検索、既存の7項目が実行されます。関係付替えスクリプトの`main()`は呼ばず、E3の付替え比較は再演しません。V1は今回の版差比較の対照として使います。

三つの版判定は、この二回の取得結果に対するメタデータ照合です。「要求版情報なし」はV2の既存結果を再利用し、第三の検索やDBを作りません。指定ありでは固定したV2の正確なbytes・hashの両方を照合し、指定なしでは比較先がないため一致・不一致を判定しません。

AIへ返す各原文・関係のsource_refには、基準パス・行・ID、input_variant、入力hash、呼出し側が指定した基準commit、基準hash、変換IDと内容を結び付けます。V2は基準commitのfixtureそのものではなく、同じ位置から派生した入力です。出典欄のパスだけを見てV1の本文と混同しないための区別です。V2の派生原本ファイルは保存しません。

### 実測：2026-11-11の一組
