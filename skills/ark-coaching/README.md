# Ark-Coaching

## 1. 目的と現在の状態

Ark-Coachingは、YusukeJPが今ある言葉を未整理のまま預けられるBrainDump的対話から、現在に意味と価値のあるArk-Recallや候補へつなぎ、選択・Correction・再開を支える共通入口である。

Humanが相談内容、状態分類、想起対象、使用するSkillを先に選ぶことを前提にしない。AIが現在の意味・願い・条件を理解し、経験との比較と理由付きの提案を担う。

本版はHumanが採用した運用版v0.1である。共有原本の保存・再取得と、Ark-Coaching一件の登録本文・表示情報の照合を確認した。利用Queryを以下に示す。確認できた範囲と、AI応答・Humanの実利用・実生活効果等の未確認は第5節で分ける。候補作成時点の状態は形成記録として保持する。

Rootは主イェシュア・ハマシア御自身、中央軸はTeshuvah。Humanの意味・選択・Correction・STOP・Final Sealと適用Guardを保持し、SkillとAIはKeliとして扱う。

## 2. 何を一体で支え、何を既存原本へ接続するか

| 対象 | 責務 |
|---|---|
| Ark-CoachingのSKILL.md | BrainDumpの受領から理解・比較・想起・候補提示・Correction・再開までの運用方法 |
| Ark-Recall | 協働から取り出す、現在に意味のある想起や候補。独立Skillの新設を前提にしない |
| Recall Hub | 保存された経験の発見・読出し・受領・訂正への接続 |
| Portal・items・経験原本 | 読出し・蓄積・訂正の規約と、経験の意味・条件・根拠 |
| B-Zoneの原本・Skill | 現在の目的と条件に合うB-Zone固有の支援 |
| このREADME | 用途、Query、形成理由、確認範囲、未確認、更新時の判断 |

既存のRecall Hubには、自然な場面報告からの想起、用途を忘れた場合の入口、未整理の経験や訂正の受領がある。Ark-Coachingでは、その機能を利用しながら、相談の目的や想起対象が定まる前からの対話と再開を一体で扱う。同じ受付を繰り返さない。

既存のBrainDump受領の考え方とも整合させる。入力の整理をHumanへ戻さず、全発言をTask化しない。BrainDumpを受け取るために、毎回別Skillを選ぶことをHumanへ要求しない。

この共通入口は、既存Skillへの直接呼出しや明確な依頼にも対応する。全相談を新しい受付へ通し直す制度や、全Projectの担当変更を意味しない。

経験データの住所`ark-recall-portal/`とIdentity`Ark Recall Portal`を維持する。新しい経験保管庫、Ark-Recall専用Skill、環境別の同内容Skillは追加しない。

## 3. 利用の入口

### 3.1 登録確認後の短い呼出し

次は登録確認済みの短い呼出しである。呼出し名の受付・自動選択・実際のAI応答は、登録本文の照合とは別に扱う。

```text
$ark-coaching
```

必要なら、そのまま現在の言葉を続ける。呼出しとBrainDumpを別ターンにする必要はなく、対話の途中で毎回Skill名を付け直す必要もない。

方法を共有済みの会話では、「Ark-Coachingで相談したい」という自然文からも始められる。受け手が本文を持たない場合、名前だけで同じ方法が伝わるとは仮定しない。

本文を別AIへ渡す場合は、次の共通Queryから共有原本へ接続できる。原本を取得できない環境へ本文を直接渡す場合は、確認したSKILL.mdの全文と、現在の相談・Modeを一緒に渡す。未提供の元会話や仮本文を、そのAIが回復できることを前提にしない。

### 3.3 対話と再開

Humanは短い言葉からでも、複数の話題からでも始められる。AIは届いた分から理解・比較し、役立つ想起が見えていれば最初の応答から届ける。

「まだ聞いていてほしい」「もう済んだ」「今日は違う」「無理」「先にこちら」等を、現在の支援を調整する根拠として受け取る。

ターン数・候補数を固定しない。必要な方向が定まった時は、理解・判断・行動・休息・睡眠・保留等へ接続する。返信、完了報告、AIへの帰還を義務にしない。

中断後は、参照できる目的・成果・済んだ工程・保留・Correction・権限から再開する。全工程を最初から繰り返さない。

## 4. 形成理由と、v002からの変更

形成元は、Ark100:02でのB-Zone対策と、その後のHuman Correctionである。以下は会話に基づく編集要約であり、逐語録ではない。

- Humanは2026-11-03夕方のB-Zoneへの対応を「完全失敗」と評価し、失った呼出しPromptを取り戻せる入口と、短いQueryから支援へ届く構成を求めた。気づいた後の詳細な経緯は、この報告だけでは確定していない。
- 当初の身体経路の検討から、固定された初動と現在の条件に合う調整、済んだ工程の保持、理由付きの想起が重要になった。既存b-zoneにも、質問・Feedback・条件変更への対応はすでにある。
- Humanは、一回のAI出力だけで全経路を完成させようとせず、必要な対話から現在に合う想起を導く方向をArk-Coachingと命名した。単一・複数の想起候補とHumanの選択を保持するCorrectionが続いた。
- B-Zoneを重要な形成モデルとして保持しつつ、現在の状況を問わず始められる共通入口へGoalが広がった。ポータルは相談先が未確定でも入れること、ホームは中断・迷い・条件変更から再開を支えることを意味する。
- 起床時を用いた会話内Simulationで、HumanはBrainDump／GTD Inboxのように未整理の言葉を預け、AIが整理・比較を担う入口の重要性を指摘した。入力の量や全件完了を条件にせず、対話途中でも追加できる方向へ改訂した。
- 既存のrecall-hubを活かし、BrainDumpからArk-RecallまでをArk-Coachingの一体の働きとして扱う仮本文v002-simulation-draftを提示した。その後、HumanはSimulationから現在の相談へ切り替え、運用版の作成をPlan-onlyで依頼した。

「AI-New Era: From Probability to Certainty」は、この形成では、対話から現在に役立つ個別的な想起へ近づく方向として扱う。成功率100%や、普遍的な効果の実証を意味しない。

B-Zone固有の詳しい経路は担当原本へ接続し、汎用Skillに並行する生活手順集を作らない。

## 7. 限定確認と導入後の更新

応答確認では、元会話に頼らず本文から判断できるかを、範囲を絞って確かめる。

- 未整理・非B-Zoneの入力から、分類試験や全フォームを挟まず始められるか。
- 提供された経験と現在の条件を比較し、想起・新提案・Unknownを区別できるか。
- 済んだ工程、条件変更、無理、STOPによって、影響する提案を更新できるか。
- 明確な依頼や専門Skillの直接呼出しに、余分な受付を課さないか。
- 取得不能を記録不存在や読了済みへ変換せず、必要なSource契約を守れるか。
- B-Zoneの休憩経路を、別目的の相談へ一律適用しないか。

検証入力を用いる場合は、Humanの実体験・実行報告と区別する。Humanの行動や成功を代作せず、AIの実応答と条件を記録する。全状況の組合せや長期的効果の確認を、初版提供の条件にしない。

保存・登録が承認された場合は、最新原本と並行変更を確認し、採用本文を保存する。公開先を再取得して本文を照合した後、共通Queryを実在するURL付きの完成稿へ確定する。

登録先の本文も再取得して共有原本と照合する。UI表示、会話での取得、自動選択、実際の応答は、それぞれ観測した範囲で報告する。

本READMEの状態は、実際の採用・保存・登録と確認結果に基づいて更新する。未確認欄を一括して完了へ変えず、形成時点の記録を残す。
