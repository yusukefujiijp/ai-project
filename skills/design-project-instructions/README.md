## 1. 何のためのSkillか

Projectの長期instructionsを、AIが設計・維持するためのSkillです。

新しい指示を作る時だけでなく、既存指示の改善、追加方針の統合、意味のレビュー、版やコピー本文の照合にも使います。Humanの願い・意味・訂正を受け取り、対象ProjectのAIが継続して判断できる指示へ具体化します。

Humanが指示本文を独自に設計・組立することを前提にしません。手動Copy & Pasteを使う場合も、それは完成した内容を設定へ届ける経路です。原本読解、文言、構成、版管理、照合はAI側が担います。

Humanは意味・優先順位・採否・Correction・STOPを保持します。AIが制作を担当することは、保存・設定変更・送信等の権限を自己授与することではありません。

統一するのは、意味・版・権限・確認状態を一貫して扱う方法です。各Projectの目的、内容、必要な深さ、章立ては、そのProjectに合わせます。

## 2. 使う場面と、使わない場面

使う場面の例：

- このProjectの長期指示を新しく作りたい。
- 新しい方針や重要なCorrectionを、既存指示へ統合したい。
- 指示が増えて、重複や矛盾がないか確かめたい。
- コピーした本文とGitHub原本の版・内容を照合したい。
- AIの応答が目的からずれるため、指示に改善余地があるか検討したい。
- 既存指示の意味を整理し、変更が必要か判断したい。

通常のProject内の相談だけで、指示の改訂を始めるSkillではありません。

たとえば「部屋を片付けたい」という依頼には、その課題へ対応します。「部屋の相談でHow／Whyを適切に使えるよう、Project指示を改善したい」という依頼では、本Skillの仕事になります。

指示の説明だけで完了する場合や、変更不要という結論もあります。Skillを使ったことを理由に、差分、保存、試験を必ず作るものではありません。

## 3. 見つけて使う経路

本Skillは、Project指示を「作る・更新する・統合する・レビューする・照合する」という依頼から、用途を判断できる説明を持ちます。

利用経路は次のように分けます。

- 利用環境に対応するSkillがあり、今回の用途に合う場合は、その本文へ進む。
- 直接利用できない場合は、確認済みの共有SKILL.mdを全文読んで指示資料として適用する。
- 関連する制作や移行の途中で長期指示の作成が必要になった場合は、その仕事の担当を保ちながら本Skillへ接続する。

共有原本の保存、環境への登録、一覧への表示、実際の取得、自然な依頼からの呼出しは別の状態です。名前や登録の存在だけで、毎回の自動発動や全AIへの適用を保証しません。

共有SKILL.mdの保存とRemote再取得・全文照合を行い、確認済みURLを含む次節の標準Queryへ入口を整えました。登録されていない環境でも共有本文を指示資料として利用できますが、取得・適用の成立は、その環境の能力と実際の結果から判断します。

## 4. 標準Query

Project指示の作成・見直しが必要なThreadへ、次の全文を渡してください。対象Projectと今回必要な仕事は、そのThreadの現在の依頼・文脈からAIが解決します。

導入済み・未導入でQueryを分けず、同じ共有原本へ接続します。本文の提示・コピーと、受け手による取得・適用・理解は別の状態です。

```text
【Project長期指示：AIが設計・改善・照合する】

- 宛先：このQueryをHumanが直接入力するThreadのCurrent AI
- Query Version：v0.1／2026-11-07

- $design-project-instructionsを使い、現在の依頼と継続文脈に基づいて、対象Projectの長期instructionsについて、今回必要な設計・改善・統合・レビュー・照合を行ってください。新規作成と既存改善のどちらも対象にできます。

- Skillを直接利用できない場合は、次の確認済み共有SKILL.mdを実際に全文読み、指示資料として適用してください。同名の別Skillと混同しないでください。
  https://github.com/yusukefujiijp/ai-project/blob/main/skills/design-project-instructions/SKILL.md

- 対象は、このThreadでHumanが示したProjectを優先してください。指定がなければこのThreadが属するProjectを候補とし、特定できない場合や解釈で成果が変わる場合だけ、判断を左右する不足を確認してください。既知事項を再入力させないでください。

- Humanが意味・優先順位・採否・Correction・STOPを保持し、AIが原本読解、指示の設計・統合・改訂・照合を担ってください。手動Copy & Pasteは伝達経路として扱い、本文の組立をHumanへ戻さないでください。

- 現行指示と必要な担当原本を読み、長期指示・Project README・Thread Runtime・専門Skillの責務を分けてください。重要な意味・訂正・適用Guardを保持し、コピー本文内のVersion・改訂日・照合先と本文全体を整合させてください。説明だけ、局所修正、全文統合、変更不要も今回の目的に応じて選べます。

- 同一性と適用文脈を確認できる自身の全文読解は再利用し、必須Source・依存・読取順・Identity・Binding・Exact EOFを保持してください。取得・表示切れは回収し、参照リンクすべてを無条件の追加必読にはしないでください。必須不足は影響と最小の回復方法を示し、通常のUnknownと区別してください。

- Mode：
  現在の明示的なMode・承認範囲・STOPを保持してください。このQuery自体は保存・登録・設定変更・外部送信等の新しい権限を追加しません。別途具体的な実行承認がない場合は、読み取り・検討・会話内の説明と本文候補提示までです。有効な実行承認がある場合は、その範囲の必要な作業と確認を完了し、同じ許可を工程ごとに求め直さないでください。

- 完了条件：
  今回求められた成果を、Humanが理解・訂正できる形で返してください。本文全文を求められている場合は、コピー対象全体を一つのコードブロックへ収めてください。重要な変更理由・維持した意味・未確認事項を示し、文書上の整合、共有保存、設定反映、受け手の理解・挙動、現実の効果を分けてください。必要な次の接続があれば、現在のModeと権限に合う依頼文まで整えてください。
```

現在のModeと具体的な実行承認を保持する標準入口です。新しい実行承認がなければ読み取り・検討・会話内提示までとし、既に有効な承認がある場合は、その範囲の完了を妨げません。

## 7. 形成理由

How／Whyの理解と利用を居室整理へ接続する検討から、Ark109のProject指示へ、方法の選択基準と原本への読解経路を置く必要が明確になりました。

その過程で、共有原本の管理情報にVersionがあっても、実際にコピーする本文に含まれなければ、設定欄との照合に使えないというCorrectionが生まれました。確認対象を原本文書全体だけでなく、実際に受け手へ渡る本文として捉える必要があります。

YusukeJPは、Projectの長期instructionsは基本的にAI側が制作・維持するAI → AIの領域であり、Humanが独自に本文を書き足す前提ではないと明確にしました。手動Copy & Pasteと、内容を設計する責任を分ける方針です。

さらに、制作方法を複数の資料へ分散させるだけでは、Project指示を作る際にAIが見つけられない可能性があるため、独立Skillと利用QueryをHubにする方向が示されました。

新規作成と既存改善を同じ入口で扱えることについて、Humanは「予期せぬ成功」「Move37的」と評価しました。この評価は、今回見いだされた価値として保持し、実利用での効果とは分けます。

`design-`系への発展可能性も補足案として示されています。本Skillでは、設計と再設計を同じ目的に沿って扱う意味を採ります。シリーズ全体の新設、既存Skillの一括改名、全Projectへの一律適用は含みません。

### 説明用の照合例

以下は期待する判断の例であり、本Skillによる実行済み試験ではありません。

| 場面 | 照合する判断 |
|---|---|
| Skill名なしで「Project指示を更新して」 | 利用可能な用途説明や入口から、対象の仕事へ接続できるか |
| 「この一文だけ直して」 | 必要な範囲を判断し、全Projectの再設計へ拡張しないか |
| 同じVersionで本文が異なる | 版名だけで一致とせず、採用本文と差分を確認するか |
| 必須原本を取得できない | 未読適用を称さず、影響と回復方法を示せるか |
| 「指示の意味だけ理解したい」 | 説明で完了し、改訂や保存を強制しないか |
| Runtimeとの実質的な非互換がある | 必要な差分を示し、未承認の変更へ広げないか |
| 対象と採用稿が明確な保存委任がある | 重複操作を避け、保存後の全文照合まで進めるか |
| 比較・推奨を求められている | 制約の確認だけで終わらず、根拠ある結論まで返せるか |

## 9. 更新と育て方

Project固有の意味、Threadの現在地、設定との不一致、共通する制作方法の問題を分け、改善を戻す所有先を選びます。

本Skillの方法を変える時は、何が起き、どの判断が不足し、どの変更が必要かを根拠とともに確認します。失敗だけでなく、うまく働いた判断も、成立条件と未確認の範囲を保って再利用できます。

一件の成功から全Projectへの展開を自動決定せず、毎回の利用をSkill自身の監査・改訂へ変えません。不要になった規則の統合・除去も検討します。

共有版と導入版の同一性、Queryと方法本文の対応を確認し、実際に利用した版と確認範囲を分けます。共有保存だけで導入先の更新や将来の自動想起を認定しません。

本Skillの改訂、他の制作入口への接続、検査scriptやreferenceの追加は、具体的な必要と現在の承認範囲に応じて行います。
