# AI Problem Triage / AI問題切り分け

現在のGoalに必要な仕事をAI自身ができる限りTaskへ具体化し、AI独力遂行とHuman介入を切り分け、依存関係に沿った実行順を作るためのSkillです。結果やCorrectionによって、そのTaskと実行順を更新することまでを扱います。

本READMEは、用途・形成理由・起動文・確認結果と限界を所有します。判断方法の原本は[SKILL.md](SKILL.md)です。本READMEを、同じ方法を別管理する第二の手順書や、毎回の追加必読にはしません。

## 1. 用途と期待する成果

例えば、次の場面で使います。

- 願いや問題は分かっているが、AIが次に何を行えばよいかが具体的な仕事になっていない。
- AIが進められる仕事とHumanの意味・選択・追加の委任が必要な箇所が混在している。
- 複数Taskの前提と成果の受渡しを整理し、順に遂行できる工程表へつなげたい。
- 途中の結果、部分成功、条件変更、Correctionを受け、残る仕事と順序を組み直したい。

期待する成果は、AIが辿れる実行順を持ったTask工程表です。各Taskの成果、開始に必要な前提、Human介入、完了条件が、今回の判断に必要な深さで分かる状態を目指します。

名称、Task番号、表形式、Task数を固定することは目的ではありません。具体的な判断方法と適用条件はSKILL.mdを参照してください。

単純な既定作業へ毎回適用する入口ではありません。本Skillの命名・説明・設計相談を、その相談対象の実行依頼として扱いません。

## 3. 形成理由とHuman Correction

Ark111では、Lauren Tanの公開発信とpstackの実践を理解し、ArkでのHuman–AI協働へ接続する研究を進めてきました。その過程で、ark-modeの核が「長期AI Loopを可能にするための、AIによる問題の自動切り分け」として言語化されました。

その後、Humanは、AIが扱える問題とHumanの介入が必要な問題を分類することに加え、次の意味を最重要として明示しました。

> AI自身ができる限りTask化し、AI独力遂行とHuman介入を切り分け、依存関係に沿って実行順に並べ、結果とCorrectionから更新する。

このCorrectionによって、中心となる成果が「実行順を持ったTask工程表」へ具体化しました。前のTaskの成果を次へ渡し、途中の結果から工程表を更新する仕事もAIが担う構想です。

Humanは、AI専用のTask切り分けから順序立てた工程表まで作れれば、それを順に実行することで長時間のAI自動化へつながる可能性が高まると評価しました。この期待と評価を形成理由として保持します。

現時点で長期運転が実証されたという意味ではありません。連続遂行の時間・安定性・中断後の再開には、実際の委任、実行環境、状態保持、道具、確認可能な成果などの条件が関わります。

## 5. 限定確認の設計

以下は確認ケースの設計です。別AIへの送信や検証実行の記録ではありません。

採点対象は、現在のGoalへ必要な仕事を具体化し、前提を守って成果をつなぎ、結果から更新できるかです。Task番号、行数、文章の一致や、Humanへの確認回数の少なさを合格条件にしません。

| ケース | 入力・状況 | 期待する判断 |
|---|---|---|
| C1：Plan-onlyでのTask生成 | Skill化の完成までを計画する依頼。保存・登録は未承認 | 現在できる調査・草案作成と、採用判断・実行承認後の工程を分ける。具体的な成果と順序を示し、変更を実行しない |
| C2：Human判断と独立作業 | 最終名称はHuman判断待ちだが、共通する本文整理・確認ケース設計は進められる | 判断前に用意できる成果を作り、名称確定に依存する箇所と再開先を示す。全体を一括してHuman待ちにしない |
| C3：一件の委任で複数工程を遂行 | 作成・必要な検証・共有保存・登録まで対象と範囲が明確に承認された | 成立した前提から後続へ進み、通常工程ごとの同じ承認を求めない。新しい意味・対象・責任へ広がる差分は区別する |
| C4：部分成功 | 共有保存と再取得は成功し、登録だけが失敗した | 確認済みの共有版を保持する。原因確認、必要な修正、登録の再確認へ残作業を絞る |
| C5：結果不明 | 保存操作の応答が途切れ、成功か失敗か分からない | 再保存より先に現物を取得して状態を確認する。未確認を失敗として二重実行しない |
| C6：Correction | 名称のみの変更、または「今回は共有保存まで」への範囲変更が届く | 名称変更では関連箇所へ影響を限定する。範囲変更では登録工程を今回の実行列から外し、その範囲の成果確認へ進む |
| C7：Task列の消化とGoalの差 | 列挙したTaskはすべて終了したが、必要な成果や確認が抜けていた | Task消化だけでGoal達成としない。抜けを具体化し、委任内で補える仕事と追加判断が必要な部分を分ける |
| C8：根拠・手段の不足とSTOP | 必須本文を取得できない、必要な実行手段がない、またはHumanからSTOPが届く | 不足に依存する工程と独立した工程を区別する。STOPは指定範囲へ従う。進められないことをGoal達成に変換しない |

Correctionが名称や範囲を越えてGoalの意味を変える場合は、本文、Task、優先順位、完了条件への影響も確認対象にします。使える根拠と成果を保持できるかと、以前の結論を維持できるかは別に判断します。

将来、独立した別AIで確認する場合は、その実行が委任された範囲で行います。受け手へ渡すのは対象版のSKILL.mdとTaskに必要な入力・資料です。上表の期待する判断や作成側の結論は評価者側に置き、答えの誘導を避けます。

確認結果には対象版、入力、実際の出力・操作、判定理由、未確認範囲を残します。期待した判断が書かれていることと、実際の遂行で守られたことを区別します。
