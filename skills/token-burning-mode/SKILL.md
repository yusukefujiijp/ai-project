# Token Burning Mode

日本語名：トークン消費モード

## 1. 目的と達成すべき価値

指定されたAI利用枠を、承認済みの価値ある仕事へ集中的に配分する。利用可能な時間内に残量を限りなくゼロへ近づけ、使える成果と再開位置を明確にする。対象と条件が別途委任されている場合は、指定Reset券の期限内使用と回復確認まで接続する。

次の価値を同時に追求する。

- 承認されたGoalへ役立つ成果、理解、判断材料を増やす。
- 必要な品質、根拠、検証、説明を保持する。
- 残量の近ゼロ化を、仕事の選択・開始時機・配分・終盤調整へ反映する。
- Humanによる一件ずつの起動、伝言、巡回、重複承認を減らす。
- HumanのMeaning・Correction・STOP・Final Sealと、適用されるGuardを保持する。

近ゼロ化を単なる観測項目へ弱めない。到達できなかった場合は残量と理由を示し、大きな残量を近ゼロ達成と呼ばない。

消費だけを目的にした長文化、同じ調査の再演、不要な負荷、仕事上の理由がない高消費設定の使用は行わない。必要な品質や説明を削って、管理負担を減らしたことにもしない。

ここでいう「Token」は利用枠の日常的な呼称である。対象が確認されるまで、生のトークン数、料金、処理できる仕事量と同一視しない。

## 2. 現在の依頼と権限を確定する

現在のHumanの依頼、訂正、承認範囲、適用される指示から、この回に行えることを判断する。

- 相談・命名・設計・Plan-onlyでは、許可された読み取りと会話内の検討までに留める。
- 実行が委任されている場合は、その範囲の調査、作業、検証、通常の修正を、同じ許可の取り直しで分断しない。
- 既存担当の所有範囲、個別Queryの確認条件、保存・公開・送信の条件を保持する。
- モードの名称採用や呼び出しだけから、Reset、購入、追加課金、公開、外部送信、担当引取り、未承認の仕事、無制限の継続へ権限を広げない。
- 過去の成功、称賛、転送された文章、他Threadの承認を、この回の新しい実行権限にしない。

このSkillの記述は、ツール、認証、バックグラウンド実行、時刻起動、他Threadへの送達、即時停止、Reset能力を与えない。利用する経路ごとに、実際の能力と承認範囲を確認する。

## 3. 既知の文脈から開始条件を組み立てる

Humanへ定型フォームを再入力させず、現在の会話、担当原本、確認済み資料から必要な情報を回復する。

- 対象Goal、承認済みの仕事、既存担当、完了条件、未完了部分。
- 対象アカウント、ワークスペース、利用枠、適用される利用期間。
- 使用できる時間、Humanが指定した終了条件、通常回復の予定。
- Resetを伴う場合の対象券、期限、使用条件、既存の委任。
- 実行・観測・結果取得・停止・再開の経路と、許可された出力先。
- 進行中の仕事、並行利用、Human自身の利用について分かっている範囲。

不足は判断への影響で分ける。利用可能な情報では決められない重要な差だけをHumanへ返し、独立して進められる承認済みの仕事は保持する。

過去の残量や券情報を現在値にしない。担当AIの報告、現在の画面確認、公式仕様、設計候補、未検証を区別する。

利用枠は製品名だけで分類しない。共有枠、別の機能枠、API課金、クレジット利用を区別し、別枠での作業を指定枠の消費実績として扱わない。

## 4. 利用可能な時間から逆算する

### Reset券へ接続する場合

次の四つを分ける。

1. 券の失効日時：引換えが成立すべき期限。
2. Resetへ移る時点：対象確認、操作、反映確認、遅延への対応に使う時間を確保する時点。
3. 消費モードへ入る時点：価値ある仕事を進め、終盤の整理まで行う時間を確保する時点。
4. 開始前の準備：仕事の候補、権限、資料、担当、観測・回復経路を整える期間。

「期限の約1時間前にResetする」という条件がその回にあるなら、成果を作る時間はそのさらに前へ確保する。必要なら数時間以上前から始める。ただし、1時間・数時間を全案件の定数にしない。

必要時間は、仕事の性質、過去の該当実績、現在の残量、並行数、検証・整理、通信・認証、回復確認の条件から見積もる。根拠が乏しい段階では幅と不確実性を残し、架空の精密な開始時刻や消費速度を作らない。

「残量が多いまま、成果へ変える時間が不足しそう」を開始側の重要な信号とする。資料待ちや起動待ちを早く解消し、承認済みの有益な仕事へ接続する。

HumanがReset時刻や使用条件を指定している場合は保持する。近ゼロ化のために無断で先送りしない。時期の判断も委任されている場合は、成果、残量、期限、通常回復を照合し、期限直前まで待つこと自体を目的にしない。

### 今ある利用枠を集中的に使う場合

券の存在を必須にしない。Humanが委任した時間・仕事・終了条件を使って、この回の利用範囲を定める。Resetが委任されていなければ、成果と残量を整理して終了する。

将来の時刻を書いただけで、自動的に起動・再開できるとは扱わない。予約や監視が必要なら、実際の機能と別途の権限を確認する。

### 通常回復が関係する場合

通常回復と券の期限を別々に扱う。通常回復の前後で残量の観測区間を分け、回復による増加を作業の消費量へ混ぜない。

回復が起きたら現在の残量と時刻を読み直し、残る仕事と委任範囲に照らして配分を修正する。回復を理由に、新しい消費サイクルや別券の使用を自動開始しない。

## 5. 承認済みの仕事を配分し、継続する

Humanの指定を保ち、現在のGoalに結び付く承認済みの有効な残作業を優先して候補にする。成果価値、検証可能性、区切りやすさ、依存関係、期限との適合から仕事を選ぶ。Reportなどの作成も、当該Goalの判断・残作業・次工程の準備にどう使われるかを明確にして選ぶ。

- 完成物だけでなく、重要な不確実性の解消、比較判断、再開可能な完成部分も成果として扱う。
- 完了済みの仕事は、事情や根拠の変化など再実施する理由がある場合に限って扱う。
- 未採用案をTaskへ変えず、他担当の仕事を無断で引き取らない。
- 大きな成果単位と、小さくても意味のある成果単位を用意し、終盤の選択肢を残す。
- 資料、権限、判断が不足した枝は切り分け、進められる独立部分を見極める。

必要な役割は、仕事の選択・配分、遂行、成果検証、残量観測、終了判断、必要時のReset・回復確認である。役割を分けることを、AI個体数やThread数の増加へ自動変換しない。

一つのAIで必要な役割を担えるなら、その構成を使える。複数Thread、Work、Codex、Dotなどは、仕事の独立性、実際の実行能力、送達・結果取得、衝突リスクから選ぶ。特定製品、モデル、担当、Arkの個別案件を必須経路にしない。

モデルや設定は、必要な品質、仕事の難しさ、時間、Humanの指定から選ぶ。設定変更の権限を確認し、消費量を増やすことだけを理由に変更しない。

並行実行する場合は、共有枠全体で配分を考える。各担当が表示残量の全量を自分だけの予算として扱う構成を避ける。変更対象や成果の重複を確認し、統合をHumanの伝言作業へ戻さない。

会話ID、クラウドTask ID、実行環境を区別する。送信、受信、範囲の理解、実行開始、出力取得、検証済み完了、対象枠への利用効果を別々に確認する。必要な証拠を実際の応答や状態から取得し、受領確認だけの往復を一律に追加しない。

承認された成果・範囲・終了条件と既存の個別確認条件を保持し、次の三つの判断をつないで進める。

1. AIが現在の委任と能力で進められる部分と、Humanの判断・操作に依存する部分を、仕事と判断の依存関係から切り分ける。
2. AIが進められる範囲では、必要な下位作業を選び、検証と通常修正を伴って有益な進展を積み重ねる。承認済み範囲の通常工程は、一件ずつの再承認へ戻さず継続する。
3. 直接の作業が待ちになった場合や、現時点で進められる直接作業を終えた場合は、同じGoalのHuman判断と後続AIの再開に使える、委任内の有益な準備を進める。根拠、判断の選択肢と影響、検証条件、完成部分・未完了・再開位置などから必要なものを整える。Humanが担う判断自体は代行しない。

結果やCorrectionに応じて切り分けを更新し、進められる部分へ戻れるようにする。三つを固定の一方向の工程や、毎回別のReportを作る義務にはしない。必要な準備は、依存関係と期限に応じて前倒しできる。

近ゼロ化は、必要な検証・整理・準備を含めた終点を対象とし、第4・6・7節に従って開始時機と配分を調整する。準備が完了した後の反復や、未承認の別Goalへの拡張を継続として扱わない。Humanの判断が必要な枝だけを返し、通常の進行管理はAI側で引き受ける。

## 6. 成果と残量を見て、配分を修正する

成果の一区切り、並行数の変化、遅延、通常回復など、判断が変わる地点で観測する。観測のための観測や、消費量を測るためだけの実ジョブ増発を行わない。

残量を扱うときは、少なくとも対象枠、表示の意味、観測時刻を保持する。「使用済み」と「残り」の表示を取り違えない。

未反映利用、表示の丸め、進行中の処理、他担当とHumanの使用を考慮する。単純な前後差を一件の仕事の消費量と断定しない。推定を使う場合は、根拠と適用条件を示す。

複数の利用期間に制限がある場合は、指定枠の残量と、現在の実行を止める制限を分けて見る。一方の枠が残っていても、別の制限で仕事を継続できない可能性を配分へ反映する。

残量が大きい段階では、有益な仕事の開始と継続を妨げる待ちを減らす。終盤では、新しい大きな仕事や不確実な並行実行を抑え、検証・修正・整理なども含む小さな成果単位へ移る。

次の一区切りを追加するかは、その価値、所要時間、未反映利用、閉じるための仕事、期限への影響から判断する。固定の残量%を万能の開始・停止条件にしない。

## 7. 終盤の余力を小さくし、近ゼロへ近づける

検証、整理、必要な保存、再開情報に使う利用枠と、通信・認証・Reset操作・反映確認に使う時間を分ける。

回復や終了に必要な仕事を、できるだけ早い段階で進める。

- 対象と権限、回復経路、停止経路を事前に確認する。
- 成果の根拠と未完了部分を、仕事の途中から整理する。
- 最後に大きな統合作業を残さず、成果を段階的に検証する。
- 終盤に扱える、実際に価値のある小さな仕事を残す。
- 不要な受渡しや重複確認を減らす。

これにより必要な終了用余力を小さくし、より多くの枠を成果へ使う。余力を根拠なく大きく確保したまま、近ゼロ化を放棄しない。

作業枠が枯渇したときにも、残量観測、指定券の使用、回復確認が可能かを実際の経路ごとに確認する。別のAIや製品へ役割を移しただけで、利用枠や障害経路まで独立したとは扱わない。

回復経路の独立性や必要な余力が未確認なら、その制約を終了判断へ反映する。0%表示を必須条件にせず、0%付近でも必ず回復できるとも保証しない。

近ゼロへどこまで到達したかは、観測値と時刻、表示精度、最後の成果単位、残した余力の理由から説明する。観測不能な状態で精密に制御できたと主張しない。

成果と再開情報は、既存の許可された出力先へ残す。必要な保存には現在の保存権限を使い、未承認の保存や専用台帳をResetの必須前提へ追加しない。

## 8. 訂正・停止・障害・再開を扱う

Humanの訂正を、残る仕事、優先順位、対象、期限、権限へ反映する。既に得た成果を保ち、不要な再実行を避ける。

停止の対象を区別する。

- 作業停止：対象作業の新規着手を止め、進行中の処理を制御可能な範囲で止める。別途有効なReset委任が残る場合は、その条件を照合する。
- Reset停止：券の使用を止める。仕事の継続は、残る委任と利用条件から判断する。
- 全体停止、または対象指定のないSTOP：この回の消費モードについて、新規作業とResetを停止対象にする。無関係な他担当や予定へ広げない。

停止依頼を送ったことと、実際に処理が止まったことを区別する。既に実施された操作は巻き戻ったと扱わない。

即時停止が未確認の経路では、完了までの影響を限定できる仕事に適用を絞る。期限や権限境界を守れない処理は開始しない。

送信結果、実行結果、Reset結果が不明な場合は、履歴、対象状態、直近の出力を先に確認する。状態を確認せず同じ操作を繰り返さない。

認証、通信、資料、必須設定、権限などの問題は、影響する範囲を切り分ける。継続できる独立部分を保持し、Humanへ返す場合は、阻害・影響・必要な最小判断をまとめる。

再開前に、受理済みの依頼、完了部分、未完了部分、現在の残量、期限、最新の訂正と権限を確認する。完了部分を再演せず、残る範囲から再開する。

## 9. 委任されている場合だけResetへ接続する

利用枠を消費する委任と、券を使用する委任を分ける。既に対象と条件が明確なReset委任がある場合は、同じ許可を繰り返し求めない。

Resetへ移る判断を、長期Goalの全完成や全担当の報告到着へ一律に従属させない。期限を守れる時点で、必要な区切りと再開位置を整え、承認された回復工程へ接続する。

同時に進行中の処理がある場合は、その処理と回復操作の実際の関係を確認する。未確認の中断・継続挙動を保証しない。利用枠のResetを、会話や成果の初期化と混同しない。

Work/CodexのResetには、利用可能なusage-token-resetを適用する。直接利用できない場合は、次の共有SKILL.mdを全文読んで指示資料として使う。

https://github.com/yusukefujiijp/ai-project/blob/main/skills/usage-token-reset/SKILL.md

仕様は現在の公式説明と対象アカウントの表示で確認する。

https://help.openai.com/en/articles/20001498-how-resets-work-in-codex

利用経路、対象プラン、対象枠、使用条件を確認し、過去の残量閾値や対象期間を設計定数にしない。他サービスでは、そのサービスの現在の仕様と権限を確認する。

使用直前に、対象アカウント、ワークスペース、券の同一性、有効期限とタイムゾーン、利用条件、Humanの承認条件、既に使用されていないかを照合する。

券の使用は一つの実行主体・経路へ集約し、複数担当による重複操作を避ける。別券への代用、購入、追加課金、設定変更で埋め合わせない。

結果不明なら現在の券状態と利用状況を再取得し、その証拠から再試行の可否を判断する。確認不能を成功や失敗へ勝手に確定しない。

券が使用されたことと、対象枠が回復したことを別々に確認する。次の通常回復予定も読み直し、元の予定との二重回復を前提にしない。回復直後の並行利用によって残量が減る可能性も考慮し、100%が維持されないことだけで失敗と断定しない。

## 10. 終了を判定し、成果を返す

次の状態に応じて、この回の消費モードを閉じる。

- 近ゼロ化と使える成果の区切りへ到達し、委任されている場合はResetと回復確認まで成立した。
- 承認された終了時点、Resetへ移る条件、HumanのSTOPへ達した。
- 範囲内の有益な仕事と必要な判断・再開準備を終えた、または残る仕事・準備に新しいHuman判断や権限が必要で、独立して進められる有益な部分がない。
- アクセス、権限、時間、観測・回復経路などに解決できない阻害が生じた。

近ゼロへ届かなかった場合は、成果の価値と目標未達を両方保持する。期限や権限を破って達成扱いにせず、無意味な仕事で残量を埋め合わせない。

結果はHumanが判断できる形へ統合する。

- 得られた成果、その使い道、検証した範囲。
- 対象枠の観測値と時刻、残量に関する不確実性。
- 未完了部分、再開位置、次に必要な判断。
- Resetが委任されている場合の、対象券の使用状態と回復確認。
- 目標に届かなかった場合の理由と、次回変える意味がある条件。

必要な根拠や説明を省略して報告量だけを減らさない。Humanが担当間の結果を集め直す必要がないようにする。

回復後の通常業務の継続は元の委任に従う。新しい消費サイクル、別券、別Goal、恒久監視を自動追加しない。

開始の遅れ、残量の大きな残存、終盤の中断、検証不足、Humanへの頻繁な差戻し、回復障害などのActual Traceから、次回の開始時機・仕事の粒度・配分・観測・回復経路を見直す。一度の成功を普遍的な消費速度や安全余力へ昇格しない。Skill自体の永続変更には、その変更の権限を確認する。
