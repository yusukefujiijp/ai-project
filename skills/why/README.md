## 1. 何のためのSkillか

日常・現実世界の状態や選択について、なぜそうなったのか、どのような事情で選ばれたのか、何が現在の形につながったのかを、根拠から理解するためのSkillである。

生活上の選択や習慣、道具の使い方、仕事の手順、制度などを主な対象とする。コードも対象にできるが、コード向けの手順へ生活例だけを付け足す構成にはしない。

目指す成果は、Humanが理由と経緯を理解し、訂正でき、必要に応じて現在の判断へ使える説明である。

例えば、次のような相談を想定する。

- このやり方を選んだ理由を思い出し、理解したい。
- この出来事が起きた理由として、今の情報から何が言えるか知りたい。
- 当時の制約が変わった今も、同じ方法を続ける意味があるか考えたい。
- 複数の説明が食い違っているので、何が違うのか整理したい。
- 新しい報告や訂正を受け、これまでの理由付けを見直したい。

理由を知ること自体が目的なら、その理解と重要な限界を返して完了できる。比較や推奨が求められている場合は、その成果まで扱う。

制作過程にも学びの目的がある。理由の種類、根拠、調査の深さ、説明の終え方を具体化することを通じて、HumanとAIが理由を理解する方法を学ぶ。この制作上の学びと、完成後のSkillの有効性が実証されたことは分ける。

## 2. 自然な入力と、扱う問いの違い

Humanが最初から理由の種類や必要な資料を分類することを前提にしない。AIは現在の発言と継続文脈から、今回必要な成果を捉える。

「なぜ」という語があっても、経験や気持ちの共有として受け取ることが適切な場合がある。同じ発言が継続中の調査へ届いたなら、理解を更新する材料にもなる。

単なる経験共有、修辞的な問い、本Skillへの言及だけで調査を開始しない。対象を作るためだけに、新しい原因調査や改善Taskを追加しない。

### 理由の種類

| 問いの例 | 主に理解すること |
|---|---|
| なぜこの出来事が起きたのか | 原因候補、成立条件、観測から言える範囲 |
| なぜこの方法を選んだのか | 当時の理由、制約、選択肢、経緯 |
| なぜこれを大切にしているのか | 本人が表明した意味・願い・目的 |
| なぜ今も続いているのか | 継続を支える事情や条件 |
| 今後も続ける意味があるか | 現在の目的に照らした利点・負担・代替 |

この表は入力フォームではない。複数の問いを含む相談も扱い、必要な違いをAIが見極める。

目的を持たない現象に意図を与えたり、本人の行動だけから心中を断定したりしない。本人の意味や評価を尊重することと、外部事実や因果を確定することも分ける。

### 時間の違い

選択や習慣では、次の三つが一致するとは限らない。

- 当時、その方法を選んだ理由。
- 現在まで、その方法が続いている事情。
- 今後も、その方法を続ける妥当性。

当初の理由が分かっても、現在の条件が変わっている場合がある。当初の理由が分からなくても、現在の比較ができる場合がある。

過去の経緯を現在の利点で補作せず、過去の理由が不明であることだけを理由に、現在可能な比較まで止めない。

## 3. Howとの関係

[Howの共有原本](https://github.com/yusukefujiijp/ai-project/blob/main/skills/how/SKILL.md)
は、対象の現在の働き・条件・つながりを理解することへ重点を置く。Whyは、理由・背景・経緯へ重点を置く。

例えば、仕事の確認手順については次の違いがある。

| 問い | 中心になる理解 |
|---|---|
| 二人の確認は、何をどの順序で受け渡しているか | 現在の働き・流れ・条件 |
| なぜ二人で確認する方式を選んだか | 採用理由・当時の制約・経緯 |
| 方法を変えると何が失われるか | 働きと理由を組み合わせた比較 |

Howにも理由の説明は含まれ、Whyでも仕組みを理解する必要がある。能力の境界を排他的に区切らず、Humanに厳密な入口選択を要求しない。

Howを先に実行してからWhyを使う順序は必須ではない。既知の理解を再利用し、今回の問いに必要な部分だけを補う。

独立したWhyを置く価値として期待するのは、理由を知りたい時に、現在の形からの推測だけで終わらず、理由を示す記録や条件へ接続しやすくなることである。

この追加効果は未確認である。利用の結果、重複や誤起動、使い分けの負担が利益を上回るなら、独立構成の維持だけでなく、統合・縮小・入口の修正も検討する。

## 4. 四つの設計事例

以下は、判断の違いを説明するための事例である。

事例Aは、この制作に先行する実際の依頼と保存資料を材料にしている。事例B〜Dは架空の場面である。いずれも、新しいWhyを実行して得た検証結果ではない。

### 4.1 事例A：明示された理由を説明する

問い：
「なぜHowの共有原本URLを確認してから、利用Queryを完成させるのか。」

材料：
- この制作に先行するHowの保存依頼。
- [Howの保存済みREADME・固定版](https://github.com/yusukefujiijp/ai-project/blob/7ac98b5f6d86157e8a1990c4ebe40f689a386c1f/skills/how/README.md)。

保存依頼では、原本の実在・本文・URLを確認した後に利用Queryを完成させること、URLの後付けや本文の組立をHumanへ戻さないことが指定された。固定版READMEの第7節には、その利用入口と確認範囲が記載されている。

この材料から説明できるのは、依頼上の目的と、それに対応する文書構成である。受け手が実在する原本へ到達でき、Humanが後からリンクや本文を組み立てなくて済むようにする、という関係を示せる。

この説明から、全環境での登録、自動発動、受け手の実理解、実生活への効果まで確認済みとはしない。

また、前回の保存回数や細かな工程を、将来すべての制作に必要な順序へ一般化しない。再利用するのは、確認済みの原本を案内し、Humanへ組立を返さないという要件である。

元の保存依頼と、READMEに記録された内容は、それぞれの所在と範囲を保持する。READMEを、元会話の全発言が収録された資料として扱わない。資料内の過去の保存承認も、現在の操作権限には移さない。

### 4.2 事例B：過去の理由が不明でも、現在の比較は進める

仮の相談：
「印刷資料を二人で確認するようになった理由は分からない。今も必要かを考えたい。」

AIは、過去の採用理由と現在の評価を分ける。

過去の理由が利用可能な記録から見つからなければ、その点は不明として残す。一方、現在の二人が何を確認しているか、どの誤りを見つけているか、時間や負担、見逃しの影響などは、比較に必要な範囲で調べられる。

- 異なる種類の誤りを補完しているなら、二人確認を維持する理由がある。
- 同じ箇所を形式的に重ねているだけなら、役割分担や確認方法を見直す候補がある。

どちらに当たるか未確認なら、条件別の結論として返す。過去の理由を推測で埋めず、導入理由が見つかるまで現在の比較を一律に止めない。

この比較から、実際の業務手順を変更する権限は生じない。

### 4.3 事例C：根拠が食い違う場合

仮の資料：
- 変更メモ：「共有表はバックアップのために複製する。」
- 同時期の議事録：「複製はバックアップ目的ではなく、他部署への提出用である。」

AIは、同じ表、複製工程、時点、用語、立場について述べているかを確かめる。別工程を指しているなら、見かけ上の矛盾かもしれない。複数の目的が重なっている可能性もある。

同じ対象について食い違いが残る場合は、両方の根拠と影響を示し、単一の採用理由は確定できないと返す。新しい資料、詳しい資料、説明しやすい物語というだけで、一方を自動的に優先しない。

複製ファイルが存在するという事実だけでは、採用目的は確定しない。

### 4.4 事例D：Correctionが説明と比較を変える場合

仮の経過：
AIが「当時は自動送信ができなかったため、手動送信になった可能性」を示した。

Humanの訂正：
「当時から自動送信はできた。送信前に内容を確認したかった。」

AIは、技術的制約の仮説を修正し、本人が表明した確認目的を反映する。現在の比較も、単純な手動・自動の二択から、送信前の確認をどこで成立させるかという問いへ更新する。

送信前に承認できる自動処理が現在利用可能なら、確認目的を保てるか検討できる。利用できないなら、その制約を残す。

目的を保持することと、同じ手段を保持することを分ける。訂正を語句の置換で終えず、依存する比較や推奨まで更新する。

この訂正だけで、現在の機能の有無や代替方法の効果まで確認済みにはしない。

原典から、対象の現在の形だけで説明を終えず、理由を示す記録と条件へ戻り、根拠の確かさに応じて説明する方法を、Arkへ適応できる核として捉えた。

現在合理的に説明できることと、実際にその理由で形成されたことを分ける点が、特に重要だと解釈した。

これは原典の構成を踏まえたAIの解釈である。原作者が日常生活全般への展開を意図したと断定するものではない。

### 5.3 Humanの方向指定とArkへの適応案

YusukeJPは、日常・現実世界を主軸とし、理由・条件・経緯を根拠から理解し、必要に応じて現在の妥当性を考えられるSkillの設計を求めた。

また、Whyの制作にHowを使う案を提示した。作成側AIはHowの本文を指示資料として用い、pstackのWhyの働き・条件・つながりを調査し、設計要件へつないだ。

この制作上の適用は、Howなしの場合との比較実験や、Howの一般的な有効性の証明ではない。

Arkへの適応案では、次を具体化した。

- 自然な入力と継続文脈から今回の成果を判断する。
- 原因、目的、本人が表明した理由、制約、現在の評価を必要に応じて分ける。
- 当時の採用理由、現在の継続事情、今後の妥当性を区別する。
- 理由が不明でも、独立して可能な現在の比較は進める。
- Correctionを、依存する説明・比較・推奨へ反映する。
- 理由の理解だけで完了できる場合と、比較・提案まで答える場合を保持する。

原典にあるモデル指定、Agent構成、固定の情報源カテゴリや出力構成は、そのまま必須条件へ移していない。

これらの適応を含む本文候補v0.1は、2026-11-06にHumanが採用した。本文の採用と、実際の挙動・効果の確認は別である。

## 6. 利用入口

### 6.1 確認済みの共有原本から使う

[Whyの共有SKILL.md](https://github.com/yusukefujiijp/ai-project/blob/main/skills/why/SKILL.md)
を、2026-11-06（Asia/Tokyo）に共有保存後のmainから再取得し、実在・全文・URLを確認した。

$whyは利用を求める会話上の表記である。使用環境で対応するArk版Whyを直接利用できれば、その入口を使う。直接利用できない場合は、共有SKILL.mdを全文読んで指示資料として適用する。下のQueryは両方の経路を一つの本文に含む。

共有原本の存在は、登録、製品固有の呼出し構文、自動発動、受け手の理解、全環境での互換性を保証しない。同名の別Skillとの同一性も区別する。

通常の利用に、このREADME、pstack原典、How、全形成史の毎回の読込を追加しない。適用される必須読解条件と、取得・表示切れの回収は保持する。

### 6.2 コピー用の利用Query

理由を理解したい対象があるThreadで、そのまま使える依頼文として整えた。対象はそのThreadの直近の依頼と継続文脈から受け取り、対象がまだなければ受け手が必要な不足だけを確認する。HumanがURLや本文を後から組み立てる必要はない。

この利用Queryは、読み取り・調査と会話内の説明・比較・提案を委任する入口である。実行を求める別の依頼とは、対象と権限を分ける。本文を掲載したことやコピーしたことだけで、調査・実行の開始や受け手への送達を成立させない。

宛先：このQueryをHumanが直接入力するThreadのCurrent AI

```text
【Why：日常・現実世界の理由・条件・経緯を理解する】

- 宛先：このQueryをHumanが直接入力するThreadのCurrent AI

- Goal：
  このThreadで私が理解したいと示した状態・出来事・選択について、理由・条件・経緯を根拠から説明してください。現在の妥当性や比較・推奨を求めている場合は、その成果まで扱ってください。理由の理解自体で完了できる場合も保持してください。

- 対象と入力：
  直近の依頼と継続文脈から今回の対象・時点・必要な成果を捉えてください。既知事項を再入力させず、対象が見当たらない場合や、解釈の違いが結論を変える場合だけ、必要な不足を確認してください。このQuery内の例示や提示自体から、新しい調査対象を作らないでください。

- 利用する判断方法：
  Ark版 $whyを使ってください。対応するSkillを直接利用できない場合は、次の共有SKILL.mdを実際に全文読み、指示資料として適用してください。同名の別Skillと混同しないでください。
  https://github.com/yusukefujiijp/ai-project/blob/main/skills/why/SKILL.md

- 説明と判断：
  今回必要な範囲で、原因、目的、本人が表明した理由、制約、現在の評価を分けてください。当時の採用理由、現在の継続事情、今後の妥当性を混同せず、根拠が支える主張の範囲を守ってください。後付けの合理化、単一原因への押込み、根拠の重複、検索結果の不在からの断定を避け、答えられる部分は十分に説明してください。過去の理由が不明でも現在の比較が可能なら、その比較を返してください。Correctionは依存する説明・比較・推奨へ反映してください。

- 読解：
  同一性と適用文脈を確認できる自身の全文読解は再利用してください。宣言された必須Source・依存・読取順・Identity・Binding・Exact EOFを保持し、取得・表示切れは未読箇所から回収してください。参照リンクすべてを無条件の追加必読にはしないでください。必須Sourceを取得できない場合は該当Failure契約に従い、未確認範囲・影響・最小の回復方法を示してください。通常のUnknownは、その影響を示して検討を続けてください。

- Mode：
  このQueryが委任する範囲は、読み取り・調査と会話内の説明・比較・提案までです。保存、登録・導入、設定・コード変更、購入、外部送信、別Agentの起動、実生活の試行へは進めないでください。

- 完了条件：
  今回求めた説明、または比較・推奨を、根拠、条件、重要な不明点とともに、私が理解・訂正できる形で返してください。全不明点の解消、行動計画の追加、他Skillとの順次実行を独自の終了条件にしないでください。回答の提示を、提案の採用や実行、実際の効果の確認とは扱わないでください。
```

共通条件は、
[Skillを使うコピー用Queryの方針](https://github.com/yusukefujiijp/ai-project/blob/main/AGENTS.md#skill-query-portability)
