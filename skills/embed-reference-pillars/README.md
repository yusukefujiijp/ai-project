# References三本柱の組込み

新しい専門領域・プロジェクト・成果物群の構成へ、feedback・lessons・success-casesを自然に組み込むためのSkill。

その領域で生まれる反応・学び・成功を、元会話を知らないAIにも発見・理解・利用・更新できる形へつなぐ。Humanが構成づくりのたびに、三本柱の意味、読取先、記録先、共有と局所の分担を説明し直す負担を減らす。

このREADMEは用途・呼出しPrompt・形成理由・確認範囲を所有する。組込みの判断方法はSKILL.md、三本の共通契約は共有References、領域の実際の経験はその所有原本が担う。

現在の共通契約は[共有References](https://github.com/yusukefujiijp/ai-project/blob/main/references/README.md)、Skill配布の分担は[Skills Hub](https://github.com/yusukefujiijp/ai-project/blob/main/skills/README.md)を参照する。

## 2. どんな時に使うか

新しい領域の構成、既存領域への三本柱の追加、経験への入口と更新先の整理など、領域の仕事と三本柱を結ぶ必要がある時に使う。

Humanが三本柱を取り入れると指定した場合は、その採用を前提に適切な組込みへ進む。元会話や形成史を毎回説明する必要はない。ただし、組み込む対象領域そのものは現在の依頼や参照資料から特定できる必要がある。

通常の一件保存だけなら、その保存先とsaveの仕事で扱う。一般的なフォルダ作成のすべてに自動適用せず、Repository直下の共有Referencesの再構築も、このSkillの通常の対象にはしない。

| 方法 | 担当すること |
|---|---|
| embed-reference-pillars | 領域の仕事に合う配置・入口・読む場面・所有先・更新経路 |
| save | 実際に残す内容の選択、担当原本への保存、保存後の確認 |
| self-improvement-loop | AIへ渡す成果物と、受け取った結果を次の成果物や作り方へ返す判断 |
| audit-agent-instructions | 指示の責務・誤起動・過剰制約などの点検 |

これらを毎回すべて起動する必要はない。必要な仕事だけを担当方法へ接続する。

## 3. どのような構成を目指すか

共有側は、三本の意味、根拠の扱い、共通形式を所有する。局所側は、その領域の対象、実際の経験、成立条件、読む場面、更新先、成果物との関係を所有する。

次は構成を考える際の対応例であり、確定保存先や必須ファイル一覧ではない。`対象領域`は説明用の表記である。

| 位置の例 | 役割 |
|---|---|
| `対象領域/README.md` | 領域の仕事と、経験を読む場面から局所referencesへ案内する |
| `対象領域/references/README.md` | 三本の対象、読む先、成果物・共有原本との分担を説明する |
| `対象領域/references/feedback/README.md` | この領域で扱う反応、読む場面、本文と共有Feedback契約への接続 |
| `対象領域/references/lessons/README.md` | この領域の条件付き判断、読む場面、本文と共通lesson契約への接続 |
| `対象領域/references/success-cases/README.md` | この領域で選ぶ成功の意味、読む場面、本文と共有case契約への接続 |
| 各三本の本文ファイル | 実際の経験を、採用した共通形式と所有関係に沿って保持する |

小さい領域では案内をまとめられる。成果物群で経験を共有する場合は、そのまとまりへ一組を置ける。既存の構成に十分な役割があれば再利用する。

入口の準備と経験の収録は別である。まだ記録がない場合は、その状態と記録先の方針を説明する。実体のない本文ファイルを存在するリンクとして案内せず、架空の初期記録を作らない。

### 領域の仕事へ具体化する例

仮に、複数の音声学習教材を作る領域を設計する場合を考える。これは説明用の仮例であり、実施・評価・成功の報告ではない。

- feedbackでは、どの教材・版を誰がどんな場面で聴き、何を理解できたか、何を改善したいと述べたかを扱える。
- lessonsでは、聴取条件や教材の目的が違う時に、説明順や区切りをどう判断するかという条件付きの学びを扱える。
- success-casesでは、Humanが特に価値を認めた理解や体験が生じた時、その意味と成立条件を残せる。
- 一教材の誤りはその台本・音声・根拠へ戻す。複数教材で使う学びは局所referencesへ、共通の制作Skillを変える提案はその方法の原本へ接続する。

実際の対象では、その領域の仕事から具体化し直す。この例の分類・表現・構成を固定移植しない。

## 6. 公開・配布時の仕上げと確認範囲

共有原本の初期変更対象はSKILL.md、README.md、Hubの局所改訂である。更新時は最新mainと対象への並行変更を確認し、採用された本文と必要な参照差分を反映する。

保存後は二つのURLから実体を再取得し、対象Skill、本文、参照先、版・commitまたはblob SHAを確認する。初回の公開前表示は、実際の取得確認を根拠に更新した。今後の更新でも、確認状態を実体に合わせ、更新後の本文を再取得する。共有本文へ到達できることと、すべての受け手環境から取得できることは区別する。

登録機構がないAIは、共有本文を読んで指示資料として利用できる。各環境への登録を行う場合は、その時点で利用可能なskill-creator等の契約に従い、共有版と登録版の本文・取得元・版を照合する。

`agents/openai.yaml`などのUI metadataは、登録先で必要な場合に扱う。共有本文を直接読むための必須ファイルにはしない。追加する場合は、このREADMEの標準Promptとの意味・権限の整合を確認する。

構造・参照の確認、共有原本の保存、登録、実際の発動、受け手の理解、実利用効果を別々に記録する。公開・登録・試験を、このREADMEの存在だけで開始しない。

実装後の読解・挙動確認では、新規領域、既存記録のある領域、必要資料の取得不能、通常の一件保存、一般的なフォルダ作成、登録の有無、過去評価と現在Correctionの違いを必要に応じて比較する。領域の仕事から経験を選び、条件と根拠を読み、適切な所有先へ戻せるかを見る。見出しや定型句の一致だけで判定しない。元会話を渡さない確認では、依頼・Skill・必要原資料を受け手へ渡し、期待する結論は渡さない。この計画の記載を試験開始とは扱わない。
