# References三本柱の組込み

対象領域の目的と仕事から、そこで生まれる経験を、次のAIが発見・理解・利用・更新できる構成へ組み込む。元会話の説明や、読取先・記録先の組立を毎回Humanへ戻さず、現在の対象に合う判断を引き受ける。

"references三本柱(Ark Projectの共有参照領域references/直下にあるfeedback・lessons・success-casesを、対象・発言者・背景とともに反応・評価・希望・提案・訂正を保持するfeedback、主に失敗・行き詰まり・訂正・復帰から学び、設計判断も含めて再利用できる条件・根拠付きの学びを保持するlessons、Humanが特に価値を認めた成功の意味・喜び・形成過程・成立条件と根拠を保持するsuccess-casesという相互補完の役割で結び、元の会話を知らない新規AI・他AI・Future AI（Future Dots・Bots・Agents等を含む）が、入口READMEから必要な本文・出典・後続の訂正へ進み、Humanの言葉や評価・確認された事実・AIの解釈・未確認事項を区別しながら、蓄積された経験の意味を再構成して現在の目的と条件に合う判断・改善・再利用へつなげるための知識継承の構造であり、三者を必須の順番・排他的分類・全件三重保存とはせず、専門領域の原本はその所有先に保って参照で結び、保存されたことを理解や効果の保証へ、過去の評価・成功・承認を無条件の一般則や現在の実行許可へ変えずに用いるもの)"

## 1. 対象の仕事と権限を受け取る

現在の依頼、対象領域、期待する成果、既存構成、最新Correction、許可された変更範囲を確認する。既知の情報を再入力させず、通常の配置判断はAIが具体化する。対象が一意に定まらない場合だけ、判断を変える不足を確認する。

Humanが三本柱の採用を指定している場合は、その採用を前提に適切な組込みを考える。必要性の再承認を毎回求めたり、局所referencesを設けること自体を重複として退けたりしない。

次の範囲を区別する。

- このSkill自体の設計・改訂・共有保存。
- 対象領域への三本柱の組込み。
- 各環境へのSkill登録。
- 実際の経験の保存、自動収録、継続運用。

一つの範囲への承認を他へ広げない。Plan-onlyでは調査・比較・構成案・本文草案までとする。対象領域の構成変更が承認されている場合は、その範囲の実装と必要な確認まで進め、同じ許可を取り直さない。

## 2. 必要な原本を読む

現在の依頼と適用契約から読取経路を組み立てる。指定された必須Source・読取順・全文読解・Identity・Binding・Exact EOFを優先する。

Arkでは、[AGENTS](https://github.com/yusukefujiijp/ai-project/blob/main/AGENTS.md)、対象へ適用される局所指示、対象領域の入口READMEと既存の記録案内を確認する。三本柱の共通の意味と所有関係は、次の原本へ戻る。

- [共有References](https://github.com/yusukefujiijp/ai-project/blob/main/references/README.md)：三本の関係、共有と専門の分担。
- [共有Feedback](https://github.com/yusukefujiijp/ai-project/blob/main/references/feedback/README.md)：反応の帰属・読取・行形式・更新。
- [共有Lessons](https://github.com/yusukefujiijp/ai-project/blob/main/references/lessons/README.md)：条件付き判断の利用と、既存形式契約への接続。
- [共有Success Cases](https://github.com/yusukefujiijp/ai-project/blob/main/references/success-cases/README.md)：成功の選択・意味・根拠・共通形式。

初回の組込み設計では共通の意味と局所への適用条件を理解する。形式や更新方法を具体化する際は、各原本が指定する契約範囲まで読む。lessonは共有Lessonsが指定する既存契約の第3〜5節を再利用し、その所在からDots固有のBoot・全件読込・所有範囲・権限を移植しない。

既存記録は今回の判断に関係する本文・出典・後続訂正を選ぶ。更新するファイルの全文・版・全行検査など、保存先が要求する確認は別に満たす。参照リンクを理由に全Repository・全Skill・全経験を読み込まない。

同一性と適用条件を確認できる自身の全文読解は再利用する。取得・表示切れは未読部分を回収する。別AIの読了報告を自身の必須読解へ置き換えない。

必須資料を取得できなければ、未確認の範囲、影響する判断、最小の回復方法を示す。契約を推測して適合済みとせず、独立して可能な意味・構成の仮案は、その限界を明示して進める。取得不能を記録なしと扱わない。

比較が役立つ場合は、[Report References](https://github.com/yusukefujiijp/ai-project/blob/main/artifacts/reports/references/README.md)や[Wiki References](https://github.com/yusukefujiijp/ai-project/blob/main/wiki/references/README.md)を読む。責務分担を参考にし、Reportの保存経路やWikiの人物・Evidence構成を全領域へ固定移植しない。

## 3. 領域の仕事から経験と利用場面を具体化する

その領域が誰の何に役立ち、どんな仕事・成果物・判断を持つかを理解する。そこから、三本それぞれに残る意味と、次に読む場面を具体化する。

- feedback：何への、誰の、どんな背景を持つ反応か。肯定・批判・希望・提案・訂正が混在する場合も意味を保つ。
- lessons：どの条件で、何を判断すると役立つか。失敗・行き詰まり・訂正・復帰を中心に、再利用できる設計判断も扱う。
- success-cases：Humanが何を特に価値ある成功と認めたか。喜び、期待との違い、形成過程、成立条件、根拠を保つ。

実際の経験と説明用の仮例を分ける。Humanの評価が確認できないものを、Human認定の成功として作らない。小さな工夫や設計への評価は、その段階の経験として扱えるが、実利用効果へ昇格させない。

「この領域にはfeedbackがある」という一般説明で終えず、次の仕事で選べる案内にする。たとえば制作前、根拠訂正時、読者から反応が届いた時、条件を変えて再利用する時など、対象の実際の場面から読む先を示す。全領域へ同じ場面一覧を配らない。

三本は必須の通過順でも排他的分類でもない。同じ経験に複数の意味があれば、独立して残す価値を判断し、必要なID・出典で結ぶ。同じ根拠の複数参照を独立した実証として数えない。

## 4. 入口・配置・本文の所有をつなぐ

局所referencesを置く単位は、経験を一緒に使い、更新する仕事のまとまりから選ぶ。専門領域・プロジェクト・成果物群の中に自然な所有先を設け、全階層へ同じ三フォルダを機械的に配らない。

共通にするものは三本の意味、根拠の扱い、共通形式である。局所で所有するものは、その領域の対象、経験、成立条件、読む場面、更新先、成果物への接続である。

新規領域では、対象領域の入口READMEから局所referencesへ進み、三本の役割と必要な本文・共通契約へ辿れる構成を標準案とする。親READMEと三本の子READMEを分けるか、一つのREADMEで案内するかは、説明の重複、記録量、読む場面、保守の明確さから判断する。

次の役割が読み取れるようにする。

- 領域の入口：何の仕事を扱うか、どんな時に経験を読むか。
- 局所referencesの入口：三本の対象、選び方、他の所有原本との分担。
- 三本の案内：領域固有の利用条件、本文の所在、共通形式・更新契約。
- 記録本文：反応、条件付き判断、成功の意味と、それぞれの根拠。
- 成果物・経験原本：対象そのものの内容、事実、詳細な経験、現在状態。

既存のreferencesが文献・原典・同梱資料等を所有している場合は、その意味を確認して共存できる配置を選ぶ。名前を合わせるためだけの移動・改名・混在を行わない。

本文の現行所有先を一つに保ち、必要な複数の入口から参照する。共通schema、保存手順、共有記録の全文を局所へ複製しない。既存のID・形式・出典・未知field・並行変更を保持し、形式の変更や移設が必要なら、その理由・互換性・影響範囲を明らかにする。

共有契約への参照には現行のRepository URLを使い、過去状態が根拠になる場合は確認した固定版へ戻れるようにする。相対参照は実際の配置から解決し、記録のsourcesはその形式契約の基準位置に従う。JSONL内のIDへ自動生成アンカーがあるとは仮定しない。

## 5. 初期構成と、経験の利用・更新を分ける

経験がまだなくても、分かっている領域の目的、三本の役割、読む場面、予定する記録先を説明できる。意味のある入口を準備することと、経験の収録を区別する。

実記録がない時は、その状態を明記する。本文ファイルを初回記録時に作る場合は、予定先を実在リンクとして案内しない。空の保存先まで準備する依頼なら、共通形式の0件表現を使う。例示レコード、仮ID、架空の評価、管理行で初期データを埋めない。

後続AIが経験を使う時は、現在の仕事に関係する記録と後続訂正を選び、本文・出典・成立条件・限界を読む。今回との共通点と違いから、使う部分、調整する部分、使わない部分を判断する。既存の結論を次のAIの解釈の上限にしない。

新しい経験や訂正の戻し先は、変える意味から選ぶ。

- 対象成果物の事実・表現・根拠の訂正：その成果物・根拠の所有原本。
- 領域固有の反応・再利用判断・成功：局所referencesの適切な記録。
- 領域を越える経験や条件付き判断：共有referencesとの分担を確認する。
- 共通の方法そのものの改訂：そのSkill・方法の所有原本へ、理由と根拠を持つ提案または承認済み変更として接続する。

一つのCorrectionが複数へ影響する場合も、それぞれが所有する意味の差分を扱い、全文を同期コピーしない。現在のHuman Correctionを、記録の完了待ちで保留しない。

実際の保存は、現在の権限と[save](https://github.com/yusukefujiijp/ai-project/blob/main/skills/save/SKILL.md)、保存先の契約に接続する。既存記録で十分なら参照またはNO_CHANGEを選べる。構成の採用から自動収録・監視・予定・継続運用を開始しない。

## 6. 判断できる結果を返す

対象の仕事と三本の経験がどうつながり、どこから読み、どこへ更新するかを説明する。配置案だけでなく、所有関係、既存原本との接続、初期状態、必要な差分と理由を示す。構成・説明量は対象に合わせる。

元会話を知らない読み手が、次を辿れるか執筆上確認する。

- 現在の仕事から、関係する経験を発見できる。
- 本文から対象・発言者・根拠・成立条件・後続訂正へ戻れる。
- Humanの言葉・評価、確認した事実、AIの解釈、未確認を区別できる。
- 成果物の修正、局所的な学び、共通方法の改訂で戻し先を選べる。
- 存在する入口と予定先、構成の準備と実記録、現在の実行権限を区別できる。

これは設計・執筆上の確認であり、別AIによる実理解や実利用の証明ではない。試験や別AIへの送信は、その操作の権限と範囲に従う。

Plan-onlyでは設計提示で止める。承認済みの適用では、変更した入口・参照・記録に必要な確認と保存先の再取得を行う。文書整合、保存、登録、受け手の理解、実利用効果を分けて報告する。

ArkのRootは主イェシュア・ハマシア御自身、中央軸はTeshuvah。HumanのMeaning・Correction・STOP・Final Sealと適用Guardを保持し、AI・Skill・ReferencesをKeliとして扱う。
