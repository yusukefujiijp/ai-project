# Ark Markdown Writer

## 目的と役割を定める

ArkのMarkdownの主読者をCurrent AI・他AI・Future AIとして設計する。元の会話や作成AIの記憶がなくても、重要な意味を復元し、現在の協働へ使える文書にする。Humanにも読める形を保ち、毎回の精読やAI間の伝言をHumanの担当にしない。現在の明示的な読者・成果物指定があれば、それを優先する。

Current Requestから対象・文書の役割・変更範囲・実行権限を解決する。作成、改訂、計画、相談を区別し、Plan-onlyでは書き込まない。既知の目的を再質問せず、通常の構成判断を引き受ける。文書への言及だけで新規Artifactや既存群の一括改訂を始めない。

対象のCurrent Runtime、Repository指示、近接するガイドを必要な範囲で確認する。指定された全文読解・Identity・Binding・Exact EOFを守り、欠落や不一致は該当契約で扱う。確認済みの読解はMaterialな変化がなければ再利用し、参照リンクを無条件の全読込リストにしない。

## 共通の入口から、必要な違いを引き受ける

Humanに用途別の注意書きや多数のSkillを選ばせず、AI側で今回の役割を判断する。

- 経験・成功事例では、出来事、Humanの評価、重要なCorrection、成立条件と根拠を残す。過去の行動や承認を現在の命令へ変えない。
- 方法・Promptでは、目的、判断基準、適用条件を明確にする。由来の成功体験と、方法の有効性に関する解釈を分ける。
- Handoff・Runtimeでは、適用される移行Skillや共通契約を使う。本Skillで再構成条件・完了判定・必要Artifactを独自に置換しない。移行文書の改善と実際の移行は分ける。
- 入口・ガイドでは、何を選び、どこを読めばよいかを示す。リンク先が所有する本文を複製しない。

複数の役割が同居する場合は、それぞれの責務と権限が読者に分かるようにする。一つの入口は、内部の状況差や権限差を消す意味ではない。Skill自体の作成・導入には環境のskill-creator手順を併用する。

## 意味と根拠を渡す

Humanの問題理解、訂正、採用理由、成功の喜び、形成順序を、今回の理解に効く範囲で残す。Rootは主イェシュア・ハマシア御自身、中央軸はTeshuvah、Human Foreground Oneは主の完全勝利（祈り・イメージVision・行動）。HumanのMeaning・Correction・STOP・Final Sealと適用Guardを保持し、AI・Skill・文書をKeliとして扱う。Humanの信仰的意味とAIによる断定を分ける。

Confirmedは誰の観測・報告・確認かを示し、AIの解釈はCandidate、根拠不足はUnknownとして扱う。Historicalは確かさとは別に区別する。記録日と出来事の日、保存状態と現在のReality、計画と実行、保存と実利用を混ぜない。同じ経験を引用する複数文書を独立した実証として数えない。

重要な主張から、確認した資料・節・版へ戻れるようにする。版によって意味が変わる場合は固定commitやSHAを使い、存在しない日時・会話URL・Sourceを作らない。逐語引用と編集要約を区別する。通常のUnknownの全解消を経験保存の条件にしない。

過去AIの結論をFuture AIの解釈の上限にしない。当時の経験とHumanの意味を辿れる形で保ち、新しい関係や代替解釈を検討できる余地を残す。

## 小さく記録し、必要な深さで読めるようにする

success-casesでは「一つの独立して役立つ成功」を一件の候補にする。小さな工夫や部分的成功も扱い、大きな完成や一般化の証明を条件にしない。「何が変わったか、なぜ有益か、根拠、未確認」が伝わる密度を選ぶ。

一件を理解するのに不可欠な条件とCorrectionはまとめる。異なる問いに独立して役立つ成功は分け、関係をリンクで示す。一Thread一件、一文一件、固定文字数にはしない。既存の大きな事例の機械的分割や、同じ経験の重複原本を増やさない。

冒頭で核心と誤読を防ぐ条件を伝え、必要な深さへ進める構造を選ぶ。自然言語、Humanの言葉、比喩も意味を担う情報として使う。AI向けであることを、英語化・Schema化・長文化・極端な短文化の義務へ変えない。章数、表の数、表現、分析方法は目的に合わせる。

## 確認して協働へ返す

別AIの立場で、元会話なしに文書の役割、何が変わったか、根拠と解釈、現在への適用範囲を区別できるか確認する。これは執筆上の確認であり、毎回答の全項目報告や新しいBoot試験ではない。

読解・照合・構造化をAI側で引き受け、Humanへは今回の判断に効く成果と重要な残点を返す。Human Reviewを全文校閲の必須工程にしない。重要な不足は資料で確かめ、Humanにしか分からない点だけを必要時に確認する。

承認済みの保存は、対象と範囲に合う検証・保存先の再取得まで行う。変更理由を残し、既存の経験を黙って塗り替えない。構造検証、保存、導入、他AIの実理解、実生活効果を別々に報告する。

## 発見を取り込み、入口を増やさず育てる

新しい重要点を得たら、どの作成判断が変わるかを見て、共通の核、特定場面の知識、経験の根拠のどこに置くか判断する。繰り返し役立つ判断はこのSkillへ、条件付きの詳細が十分に増えた時だけ明確な読取条件付きのreferenceへ、経験そのものは適切な記録へ置く。

追加だけでなく、重複の統合・Correction・不要になった規則の除去も行う。毎回すべての知識を発動させず、実際の依頼に必要なものを選ぶ。文書種類が増えるたびに別Skillやqueryを作らない。この成長方針自体は将来の変更を自動承認しない。

具体的な分担や粒度の根拠を知る必要がある時だけ、[成功事例の入口](https://github.com/yusukefujiijp/ai-project/blob/main/success-cases/README.md)や[移行入口を統合した事例](https://github.com/yusukefujiijp/ai-project/blob/main/success-cases/one-transition-entry.md)へ進む。通常のMarkdown作成に、事例全件や形成史の再読を課さない。
