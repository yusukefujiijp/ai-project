# chocoZAP Sweet Spot

**実データの正本は [sweet-spots.json](sweet-spots.json)。日付ごとの条件・訂正・Feedbackを一つのJSONで扱う。** 共通する方法と会話の支援は [chocozap-sweet-spot](../skills/chocozap-sweet-spot/SKILL.md) が担う。

## 1. 読み出す

- 日付は `days["YYYY-MM-DD"].visits` から選ぶ。同日の来館を分け、対象の `spots` を読む。これは本人のSweet Spot申告であり、推奨重量や運動完了の認定ではない。
- 日付基準は `Asia/Tokyo`。日跨ぎの同じ来館は開始日の下へまとめ、分かっている観察時刻は個別に残す。「今日／昨日」は報告時点から解決し、古い相対日付を読出日で解釈し直さない。実施日不明の来館だけは任意の `undated` 配列へ置く。判明時はID・出所を保って該当日へ移す。
- `created_at` は記録作成時刻。実施・発言時刻を推定しない。未報告の項目は省略でき、省略や `null` は未確認を表す。未実施・変化なし・ゼロとは扱わない。
- 一覧や比較はJSONから必要時に作る。「前回」はGit更新順ではなく実施日・来館から解決する。機械・使い方・来館・既知の周回を合わせ、同一来館内の変化と来館間の変化を分ける。数値だけで成長・後退や原因を断定しない。

## 2. JSONの最小構造（schema_version: 1）

- 全体：`schema_version`、`timezone`、`days`。各日には `visits` 配列を置く。新しい日付・項目は実際の報告がある時に追加する。
- 来館：`id`、`reporter`、`spots`、`sources`。記録作成の `created_at`・`recorded_by`、本人が日付を確認した `date_source` は分かる場合に添える。来館IDは全体で一意とし、日付変更でも保持する。
- `spots`：各観察の `id`、`machine`、`source` と、報告された `mode`・数値の `kg`。`mode` は片手・片足・縦／横など本人の語を保持する。`round`・感覚等は報告があれば添える。観察IDは来館内で一意とし、順番から時刻や周回を推定しない。
- `sources`：来館内の出所IDをキーに、本人の原文を `text` へ一度だけ保存する。必要なAI側の問いや文脈は `context` で区別する。`source`・`date_source`・`previous_source` はここを参照する。
- `corrections`：任意の配列。`id`、対象観察IDの `target`、変更する `field`、`from`、`to`、訂正の `source`、訂正前の `previous_source` を持つ。IDは来館内で一意。対象の現在値と出所も更新し、履歴へ順に追記する。訂正は新しい運動観察として数えない。
- `feedback`：任意の配列。`source` と、必要なら対象観察・訂正IDの `about` を持つ。感想の原文は出所へ置き、同じ文章を複製しない。

同条件の再確認や二周目・別来館の新報告は、新しい観察IDで追加する。同じ重量でも新しい報告を消さない。参照元がある場合は `based_on: {visit_id, spot_id}` 等で対応を示す。省略可能な項目をHumanの必須入力にせず、未報告の機種・左右・回数等を補わない。追加項目の意味が自明でなければこの案内へ短く説明する。

## 3. 通常の更新

Humanが承認した本Sweet Spot運用の本人報告・訂正・Feedbackを、現在の権限の範囲で継続保存する。同じ範囲の許可を聞き直さず、現在のSTOP・Plan-only・保存しない指定を優先する。設計相談、仮例、AIの推奨、長期メモリを実記録へ転記しない。

1. JSONの最新内容とSHAを取得し、対象日・来館・観察を解決する。確認済みで変更のない本案内は再利用する。通常の数値更新に全体レビューやアーカイブ読込を追加しない。
2. JSONを解析し、対象項目の更新または新観察の追加を行う。他の値・未知の追加項目を保持する。訂正では履歴と対象値を同時に整える。
3. 構文、ID・出所参照、今回の差分を確認する。再試行は出所・対象・保存結果から既反映を判定し、変更がなければ `NO_CHANGE`。新しい同値の申告とは区別する。
4. 現在のSHAを使って保存する。同じファイルへ並行書込みせず、競合時は再取得して整合させる。古い全文で強制上書きしない。
5. 保存先を再取得し、対象日・値・出所・差分を照合して保存完了を伝える。JSONにはEOF文字列を追加せず、構文解析と内容照合で確認する。

取得失敗・未保存はその範囲を明示し、会話で確認できる情報から支援を続ける。日付がないことと取得失敗を区別する。正本の取得失敗から旧資料への書込みや現行値の代用へ切り替えない。

## 4. 履歴と再利用

Git履歴から過去版を参照できる。読むことと、正本へ復元する操作を分ける。日別Markdownやバックアップ用コピーの定期生成は行わない。当面は一つのJSONを使い、容量・読書き時間・競合・比較範囲に問題が現れたら月別等の分割を検討する。
