# Ark Recall Portal

## 1. 何ができるかを、忘れていても入れる入口

"Ark Recall Portal(忘却を前提とし、主にB状態のHumanが過去の文脈や利用できる支援を思い出せない時でも、何ができるかと根拠のある具体例が見える入口から入り、必要な経験・教訓・既存の支援への想起と再接続を助け、現在の問題解決と複数問題同時解決を支えるArk Projectのポータル)"

Humanに、過去の話、品名、Skill機能、検索語を先に思い出してもらわない。用途の曖昧な呼び出しには、できることと実際に読める記録の例を先に示す。分かる場面が既にあるなら、総合案内を挟まずその問いへ答える。「何を思い出したいですか？」だけで入口を閉じない。

主な用途は、場面に関係する過去の反省を取り出すこと、使い道を見て想起の手掛かりを得ること、新しい反省・希望・訂正を受け取り許可された範囲で残すことである。必要時は既存の現在地map等へ接続する。専用Webサイト、全Arkの新しい司令塔、常時監視や自動通知の仕組みではない。

主対象はB状態での利用。A状態での事前整理、B状態の自己診断や申告、分類入力を利用条件にしない。Humanの忘却を人格・信仰の失敗へ変換せず、B状態を理由にAIの検討・説明品質を下げない。

Rootは主イェシュア・ハマシア御自身、中央軸はTeshuvah、Human Foreground Oneは主の完全勝利（祈り・イメージVision・行動）。AI・Portal・Skill・記録はKeliであり、Root・王座・Oracleではない。Humanの意味・Correction・STOP・Final Seal、身体・睡眠・安全等のGuardを保持する。

## 2. 読む入口と責務

- [items.json](items.json)：場面と想起項目。入口の具体例もここから選ぶ。
- [Ark28:01経験原本](../ark-project/ark28/ark28-01/task-records.json)：初版に必要な本人発言・反省・Correctionの選択記録。
- [Task Recordsガイド](../formats/task-records/README.md)：経験原本の意味と更新。構造検査時には同階層のSchemaを使う。
- [共有Skill](../skills/ark-recall-portal/SKILL.md)：呼出しの判断と本入口への接続。
- [検証ケース](tests/recall-cases.json)：検証担当向け。本番の想起情報・本人の経験として検索しない。

共通の判断と保存規約は本書、呼出しの案内はSkill、経験の事実は出典原本が所有する。itemsは「いつ何を思い出すか」を取り出すための出典付きの派生資料であり、第二の経験原本やTask状態台帳ではない。個々の反省追加のたびにSkillを書き換える必要はない。

対象は通常 `yusukefujiijp/ai-project` の `main`。現在の明示指定があればその範囲を優先する。正式に渡されたローカルのRepository資料でも同じ相対配置から読む。古いキャッシュをCurrent Remoteと呼ばない。確認済みで変化のない読解は再利用できるが、訂正・保存状態・版の違いが判断に効く時は現行を確認する。

本書を選択したら先頭からEOFまで読む。既に全文確認した同一内容は再利用してよい。各Sourceに明示された必須読解・Identity・Binding・EOF契約は検索結果の抜粋で代替しない。参照先全件の無条件読込やArk全体の再Bootは要求しない。

## 3. 入力から、今役立つ支援を返す

### 3.1 用途を忘れた／例を見たい

`items.json`の収録範囲・場面・項目を確認し、現在利用できる使い道と記録に基づく具体例を示す。Scene名・例の数・回答の長さは固定しない。大量の項目があるなら意味のあるまとまりにして見せる。「どんな例があった？」には既存例を探し出し、Humanへ記憶の説明を求めない。

具体例はitemsと原本から作り、READMEへ品目一覧を二重管理しない。関連Skillを案内する場合は、実際に利用可能かを確認し、想起データの実例と別の支援機能を混同しない。

### 3.2 場面が分かる

現在の入力、場面の意味、itemsの検索補助語から候補を拾う。補助語の完全一致を必要条件にしない。初版程度の小さな一覧は全項目を確認するのが簡単である。成長後はScene選択・検索等を使い、見落としや読込負担に応じて方法を変える。固定件数閾値や特定検索技術を必須にしない。

「買っておくもの一覧」等では一番似た一件だけで止めず、確認した収録範囲内の該当候補を拾う。拾った項目の条件・除外・状態・訂正を確認し、必要な原本へ戻る。関連する新しいCorrectionがあるなら反映する。古い派生要約が原本と食い違う場合は原本と現在のHumanの意味を優先し、保存の修正は権限のある範囲で行う。

過去の反省から得た候補と、現在の必要性・在庫・実施状況を分ける。一般的な新提案が必要なら、本人の過去の記憶として提示しない。Human向けには、何を思い出したか、何を根拠にしたか、現在への適用に効く条件を分かりやすく返す。内部JSONの全項目表示は要求しない。

### 3.3 現在地が必要

`map-ark-current-position`が利用可能なら、そのSkillで目的・枝・到達点・未接続・Next stepを整理する。Portalは想起の入口、mapはProject上の位置づけを担当する。両者を同一化せず、毎回の同時起動や互いを呼び続ける構成にしない。

別環境でmapが未提供なら、呼び出したと偽らない。現在見える根拠から位置づけを説明し、利用可能な共有Sourceが必要な場合だけ探す。mapの新設・改訂・Main移管はこの連携の自動処理に含めない。

### 3.4 取得できない／根拠がない

「取得を試みたが読めない」「確認した範囲にはない」「会話にはあるが保存未確認」「訂正が競合する」を分ける。全文を読めていない一覧について、該当項目ゼロや完全な網羅を宣言しない。

利用可能な現在の会話だけで助けられる部分は、その根拠の範囲を明示して支援する。過去の記憶を創作せず、判断に必要な一点だけを確認する。取得障害を、Humanへ全履歴を思い出してもらう理由にしない。必須契約不足で停止が必要なら、影響する操作と最小の回復条件を示す。

## 4. 反省を残し、訂正で育てる

### 4.1 入力を受け取る

新しい反省・希望・訂正を自然な発言から拾う。実体験、例示、仮定、設計相談、実行報告を区別する。日付・数量・原因等が不明でも、その不明を保持して意味を残せる。Humanに必須フォームを課さず、引用の反復を新しい出来事に数えない。

今回の初版作成承認は、本Threadの選択記録と二場面の構築を対象とする。将来の入力は、現在適用される記録委任と依頼のScopeに従って保存する。明確な継続委任の範囲内では同じ許可を取り直さないが、設計相談・読出しだけ・Plan-only・STOPを新しい外部書込承認へ変えない。会話での受領と保存確認を分ける。ChatGPT長期メモリをGitHubへ輸出しない。

### 4.2 保存する場合

1. 現在の原本とitemsを読み、同じ経験・同じ訂正が既にないか確認する。
2. [Task Recordsガイド](../formats/task-records/README.md)に従い、経験が報告されたThreadの原本へ発言・所在・意味・訂正を記録する。新しい出来事は現在のThread、以前の出来事への後日訂正は元の原本へ、発言元を明記して追加できる。Thread番号をこの初版のArk28:01へ固定しない。
3. 該当するitemsを作成または更新する。場面・検索補助・想起内容・条件・原本参照を対応させる。新しい種類の反省も受け取り、初期二場面を永久的な上限にしない。
4. JSON構造、IDと参照、出典との意味対応を確認する。保存後に原本とitemsを再取得し、必要な内容が両方に反映されたことを確認する。

原本だけ保存できた時は「原本保存済み・Portalへの反映未完」と区別し、可能なら承認範囲で残りを完了する。itemsだけで完了扱いにしない。競合した他者変更を上書きせず、必須不足・権限・Scopeの差は影響部分を止める。リンク追加のために固定Handoff／RuntimeのBindingを無断で変えない。

### 4.3 一回の状態と、今後の条件

- 「今回は在庫がある」「今回は要らない」：現在の機会だけの適用条件。項目全体を恒久取消ししない。
- 「買った」：その回の実施。今後の候補を自動削除しない。
- 「今後は不要」：今後の想起条件の変更。根拠と訂正履歴を残す。
- 「前の発言が間違い」：原発言へのCorrection。元の意味を黙って消さない。
- 沈黙・未報告：成功、未実行、失敗のいずれにも変換しない。

`active`は想起候補、`withdrawn`は通常の候補から外す状態。どちらもTask完了状態ではない。`episode_overrides`は対象となる機会の説明と出典を持つ一時的適用差分であり、現在の機会と一致する根拠がなければ後日へ持ち越さない。範囲が判断を変えるほど曖昧な時だけ、最小の確認をする。

## 5. itemsの小さな契約

トップレベルの`format / format_version / revision / updated / coverage`は、形式・改訂・収録範囲を示す。`scenes`は場面の名前、`items`は実際の想起項目である。入口の実例はitemsから組み立てる。Source発言日時とupdatedを混同しない。

各項目は次を保持する。

- `id`：安定ID。`scene_ids`：実在するSceneへの接続。
- `label / recall`：想起内容の編集要約。`retrieval_hints`：検索補助であり本人の原文ではない。
- `status`：activeまたはwithdrawn。`conditions`：適用場面と、仮定してはいけない条件。
- `source_refs`：Repositoryルート相対path、record_id、reviewed_revision、node_ids、source_ids。
- `episode_overrides`：一回の機会への差分。追加時には`scope / status / source_refs`を記し、必要なら安定したepisode_idを付ける。
- `corrections`：重要な変更の理由・出典・対象範囲。追加時には`scope / change / source_refs`を持たせる。
- `evidence_note`：原文と編集要約、候補と実行命令の区別。

Sourceのrevisionがreviewed_revisionより進んでいれば関連する差分を確認する。同じrevisionだからHumanの新しい訂正が無効になるわけではない。未対応の重要な形式変更は推測で読まず、その範囲を明示する。形式はこの初版に永久固定せず、変更時に意味と対応関係を残す。

## 6. 形成、確認範囲、次の成長

旧称はArk Recall Hub。2026-09-28にHumanがPortalへの名称・配置変更を報告し、入口を中心に段階的に育てる初版計画の実行を承認した。根拠は[原本](../ark-project/ark28/ark28-01/task-records.json)の`portal-entry-first / portal-name / portal-incremental-growth`。Ark27のMainとArk28:01の補助という役割を変更しない。

初期収録は休日前準備とToken Resetの二場面であり、全Ark履歴ではない。睡眠・仕事を挟む忘却、用途そのものを忘れること、自然な反省の蓄積というHumanの意味を保持する。忘却の一般的な医学理論を実証した文書ではない。

検証は[ケース集](tests/recall-cases.json)へ分離する。構造検査、元会話なしの応答、保存確認、Skill導入、自然な自動選択、Humanの実生活効果は別の証拠である。検証例・期待値・架空入力を本番の想起候補へ混ぜない。

2026-09-28、原本の対応Schema・ID参照・JSON重複キー・入口EOF・Skill形式を検査した。元会話と期待回答を渡さない6つの独立したAI文脈で、計10応答を観測した。用途の入口、場面からの想起、Resetの教訓、一回の見送りと恒久訂正、設計相談、取得不能、現在地説明を区別できた。隔離コピーへの仮想項目の追加後、さらに新しい読み手が既存項目と新項目の両方を復元した。架空の品目は本番items・経験原本に含めていない。これは明示的にSkillを渡したローカル資料での限定確認であり、自然な自動選択・実生活効果・全AI互換性は未観測。保存先の再取得と利用環境への導入は、応答確認とは別に確認する。

実利用では「入口から使い道が分かったか」「必要な経験へ届いたか」「訂正が今の回答へ反映されたか」を自然なFeedbackから読む。Humanへ毎回の採点・全資料校閲・新しいTaskを課さない。入口の表現、項目、共通方法のどこを直すかを分け、追加だけでなく整理・統合・撤回も選べる。

全履歴移植、既存Skill統廃合、専用UI、大規模検索、Schedule、常時監視は初版の自動的な続きではない。呼出し自体を忘れた時の通知まで解決済みとはしない。
