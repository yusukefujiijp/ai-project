# 前日の協働を、翌日へつなぐ日次総括

## 1. 目的と分担

[dot-0000: 初穂](../actors/dot-0000/README.md)が、一日の協働から成果・重要な訂正・判断・未接続を読み、既存原本との照合によって意味のある保存漏れを回収し、Humanへ総括を返す。Humanが毎回 `$save` を思い出す負担を減らし、翌日・別AI・文脈回復後も意味と根拠を取り戻せることが目的である。

[定期Ark Map](../ark-map/README.md)は「今の位置と理由ある次の接続」、本運用は「前日の活動の意味と保存状態の照合」を担う。Mapの予定・表示・限定saveを変更せず、日次総括からMapを再実行しない。両者は同じ成果原本を参照し、既に十分な成果を重複保存しない。新しい常設Inbox、全会話保管庫、全AIの仕事を引き取る担当ではない。

総括の本文、日別の活動記録、成果を所有する原本は役割が違う。同じ本文を全保存先へ複製しない。総括は今日までの意味をHumanへ返し、成果原本は再利用する内容を所有し、recordsは活動の時点と原本への接続を残す。

共通の権限・品質は[AGENTS](../../AGENTS.md)、RootとIdentityは[ARK](../../ARK.md)。保存判断と競合・結果不明の扱いは[$saveスキル](../../skills/save/SKILL.md)、全体の現在地や次の接続が必要なら既存の[Map](../../skills/map-current-position/SKILL.md)・[next-step](../../skills/next-step/SKILL.md)を使う。共通本文をここへ再定義しない。

## 2. 対象日と、遅れて分かったこと

日本時間の日付変更後に一日一回行う。Humanは23:50、23:45、0時過ぎと時刻の柔軟な設計を認め、前日が時間として閉じた後の総括を評価した。具体的な実行時刻・有効状態は製品側の予定を確認する。この文書や過去の実行記録だけから予定を作り直さない。

主対象は、実際の実行時点における前日の **00:00以上、翌00:00未満（Asia/Tokyo）**。日次運用として最初に扱う日は **2026-10-13** とする。これより前の全履歴を初回に棚卸しする承認ではない。ただし、対象活動の意味・既存保存・訂正を照合するため、必要な過去の根拠へ戻ることはできる。

前日の活動総括と、総括を作成する確認時点の残件は時間軸を分ける。昨日始まり今日完了した仕事を現在の未完了へ戻さない。残件の確認では、既知の持越しや現在の活動に関係する以前の案件も必要に応じて辿るが、初回対象日より前の全履歴を棚卸しする範囲拡張にはしない。

日付が閉じたことは、活動の全取得・作業の完了・保存の完了を意味しない。日を跨ぐ仕事は、その日までの到達点と後日の結果を分ける。記録日は[records契約](../../records/README.md)に従い実際の保存時点のJST日付とし、前日のファイルへ黙って埋め戻さない。活動日時、対象日、確認日時、保存日時を区別する。

日を跨ぐ遅延や中断では、単に新しい「昨日」へ対象をずらして旧対象を忘れない。初回対象日以降の確認記録・残点を照合し、抜けた対象日や未確認の資料を次回へ接続する。複数日を扱う場合、古い未確認分を原則として先に見るが、現在のHuman訂正・STOPと重要な現状確認を優先できる。処理できなかった範囲を残したまま「最新日まで全て確認済み」としない。

既に確認した日にも、遅れて公開された成果・重要な訂正・新しい根拠が見つかれば必要な差分を再照合する。全過去日を毎回再監査する義務にはしない。前回の起動時刻、最後の記録日時、単一のカーソルだけを保存済み範囲の証明にしない。

## 3. 読む範囲と、保存できる範囲

総括はArk全体を見渡す目的を持つが、実際に確認できる範囲を明示する。現在のDot対話、取得した公開Ark原本と必要な変更履歴から、活動側と保存済み側を照合する。recordsだけを読むと未記録活動が見えないため、日別記録の不存在を活動なしの証拠にしない。

必要なWork会話等を総括の理解のために読み取れる場合も、取得した本文・時点・担当を区別する。検索snippetや会話名だけで内容・完了を断定せず、未取得の枝を網羅済みにしない。他AIの成果を初穂自身の実行成果へ付け替えない。既存の担当AIが仕事を持っている場合、総括を理由に同じ仕事を並行実行しない。

残件を取り上げる時は、担当、作業状態、次に進む条件を別々に確認する。前回総括は候補を発見する入口として使い、担当原本・元の会話の後続と再照合する。依頼済みを現在実行中へ、最終応答を案件全体の完了へ変換しない。完了・取消・置換・一部完了を成果と残る条件の単位で読み、同じ名前だけで別案件を統合しない。文書の更新日時と、状態を裏付ける出来事・観測の日時を分ける。根拠が食い違う場合は、文書が新しいという理由だけで一方を採用せず、現在の判断へ影響する不一致と必要な確認を示す。

本運用によるGitHub保存対象は、**このDotの現在の会話で提供されたArk協働の内容、および実際に確認した公開Ark原本**から得る成果・訂正・根拠・再開文脈に限る。読み取れた私的Work会話、別会話、ChatGPT長期メモリを転記・バックアップ・同期しない。これらの私的資料の意味を要約し直して公開することも同じ境界に従う。公開原本で独立に確認できる事実は、その公開原本を根拠として扱う。

公開保存に不適切な個人情報や秘密情報は保存しない。新しい公開範囲・第三者への開示が必要な場合は、その対象だけを保留する。私的な根拠・未公開の残点は公開確認記録にも混ぜず、必要ならHumanへの私的な総括で扱う。

## 4. 一回の照合と保存

1. 本書のmetadataからExact EOFまでと、最新Human指定・Correction・Plan-only・STOPを確認する。同一版で読解を継続利用できる場合は再利用する。書込直前にも現在有効な指定を確認する。
2. 今回の対象日・持越し・必要なSourceを復元する。読めた対象と読めなかった対象を区別し、全Repository・全会話・全Skillの無差別読込はしない。
3. 活動の意味を抽出する。成果、重要な訂正、採用判断、失敗から分かった条件、再開に必要な未解決・保留を候補にする。未採用案やAIの仮説はその状態を保持し、成功だけに絞らない。
4. 担当原本・関連記録と照合する。残件は前回の掲載から自動的に持ち越さず、今も残る根拠と次の接続を確認する。「残す価値がある」と「未保存である」を別々に判断し、意味と根拠が既存原本で十分ならNO_CHANGEとする。同義の言い換え・操作の細切れ・総括全文の複製は増やさない。
5. 許可された不足だけを保存する。保存先の全文・revision・形式を確認し、他AIの追記・未知field・順序を保持する。依存する書込を並行しない。保存後はRemoteから再取得して、対象path・意図した差分・保持内容を照合する。
6. 日次照合の結果を、再開に役立つ範囲で既存recordsへ残す。最後に、このDotの会話へ日本語の総括を返す。保存できない場合も、確認できた総括は返す。

現在の承認済み継続保存先は以下に限る。

- `records/YYYY/MM/YYYY-MM-DD.jsonl`：通常の主な保存先。[records契約](../../records/README.md)の一行一活動・保存日・出典・追記・訂正に従う。
- `dots/lessons/lessons.jsonl`：実際に得たDots共通の再利用可能な学びがある場合だけ。[lessons契約](../lessons/README.md)の同一項目更新・schema・競合条件を守る。
- `dots/logs/dot-0000.jsonl`：初穂固有の経緯として独立した価値がある場合だけ。[logs契約](../logs/README.md)の実在するtask_id等を満たす。内部予定IDを公開したり、記録のためだけに架空IDを補ったりしない。

一件を機械的に三重保存しない。本運用専用lessons・全文日報フォルダ・第二の進捗台帳は初版では作らない。Map専門lessonはこの日次運用の保存先には含めず、Map固有の別の有効な委任がある時だけその範囲で扱う。

Topic原本、Board、Rootのreferences、共有Skill、運用原本自身などは、この継続saveの権限外である。別途、内容と具体的保存先について有効な明示承認がある場合だけ進む。本書の編集だけで保存範囲・実行権限を広げない。

## 5. 日次確認記録と回復

日次照合自体を、一つの意味あるAI活動として既存recordsに記録できる。通常の六必須fieldを使い、summaryに「日次総括」「対象日」、実際に照合した範囲、結果と重要な未確認を分かるように書く。sourcesから、照合した版・成果原本・回収した記録へ戻れるようにする。必要な意味は本文に残し、公開不能な内容を識別子へ隠して転記しない。

この行は、その時点の観測証拠であり、全AI活動の網羅証明や現在Task一覧の正本ではない。対象ごとの成果本文を再録せず、追加不要・一部確認・保留などを理由付きで区別する。対象日ごとの確認結果を辿って未確認分を復元し、独立した可変カーソルを追加しない。

一つの実行で複数日の追いつきを扱う場合も、確認した日と残した日が明確ならまとめられる。新しい実質的な照合結果がない同一実行の再試行では、同じ確認行を重ねて追加しない。確認したことを再度確認する記録を無限に積まない。

- 既存原本で十分：対象を明確にNO_CHANGE。日次照合自体の観測結果とは分ける。
- Plan-only・会話内だけ・保存STOP：その対象の保存は意図的保留。保留記録だけを背景保存して禁止を迂回しない。
- 保存権限の対象外：候補の実行・公開へ進めず、必要な条件をHumanへ示す。
- 資料不足：未確認の範囲を示す。「活動なし」「保存不要」へ変換しない。
- 結果不明：同じID・本文・版・履歴を先に照合し、盲目的に再送・新ID生成をしない。

一部の保存が成功してから中断した場合は、Remoteの成功部分を保持し、未確認部分だけを照合して再開する。確認記録がないことだけで全処理未実行とせず、既存成果と操作の結果を確認する。保存と報告の成否も別であり、報告が見えないことだけで再保存・再送しない。

対象日・重要な未確認を回復できなければ、回復できる範囲を明示して総括し、網羅性を装わない。全日程を処理し終えたという架空の完了印を残さない。

## 6. Humanへ返す総括

冒頭で対象日とその日の実際の意味が分かるTitleを置き、執筆者は **執筆: dot-0000: 初穂（役割: Chief）** とする。対象期間と確認時点が違う場合は分かるように示す。具体的な見出し・分量・案数を永久固定せず、次を必要な深さで届ける。

- その日の協働で何が進み、何が変わったか。GitHub保存、会話内の計画、他AIの実行、Human報告を区別する。
- 原本に保存・再取得確認できた意味のある差分とリンク。
- 既存原本で十分だったもの、未確認・保留と理由。無変化を反復で埋めない。
- 盤面から読める現在の意味と、翌日に役立つ接続。新Taskの数を増やすことを目的にしない。

### 残っていることと次の接続

この一節に、確認時点で重要な残件と再開先をまとめる。Humanが並列Threadを巡回して、目的・到達点・担当・未完了を頭の中で再構成する負担を引き受ける。総件数や管理項目を増やすことを成功としない。

最初に、確認できた範囲でHumanの判断・行動が必要かを短く示す。各項目には、何が残るか、確認できた到達点、誰が次を担うか、進む条件、根拠と戻り先を必要な密度で含める。重要な確認時点が共通なら節でまとめ、異なる時点・古い観測・未確認は該当項目で分かるようにする。会話・原本のリンクは実際に確認できたものを使い、取得できないリンクを生成しない。

- Humanの判断・行動が必要なもの、担当AIへの依頼済み、条件待ち、意図的保留、状態未確認を区別する。固定五分類や空の見出しを埋める義務にしない。担当と状態は別軸であり、AI担当の件にもHumanの判断が必要な場合がある。
- 現在の実行を確認できなければ「依頼済み・完了未確認」等とする。取得不足をHuman待ちの宿題へ変換せず、確認できないことだけで完了・継続・失敗を決めない。
- Plan-onlyの検討、採用前の案、意図的保留を保ち、毎日の承認要求や催促に変えない。残件であることは、今すぐ実行すべきことを意味しない。
- 順序は確認できた期限・影響・他の仕事への依存・現在のHumanの焦点から判断する。共通する一つの判断で複数の枝が進むなら関連をまとめるが、対象別の承認条件や担当の違いを消さない。古さ・件数だけで優先度を決めない。
- 完了・取消・置換が確認できた項目は現在の残件から外し、重要な変化なら総括で短く伝える。前回の一覧自体を正本にせず、第二の進捗台帳・独自の番号体系・担当移管を作らない。

確認できなかった重要な範囲がある時は、一覧の限界を簡潔に示す。「確認範囲ではHuman対応なし」と「全活動に残件なし」を区別し、定型の免責を各行で反復しない。件数・分量・内部構成はFeedbackで育てる。私的Work由来の残件は第3節の境界に従い、この私的な総括から公開記録へ自動転記しない。公開できない題名・存在・件数等を記録のために漏らさない。

通常は照合・保存確認を終えた後に一通返し、保存前の候補を保存済みと誤認させない。追いつき分も一通へまとめる。結果が部分的でも、得られた有用な判断と限界を返す。送信結果不明なら既存会話を確認し、盲目的に再送しない。後から重要な訂正が必要になれば、何が変わったかを伝える。

毎回のニュース・天気・Map全文、固定の件数予告、Humanによる日記入力・毎日の採点は要求しない。情報を探し、分類し、照合する負担をAI側で引き受け、必要な説明・洞察は保つ。日付の総括だけで終わらず、必要ならLiving ReviewからNext stepへ接続する。追加行動が不要なら今回完了を選べる。

## 7. 運用上の境界と検証

現在のHumanの計画限定・STOPは背景saveにも適用する。全面停止ならその範囲に従い、無関係な承認済み対象まで一律停止しない。原本または最新のHuman指定を確認できなければ書込を止め、確認できる範囲の読み取り専用総括を返す。

この定期運用から、新しいTask・予定・自動保存トリガ、外部AIへの送信、Reset、共有Skill・権限の改訂、他AIの未完了作業の引取りを開始しない。既存Mapや他の予定を変更しない。予定の停止・再開・修正も、その時のHuman指定と現在の実設定で判断する。

原本保存、予定登録、実際の起動、照合とRemote保存、Humanへの到達、翌日の再開への有用性を別々に確認する。設定確認だけで初回実行や全活動の保存率を検証済みとしない。重要な訂正を取り戻せるか、重複や誤った完了が増えないか、Humanの想起負担が減るかを、実際の出力とFeedbackから見直す。深夜の配信を読むためにHumanが起きて待つ必要はない。

残件整理の導入・改訂では、昨日未完了で今日完了、依頼済みだが稼働不明、意図的保留、共通条件待ち、一部だけ完了、取消・置換、資料間の矛盾、一部資料未取得、私的Workのみの根拠、同じ材料での再試行を必要な範囲で照合する。設計上の確認と実運用の成功を区別する。Humanが元Threadを探し回る時間が減るか、誤った完了・余計な宿題・担当移管・公開が増えないかを実際の出力とFeedbackから見る。毎日の採点入力は要求しない。

初版は既存Skillと契約を活かし、原本一つと入口一つで始める。実際の欠落・重複・競合・読解負担が見えた時に方法を改善する。Humanの「Ark Project Style」は、柔軟な修正と認知負荷軽減を意味し、将来の権限拡張や原本自動改訂の包括承認ではない。
