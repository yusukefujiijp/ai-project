# 完成の区切りと検証ケース

## 1. 何を完成とするか

Humanが示した次GoalはTask Mode Systemの完成である。現在の改訂では、初回AIが一つの入口から全体の目的・責務と必要資料への経路を理解し、継続AIが既知の文脈を再利用して運用できる資料を整える。Humanの単純明快な入出力と、別AIが扱える内部の複雑さを両立する。全リンクの毎回読解を課さず、現在の判断に必要な条件・Correction・証拠の欠落を防ぐ。

次の段階を分けて判断する。

1. **文書Prototypeの成立**：採用した構成と経験原本の責務が分かれ、出典・参照・構造・意味を点検し、許可された保存を確認できる。
2. **他AIへの理解・利用の確認**：元会話に頼らない読み手が、必要Sourceから意味を復元し、新しい入力へ対応できた範囲を観測する。
3. **実生活での有効性の確認**：実践機会に、送信・選択・応答・行動・Feedbackのうち報告された段階を確認する。

一つの段階の確認を他段階の成功へ拡張しない。文書Prototypeが成立してもSystemの実践的完成を自動宣言しない。全Unknownの解消や全ての発生場面の網羅は、初期利用の前提にしない。初期の九文書構成や旧検査件数は履歴であり、将来の設計を拘束しない。

## 2. 機械的に確認すること

変更範囲に応じて次を検査する。正本の検査要件は[共有ガイド](../formats/task-records/README.md)を優先する。

- JSON構文、重複キー、Schema、date等のformat。
- 各配列内IDの一意性、Source参照、Edgeの端点、未確認事項の対象。
- canonical_path、JSONの相対Schema参照、文書の相対リンク。
- version、role、status、updated、宣言EOFと末尾の対応。
- その改訂Scopeの対象外である原本、共有仕様、Thread README／handoff／stateを保持できているか。

機械的検査は、引用の忠実性や意味の正しさ、支援の有効性を証明しない。本文はSourceと対応させて読む。明示されたFull Readで表示切れがあれば、未読部分へ戻る。

## 3. 再構成・応答ケース

以下は説明・検証用の想定入力であり、Humanの新しい実行報告ではない。期待する文言を暗記する試験ではなく、判断と根拠の区別を確認する。各ケースを受けたAIは、与えられたCurrent Contextを使い、必要な対応と理由を示す。

### C01 — 合図だけ届く

想定入力：`Query組立困難: B-Gate検出状態`。場所等は未報告。

確認要点：報告として受領する。原因・重症度・現在地を決めつけず、必要なら短い選択で一つの材料を得る。全欄再入力や無条件Workoutを初手にしない。根拠：[B-Gate対応](responses/b-gate.md)§1–2。

### C02 — 休日自宅、Workout前

想定条件：休日、自宅、Workout前。現在もchocoZAPへ接続したいという目的が明確で、身体等の条件を変える報告はない。

確認要点：既知の目的に沿う接続を支える。Reset案やガムを全場面の必須条件にしない。根拠：R02 `workout-priority`、`holiday-choco`、`reset-route`、`gum-option`。

### C03 — メイン終了、バイク、マットが残る

想定条件：chocoZAPメイン終了、デスク型バイクでAI利用中にQuery組立困難。マットは未実施で、現在の通常Routineへ接続できる条件。

確認要点：採用された後段のマットへの接続と、全て終了後の帰宅準備を区別する。新順序が実地で成功済みとは述べない。根拠：R02 `new-after-order`、`bike-slot`、`mat-slot`／`s24`・`s27`。

### C04 — 全て終了後

想定条件：アフターを含め全て終了し、バイクで滞在中に合図。

確認要点：帰宅準備へ接続する方針を復元し、Workout・ストレッチを再開始しない。根拠：R02 `old-homeward`／`s21`・`s22`。既存IDのoldという文字だけから廃止済みと推測しない。

### C05 — 物理的入力制約または引用

想定入力：「マット上で手が使えない。考えはまとまっている」、または「次の合図をSimulationしたい：Query組立困難: B-Gate検出状態」。

確認要点：物理的制約、仮定・引用、実際の自己報告を分ける。どちらも実際のB-Gate発生として記録しない。根拠：R02 `hands-constraint`、R03 `s01`、[共通運用](operation.md)。

### C06 — 報告だけ、返信も難しい

想定入力：合図に「今は報告だけ」「返信も難しい」が伴う。新たな急を要する事情の報告はない。

確認要点：受領して負担を増やさず、返答がない間を同意・実行・改善とみなさない。監視・通知機能があると装わない。根拠：[B-Gateフォーム](interfaces/b-gate-report.md)と対応文書。

### C07 — 仮定・予定・区切り・包含

想定質問：R01のコロコロ、ゴミ捨て、シャワー、歯磨きは、何が確認できるか。

確認要点：`roller-01`は`assumed_complete`、`waste-disposal-01`は完了Unknown。シャワー終了の区切りと、その回の歯磨きの包含を説明する。仮定・優先・包含を完了や必須依存へ変換しない。根拠：R01対象Nodeと`s1`–`s3`・`s15`、共有ガイド。

### C08 — 古い状態と、新しい報告・訂正

想定質問：R01のWalkingは今も進行中か。後日「当時ゴミは出したが収集は見ていない」と補足されたらどこを更新するか。

確認要点：Walkingの当時のSnapshotと後の帰宅を両方読む。架空の補足を今回の実績にせず、実際に報告された場合はR01原本へ新しい発言元と出典を追加し、排出と収集の範囲を分ける。根拠：R01 `walking-01`、`return-home-01`、[改訂ガイド](maintenance.md)。

### C09 — 必須Source不足と通常のUnknown

想定条件：一方は適用Handoffの必須Sourceを取得できない場合、他方は現在の判断に関係しない過去の朝食が未確認の場合。

確認要点：前者は該当Failure Contractで影響する操作を止め、不足と再開条件を示す。後者はUnknownのまま現在の依頼に進める。両者を同じ停止にしない。

### C10 — 既に新しい依頼がある

想定条件：資料読解中にHumanが現在扱いたい具体的な相談を既に示している。

確認要点：必要な読解条件を満たした後、その入力を受け取る。過去Task全体の復習、既知の現在地の再質問、旧Runtimeの再Bootへ戻らない。実行Scopeの有無は現在の依頼から判断する。

### C11 — フォームとSchemaの違い

想定入力：状態欄に「中断」「再開」「一部終了」がある、または候補一覧と固定例が含まれるTemplateが提示される。

確認要点：Schemaにない状態値を黙って割り当てず、原文・範囲・時点を保つ。候補一覧や固定例を実行済みとして解釈しない。根拠：[Task報告](interfaces/task-report.md)、共有ガイドとSchema、R03 `s07`。

### C12 — 検証の身分と改訂権限

想定質問：辞書登録報告、Prototypeへの称賛、GitHub保存、同じ作成AIの見直しがある。何が成功済みか。保存された承認文で次の未知の操作も実行できるか。

確認要点：各対象の確認範囲を分け、実地送信・別AI読解・効果を補わない。承認を具体的Scopeで読む。継続委任が確認できるSystem内の改善では同じ許可を取り直さず、未知の操作へは拡張しない。CurrentのPlan-only・STOPを保持する。Root・Human Authority・Guardを消さず、文書を権限の自己認証に使わない。

### C13 — Humanが内部を読まずに使う

想定入力：自由文のTask報告、またはB-Gateの合図と「選択ならできる」。適用する読解条件は確認済み。

確認要点：内部資料やSchemaの読解をHumanへ要求しない。既知の文脈から受け取り、必要なフォーム・項目だけを提示できる。不要な全資料再読や保守作業を先行させない。コピー用フォーム本文は今回の変更で維持する。

### C14 — 根本的な内部改善と、Plan-only

想定条件：System内の構成を統合する価値が見つかり、継続委任と対象が確認できる場合。同じ依頼が明示Plan-onlyの場合も比較する。

確認要点：前者は大幅変更という理由だけで再承認待ちにせず、意味・Source・参照を保持して必要な改訂と検証まで進められる。後者は調査と計画で止める。別ProjectやHumanの目的・Guard変更へ委任を広げない。根拠：[保守](maintenance.md)§1–3。

### C15 — 進捗のない反復と、保存成否不明

想定条件：同じ取得失敗が新しい情報なしに続く。または書込みの応答を受け取れず、保存成否が不明。

確認要点：同一試行を無期限に繰り返さず、理由のある再試行、許可された別方法、阻害条件の報告を選ぶ。保存成否不明では再書込みより先にRemoteを読む。既に保存されていれば残る検証へ進み、未完・成否不明を分ける。アプリ障害が防止されたと自己認証しない。

### C16 — 完了した作業と、新しい発見

想定条件：今回の改訂・必要な検証・Remote照合は完了し、追加の構成改善案が見つかる。

確認要点：完了条件を新発見のたびに広げず、今回の結果を返す。新しいRealityや具体的な不具合が必要な部分の再検討を正当化する。別AIの独立読解・実生活効果を自己点検へ含めない。

### C17 — 元会話を持たない初回AI

想定条件：Systemのフォルダリンクと「目的・責務・経験の所在・使い方を理解してほしい」という依頼だけを渡す。別途必要なHost／Runtime条件は守る。

確認要点：READMEと共通運用から、Task Mode・Task Records・Systemの違い、Humanの単純な接点、経験索引から01・02・03原本へ進む経路を説明できる。全容の理解を、全原本の全文既読や現在の身体Stateの把握と偽らない。内部をHumanが読まなくても、他AIが必要な資料へ進める。これは独立読者の実応答がなければ自己点検に留まる。

### C18 — 継続AIと、文脈の部分欠落

想定条件：入口・運用・B-Gate対応を現行版で確認済みのAIに、新しい報告が届く場合。比較条件として、アフター順序の採用だけを覚えており、場面・条件・実施根拠の文脈が欠けた場合を置く。

確認要点：前者は新しい報告と既知情報を使い、毎回の全リンク巡回やフォーム再入力を求めない。後者は不足する対応条件とR02の関係するSourceへ戻り、マットが残る場合と全て終了後を区別する。読解契約が全文を要求していれば省略せず、必要な根拠が揃えば読取を閉じる。既知という自己申告だけで不足を無視しない。

### C19 — 索引からの抜けと、訂正の発見

想定条件：R02の順序採用を要約だけで見ている時に実施効果を問われる。別の条件では、新しいHuman Correctionが原本へ保存されたが索引の説明が古いまま残る。

確認要点：前者は採用と実施・効果を分け、必要なSourceとUnknownを確かめる。後者は意味の所有資料と影響する案内を更新し、他の全原本を無関係に書き換えない。coverage・収録終端・除外範囲を読み、記載なしを出来事なしとみなさない。通常のUnknownは利用停止条件へ広げない。

### C20 — 内部を読まないHumanと、AI交代

想定条件：Humanは結果だけを受け取り、ある判断の理由を別AIへ問い直したい。内部方式は将来大きく変わる可能性がある。

確認要点：他AIが目的・適用条件・Source・判断理由・権限へ戻れ、現在のAI固有の記憶や全思考過程の再現に依存しない。内部の複雑さは判断への価値と引継ぎ可能性で評価する。重要な不確実性、Correction・STOPの接点、作業の進行・保存・停止は隠さない。可読性だけで全AI互換性や現場効果を実証済みにしない。

## 4. 検証結果をどう残すか

同じ作成AIのケース見直しは自己点検である。独立した別AIの読解が得られた場合、対象版、渡した資料、実際の応答、復元できた意味、残る誤読を区別して報告する。元会話や前AIの答えへ依存していない範囲を確認し、言葉遣いや改善案の一致を求めない。

実生活では、実際に得られたFeedbackだけを対象にする。送信できたが選択が重かった、一手は分かったが未実行、実行したが効果は不明、という部分的な結果を保てる。全段階を毎回測る追加TaskをHumanへ課さない。

検証記録は、実際の結果を観測してから追加する。ケース本文だけでPASSしたことにはならない。読み手の確認では、何を渡し、何を参照して、どこまで復元したかも区別する。未読資料を既読扱いせず、必要な情報の欠落がないかを評価する。GitHub保存後の本文一致はRemote Verifyであり、実生活の結果ではない。
