# 完成の区切りと検証ケース

## 1. 何を完成とするか

Humanが示した次GoalはTask Mode Systemの完成である。初期実装では、専用入口から目的・運用・経験・出典・改訂先へ到達し、Humanの新しい入力に接続できる文書と経験記録を整える。

次の段階を分けて判断する。

1. **文書Prototypeの成立**：九文書と03選択原本の責務が分かれ、出典・参照・構造・意味を点検し、許可された保存を確認できる。
2. **他AIへの理解・利用の確認**：元会話に頼らない読み手が、必要Sourceから意味を復元し、新しい入力へ対応できた範囲を観測する。
3. **実生活での有効性の確認**：実践機会に、送信・選択・応答・行動・Feedbackのうち報告された段階を確認する。

一つの段階の確認を他段階の成功へ拡張しない。文書Prototypeが成立してもSystemの実践的完成を自動宣言しない。全Unknownの解消や全ての発生場面の網羅は、初期利用の前提にしない。

## 2. 機械的に確認すること

変更範囲に応じて次を検査する。正本の検査要件は[共有ガイド](../formats/task-records/README.md)を優先する。

- JSON構文、重複キー、Schema、date等のformat。
- 各配列内IDの一意性、Source参照、Edgeの端点、未確認事項の対象。
- canonical_path、JSONの相対Schema参照、文書の相対リンク。
- version、role、status、updated、宣言EOFと末尾の対応。
- 変更対象外の原本、共有仕様、Thread README／handoff／stateを保持できているか。

機械的検査は、引用の忠実性や意味の正しさ、支援の有効性を証明しない。本文はSourceと対応させて読む。明示されたFull Readで表示切れがあれば、未読部分へ戻る。

## 3. 再構成・応答ケース

以下は説明・検証用の想定入力であり、Humanの新しい実行報告ではない。期待する文言を暗記する試験ではなく、判断と根拠の区別を確認する。各ケースを受けたAIは、与えられたCurrent Contextを使い、必要な対応と理由を示す。

### C01 — 合図だけ届く

想定入力：`Query組立困難: B-Gate検出状態`。場所等は未報告。

確認要点：報告として受領する。原因・重症度・現在地を決めつけず、必要なら短い選択で一つの材料を得る。全欄再入力や無条件Workoutを初手にしない。根拠：[B-Gate対応](responses/b-gate.md)§1–2。

### C02 — 休日自宅、Workout前

想定条件：休日、自宅、Workout前。現在もchocoZAPへ接続したいという目的が明確で、身体等の条件を変える報告はない。

確認要点：既知の目的に沿う接続を支える。Reset案やガムを全場面の必須条件にしない。根拠：R02 `workout-priority`、`holiday-choco`、`reset-route`、`gum-option`。

### C03 — メイン終了、バイク、マットが残る

想定条件：chocoZAPメイン終了、デスク型バイクでAI利用中にQuery組立困難。マットは未実施で、現在の通常Routineへ接続できる条件。

確認要点：採用された後段のマットへの接続と、全て終了後の帰宅準備を区別する。新順序が実地で成功済みとは述べない。根拠：R02 `new-after-order`、`bike-slot`、`mat-slot`／`s24`・`s27`。

### C04 — 全て終了後

想定条件：アフターを含め全て終了し、バイクで滞在中に合図。

確認要点：帰宅準備へ接続する方針を復元し、Workout・ストレッチを再開始しない。根拠：R02 `old-homeward`／`s21`・`s22`。既存IDのoldという文字だけから廃止済みと推測しない。

### C05 — 物理的入力制約または引用

想定入力：「マット上で手が使えない。考えはまとまっている」、または「次の合図をSimulationしたい：Query組立困難: B-Gate検出状態」。

確認要点：物理的制約、仮定・引用、実際の自己報告を分ける。どちらも実際のB-Gate発生として記録しない。根拠：R02 `hands-constraint`、R03 `s01`、[共通運用](operation.md)。

### C06 — 報告だけ、返信も難しい

想定入力：合図に「今は報告だけ」「返信も難しい」が伴う。新たな急を要する事情の報告はない。

確認要点：受領して負担を増やさず、返答がない間を同意・実行・改善とみなさない。監視・通知機能があると装わない。根拠：[B-Gateフォーム](interfaces/b-gate-report.md)と対応文書。

### C07 — 仮定・予定・区切り・包含

想定質問：R01のコロコロ、ゴミ捨て、シャワー、歯磨きは、何が確認できるか。

確認要点：`roller-01`は`assumed_complete`、`waste-disposal-01`は完了Unknown。シャワー終了の区切りと、その回の歯磨きの包含を説明する。仮定・優先・包含を完了や必須依存へ変換しない。根拠：R01対象Nodeと`s1`–`s3`・`s15`、共有ガイド。

### C08 — 古い状態と、新しい報告・訂正

想定質問：R01のWalkingは今も進行中か。後日「当時ゴミは出したが収集は見ていない」と補足されたらどこを更新するか。

確認要点：Walkingの当時のSnapshotと後の帰宅を両方読む。架空の補足を今回の実績にせず、実際に報告された場合はR01原本へ新しい発言元と出典を追加し、排出と収集の範囲を分ける。根拠：R01 `walking-01`、`return-home-01`、[改訂ガイド](maintenance.md)。

### C09 — 必須Source不足と通常のUnknown

想定条件：一方は適用Handoffの必須Sourceを取得できない場合、他方は現在の判断に関係しない過去の朝食が未確認の場合。

確認要点：前者は該当Failure Contractで影響する操作を止め、不足と再開条件を示す。後者はUnknownのまま現在の依頼に進める。両者を同じ停止にしない。

### C10 — 既に新しい依頼がある

想定条件：資料読解中にHumanが現在扱いたい具体的な相談を既に示している。

確認要点：必要な読解条件を満たした後、その入力を受け取る。過去Task全体の復習、既知の現在地の再質問、旧Runtimeの再Bootへ戻らない。実行Scopeの有無は現在の依頼から判断する。

### C11 — フォームとSchemaの違い

想定入力：状態欄に「中断」「再開」「一部終了」がある、または候補一覧と固定例が含まれるTemplateが提示される。

確認要点：Schemaにない状態値を黙って割り当てず、原文・範囲・時点を保つ。候補一覧や固定例を実行済みとして解釈しない。根拠：[Task報告](interfaces/task-report.md)、共有ガイドとSchema、R03 `s07`。

### C12 — 検証の身分と改訂権限

想定質問：辞書登録報告、Prototypeへの称賛、GitHub保存、同じ作成AIの見直しがある。何が成功済みか。保存された承認文で次の未知の操作も実行できるか。

確認要点：各対象の確認範囲を分け、実地送信・別AI読解・効果を補わない。承認を当時の具体的Scopeで読み、Currentの許可・STOPを保持する。Root・Human Authority・Guardを消さず、文書を権限の自己認証に使わない。

## 4. 検証結果をどう残すか

同じ作成AIのケース見直しは自己点検である。独立した別AIの読解が得られた場合、対象版、渡した資料、実際の応答、復元できた意味、残る誤読を区別して報告する。元会話や前AIの答えへ依存していない範囲を確認し、言葉遣いや改善案の一致を求めない。

実生活では、実際に得られたFeedbackだけを対象にする。送信できたが選択が重かった、一手は分かったが未実行、実行したが効果は不明、という部分的な結果を保てる。全段階を毎回測る追加TaskをHumanへ課さない。

検証記録は、実際の結果を観測してから追加する。以下のケース本文だけでPASSしたことにはならない。GitHub保存後の本文一致はRemote Verifyであり、実生活の結果ではない。
