# B-Gate報告を受けたAIの対応

## 1. 受領できたことと、分かったこと

Humanから「Query組立困難: B-Gate検出状態」が届いたら、支援を求める状態報告として受け取る。文脈上の引用・仮定・Simulationなら実際の発生報告にはしない。

この合図は、Queryを組み立てること自体が難しいというHumanの自己報告を、AIとの接続に使う採用名称である。原因・現在地・Task段階・医学的な認知状態まで確定するものではない。User辞書登録はHuman報告として確認されているが、端末UIの直接確認とは別である。

[System入口](../README.md)のRoot・Human Authority・Guard・Current Runtimeを保持する。新しいHuman報告を過去記録から上書きしない。高認知状態で準備した応答案も、現在の身体・責任・時間制約で修正できる。

## 2. AIが行う判断

### 2.1 まず利用可能なCurrent Contextを使う

同じ会話で、場所、何を終えたか、現在の目的、今可能な応答が既に示されていれば利用する。古いThreadや以前の日のWorkout記録を現在地として利用しない。明示された「今は報告だけ」「STOP」も受け取る。

名称だけで情報が足りなくても、報告を不成立にしない。認知困難を報告したHumanへ、詳しい事情を一から書かせることを初手にしない。

### 2.2 場面・進行・応答可能性を分ける

次のうち、対応を変える部分だけを見る。

- 場面：自宅、仕事、移動、chocoZAP等。
- 進行：始める前、途中、メイン終了、アフター途中、全て終了等。
- 応答可能性：短文を読む、選ぶ、一言返す、返信も難しい等。
- 制約と希望：身体、就寝、出勤、約束、今してほしいこと等。

B-Gateの段階を未合意の数値尺度や一方向の重症度段階へ固定しない。手が使いにくい、通信できない、沈黙していることだけでQuery組立困難と判定しない。

### 2.3 必要な不足だけを軽く確認する

場面が全く不明なら、短い選択で一つの判断材料を得る。何を聞くかは文脈次第であり、場所から始めること自体を固定規則にしない。質問が不要なほど情報があれば、その情報から進める。

下記は場面が不明な場合の説明用応答候補である。実際のHuman報告・実地成功ではない。

> 受け取りました。今いる場所だけ選べますか：自宅／外出先／不明。返信が難しければ、今はここで止めて大丈夫です。

一回の応答で全フォームを埋めさせない。既知事項を再質問しない。「不明」でも使える材料から支援できる範囲を探す。判断に必要な根拠がないまま、強い行動指示を選ばない。

### 2.4 現在有効な接続を返す

一つの有限な行動、短い確認、現状の言語化、休止や保留から選ぶ。現在のGuardを変える報告があれば、その条件に合わせる。沈黙から同意・実行完了・改善を推定せず、応答可能になるまでの未知を保持する。

AIの応答は短くてもよいが、Humanが処理できないと先回りして必要な意味を削らない。詳しい検討をHumanが求めている高認知の設計場面では、比較・仮説・Simulationを十分に行える。

## 3. 既存経験から使える条件付き接続

根拠は[Ark27:02原本](../../ark-project/ark27/ark27-02/task-records.json)。これは過去の採用方針と形成経緯であり、以下を読んだだけでTaskを実行しない。

### 3.1 休日・自宅・Workout前

HumanはWorkout-firstと、できればchocoZAPへ接続する方針を示した（`workout-priority`、`holiday-choco`、Source `s07`・`s10`）。現在もその目的・条件に合い、適用Guardを妨げる報告がなければ、その接続を支える。

トイレ→シャワー→chocoZAPというReset案（`reset-route`／`s14`）は、必要時の経路である。全て揃うまで進めない必須依存へ変えない。`gum-option`も任意の方針として扱い、カフェインの無条件追加を指示しない。すでにWorkout後なら、この場面へ巻き戻さない。

### 3.2 chocoZAPメイン終了後のアフター

採用された順序は、**デスク型エアロバイク→ヨガマットストレッチ**（`new-after-order`／`s24`・`s27`）。新アフターの先行部分であるデスク型バイクでAI利用を試し、Query組立困難が出たら後段のマットへ移るという方針である。

したがって、現在デスク型バイクにいてマットがまだ残っていると分かる場合、後段への接続候補を示せる。単に「chocoZAP後」とだけ言われた場合は、メイン後なのか全て終了後なのかを文脈から区別する。新順序の実行・効果は、この資料では未確認である。

### 3.3 全て終了後

その他が全て終了した後、デスク型バイクでAIを使う予定の時間にQuery組立困難が出た場面では、Humanは即時帰宅準備すべきだったと振り返った（`old-homeward`／`s21`・`s22`）。全て終了したという現在の条件に合えば帰宅準備へ接続する。Workoutやストレッチをもう一度開始しない。

`old-homeward`という既存IDだけを見て方針全体を廃止済みと読まない。名前とScopeを一緒に読む。新アフター順序が採用されても、全て終了後という条件の意味は別である。

## 4. 形成経緯を失わない

旧Routineはヨガマット→デスク型バイクだった（`old-after-order`／`s36`）。マットでは手が自由に使えず閲覧中心になるというHuman説明（`hands-constraint`／`s25`）があり、先にバイクでAIを使い、困難を検出したらマットへ移るという発見に至った。

手の制約とQuery組立困難は同じではない。仕事・Workout・時間帯・疲労の関係は、報告・理解の範囲を保ち、医学的因果の実証にしない。詳細は[形成経緯](../experience/formation.md)を参照する。

Ark27:03ではHumanが、chocoZAP系はある程度クリアした一方、問題はB-Gateがいつ来るか分からないことだと訂正した。本対応はchocoZAPだけの手順へ縮小せず、未知の場面でも少ない入力から状況を区別する準備を担う。

## 5. 適用結果の扱い

受領、場面理解、支援の提示、Humanの選択、実行、効果を分ける。HumanのFeedbackがあれば、どの応答や項目が役立ったか、何が負担だったかを報告範囲で学ぶ。新しい実行があれば現在のThread原本へ、古い経験への訂正ならその経験原本へ、出典付きで反映する。

通常のUnknownを全て聞き尽くさない。必須Sourceや権限の不足・意味を変える競合があれば、該当契約で影響する操作を止める。現在のTaskや依頼の区切りでHuman Reviewへ戻り、別Taskや次Trialへ自動昇格させない。
