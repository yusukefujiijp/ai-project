# pstackの設計理解

pstackの理解では、各原則を個別に知ることに加えて、どの状況で何を選び、その結果を何に使うかを読む必要があります。本稿は、Goalを受け取る入口から、仕事・検証・継続・中断・再開・終了までをつなぎます。

[人物と全体像](README.md) · [Arkへの接続](ark-connection.md) · [根拠記録](evidence.jsonl)

<a id="ps-scope"></a>

## 対象版と説明の位置づけ

対象は、cursor/pluginsのcommit `1ba91fc25c0977741dd0e267849e6234b037ed0a`です。[poteto-modeの入口](https://github.com/cursor/plugins/blob/1ba91fc25c0977741dd0e267849e6234b037ed0a/pstack/skills/poteto-mode/SKILL.md)と、今回の判断に必要な個別本文を読みました。

「原型」は、この固定版の公開文書・コードを指します。各文をLauren本人の逐語発言とは扱わず、現在の最新版、Grok Bot当時の内部実装、すべての原則の網羅的読解とも区別します。

以下では、本文の明示内容と明示された理由を説明し、そこから導く関係はAIの解釈として示します。実行指示は研究対象です。このWikiからLoop、別AI、外部操作、保存などの許可は生じません。

<a id="ps-entry"></a>

## 入口はGoalを仕事と検証へつなぐ

**原型の明示内容：** poteto-modeは、最初にHumanのGoalと解こうとしている問題を言い直し、変更を伴う場合は必要な変更の見通しを示します。そのGoalを委任先の説明、PRの理由、最終報告へも通します。最初の言い直しについて、毎回の確認待ちを必須にはしていません。［E-LT-ENTRY-1BA91FC］

次に仕事をPlaybookへ対応させ、その手順を読み、必要な仕事へ具体化します。原則の索引は、どの本文を読むかを選ぶ入口です。適用する原則は個別のSKILL.mdを全文読むよう指定されています。名前や索引だけで原則の詳細を知ったとは扱えません。

非自明な変更・設計判断等ではhowへ接続します。大きな一回の仕事、継続的なプロジェクト、一件の終了条件へ向かう実行は、入口でも異なる経路として扱われています。Autonomous runとOrchestrateを、名前だけで同じものにまとめません。

委任では、入口を受け取った親がPlaybookを進め、個別作業を渡します。親は受け手の成果を確認し、自分の説明を作る責任を持ちます。別AIの報告をそのまま完了の証拠にはしません。

**AIの解釈：** Goalの再記述が委任・検証・報告へ伝わることで、途中の仕事が「何のためだったか」から離れにくくなります。言い直しだけを済ませても、後続の条件が更新されなければ、この関係は成立しません。

<a id="ps-human"></a>

## 調べることとHumanが決めることを分ける

**原型の明示内容：** 方法や挙動について質問する前に、観測で分かる事実か、読み取り調査で答える仕事か、実際の製品判断・選好かを分類します。観測で決まる分岐にはPrototype、引用付き回答を成果とする読み取り調査にはInvestigationという区別があります。［E-LT-ENTRY-1BA91FC］

Never Block on the Humanは、可逆でレビュー可能な仕事について、進めてHumanが訂正する方針を示します。本文の理由は、可逆な判断の誤りより、確認待ちで停止する損失が大きい場合があるためです。製品の方向はHumanが持つとしています。［E-LT-HUMAN-GATE-1BA91FC］

ただし、入口のAutonomyはteam chatなどを無確認で進める例に含め、Never Block on the Humanの本文は外部メッセージを確認が必要な例に含めます。例示の対象範囲に差があり、この本文群だけから、あらゆる外部操作に適用できる一律の許可を確定しません。

**Arkへ接続する時の論点：** 調べれば分かることをHumanへ丸投げしないことと、調べるための実行権限があることは別です。読み取りだけの委任では、その範囲の調査を担います。原型の可逆性や自律方針を、そのままArkの追加権限へ転用しません。

<a id="ps-verification"></a>

## 検証できる単位が、次の判断の土台になる

| 原則 | 原型の指示・明示理由 |
|---|---|
| Sequence work into verifiable units | 小さな変更単位を確かめてから後続へ進む。原因を局所化し、壊れた土台へ仕事を積まないため |
| Prove It Works | 実物を直接確かめる。代理情報や自己申告からの誤った推定による損失を避けるため |
| Build the Lever | 非自明な仕事では、仕事や検証を再実行できる道具を成果にする。他者が確認を再現できるようにするため |

［E-LT-UNITS-1BA91FC / E-LT-PROOF-1BA91FC / E-LT-LEVER-1BA91FC］

原型が挙げる単位は、既知の状態、一つの変更、その確認、次の変更という関係を持ちます。提出するcommitやPRの順序も、根拠の流れを読み手が追えるように設計します。

Prove It Worksは、実際の値・成果・動作を確認対象とし、プロセスの生存を間接的な状態から推定するような確認を避けます。確認が失敗した場合には、観測方法自体の妥当性も疑うよう求めています。

Build the Leverは、道具の作成を原型の実際の成果として求めます。本文を紹介しただけ、手作業を終えただけでは、その原則を実施したことにはなりません。

**AIの解釈：** 単位を分ける意味は、作業量の縮小に加えて、後続の判断に使える確かな状態を作ることにあります。検証が失敗した単位に依存する仕事へ進めば、後で原因を分けにくくなります。一方、失敗した単位に依存しない仕事まで止める必要があるかは、別の判断です。

何を検証すればGoalの達成を示せるかも必要です。検査が通っても、その検査がHumanの願いを十分に扱っていなければ、Goalへの適合は別に検討します。この三者の切り分けは[Ark側の方法](ark-connection.md#ark-method)で具体化しています。

<a id="ps-run"></a>

## Autonomous runは終了条件に対して反復する

**原型の明示内容：** Autonomous runは、最初に検証可能な終了条件を定め、その条件へ向けて仕事を進めます。［E-LT-RUN-1BA91FC］

- イベントを待つ仕事には監視役と時間ベースの補助的な確認を使い、それ以外には適切な間隔の再開を選ぶ。
- 再開にはCursor内蔵の`/loop`を使う。本文はこれをpstackのSkillとは区別する。
- 各反復で証拠が支持する変更を行い、終了条件に対して検証する。前進した変更を残し、役立たなかった変更を取り除く。
- 作業単位ごとに検証し、最後だけに確認をまとめない。
- 途中で見つかった問題へ対処した後も、元の終了条件へ戻る。
- 判断と結果を反復ごとに記録し、条件を満たした時に終了する。

原型は、停滞だけで終了せず、方法を変えて進むことを求めます。同時に、真の行き止まりは表明し、成功扱いにするために終了条件を緩めない方針です。

**AIの解釈：** 終了条件は、作業の選択、途中の寄り道からの復帰、成果確認、終了判断をつなぐ中心になっています。ただし、Humanによる正当なGoal変更をどう反映するか、現在の委任や資源上限とどう組み合わせるかは、Arkの契約に沿って扱う必要があります。

この本文の読解は、Cursorの`/loop`の実装・実動作を確認したことでも、別環境で同じ継続が可能と確認したことでもありません。

<a id="ps-trail"></a>

## 判断記録は、理由と証拠を後から追うために使う

Show me your workは、一つのTSV記録に、時刻・段階・判断・理由・証拠への参照・結果を残します。重要な分岐、検証済み単位、方針変更、取り消し、障害などを記録し、Loopでは反復ごとに一行を残す方針です。［E-LT-TRAIL-1BA91FC］

記録は追記型です。誤りを消して過去の判断を作り直さず、後続の行で訂正します。新しい会話や置換された受け手は別のrunとして扱い、既存記録へ加わる際の`start`行で、どの範囲を別runから受け取ったかを示します。

終了前には、当該runの会話記録と照合し、各行が実際の判断・操作へ対応するか、証拠が主張を支えるかを確かめます。原型はさらに、異なるモデル系列の受け手による記録レビューを要求します。これは全作業のやり直しではなく、弱い根拠、確認漏れ、危うい判断などを読む工程です。

記録用の`log.sh`も全文を読みました。コードは時刻付与、セル整形、ヘッダーと行の追記を担います。記録内容の真偽、Goal達成、再開時刻を判定する処理は含みません。これはコードの静的読解であり、実行試験ではありません。［E-LT-LOG-1BA91FC］

**AIの解釈：** 記録は、判断を検証するための材料です。記録があること自体を、その判断の正しさへ変換できません。異モデルによるレビューも、実施したことと指摘の妥当性を分ける必要があります。

<a id="ps-resume"></a>

## 中断・再開では、残っている現実から仕事を選ぶ

Pause safelyは、安全な区切りで止め、作業状態と再開情報を残す手順です。原型では、現在の単位を終えるか戻すかを判断し、新しい仕事を始めず、入れ子の受け手を止めます。wipコミットや再開メモの作成も含みます。［E-LT-PAUSE-1BA91FC］

これらの保存操作は原型の指示です。ArkのPlan-onlyや停止指示のもとで、同じ操作が許されることを意味しません。

Session pickupは、以前の記録と作業実体から、何を継承し、何が完了し、どこから再開するかを復元します。完了した作業や再現手順を初めからやり直さず、残る仕事を適切なPlaybookへ渡します。同時に、継承した主張を元のGoalと実物に照らすことも求めています。［E-LT-PICKUP-1BA91FC］

Make Operations Idempotentは、前回の意図より、現在ある状態を読み、Goalとの差分だけを処理する設計を求めます。本文は、中断・再試行が通常起こる環境で、部分実行の残り方によって結果が変わると、再開のたびに調査が必要になると説明します。［E-LT-IDEMPOTENT-1BA91FC］

**AIの解釈と仮例：** 保存操作の応答が途切れた時、成功・失敗のどちらも確定していなければ、同じ追加を直ちに繰り返すより、実体や識別子を照合して差分を判断する方が適切です。この仮例は、特定の保存先で冪等性を実証した記録ではありません。

既存成果の再利用と、現在状態の照合は両立します。全工程の再演を既定にする必要はなく、過去の報告だけで現在の成果を確認したことにすることもできません。

<a id="ps-relations"></a>

## 原則の関係から何を理解できるか

本稿からのAIの統合的な解釈は、次の通りです。

1. Goalの理解が、仕事の選択と検証対象を決める。
2. 検証可能な単位が、後続へ渡せる状態を作る。
3. 実物の確認が、継続・修正・終了の根拠になる。
4. 判断記録が、その根拠と変更理由を後から追えるようにする。
5. 中断後は、記録と実体の差を読み、残る仕事へ接続する。
6. これらを実際に繰り返すには、権限、再開機構、状態保持、観測手段が必要になる。

判断方法、証拠、実行環境は互いに支え合います。一つが存在することだけで、他も成立したとは言えません。

原型の固定版を読むこと、Arkで方法を採用すること、受け手の実応答を観測すること、長期運転の効果を確認することは別の段階です。[Arkへの接続](ark-connection.md)では、それらを混ぜずに扱います。

別版を読む場合は、その版と取得範囲を残し、何が変わったかを資料から確かめます。古い固定版の意味を、新版が最初からそうだったように書き換えません。過去のAI解釈も、将来の読者が検討できる候補として保持します。
