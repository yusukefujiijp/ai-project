# エージェントへの委任と信頼

**AIにどこまで仕事を任せられるかは、仕事・権限・環境・確かめ方の関係として考えます。** これは[Lauren Tanの公開実践](../../people/lauren-tan/README.md)などから編んだAIの見立てです。人物名を知らずに「任せたいが、何を確かめればよいか」から入るためのページです。

ここで扱う信頼には、記述を根拠付きで理解できることと、実際の仕事を委任できることの両方があります。前者の確かさだけで後者の権限・実行環境が整ったことにはなりません。利用時の権限とGuardは[AGENTS](../../../AGENTS.md)および現在のHuman指示が所有します。

<a id="at-verification"></a>
## 成果を、仕事に合う方法で確かめる

まず、任せる仕事の終点と、そこへ到達したと判断できる証拠を考えます。コードなら実際の動作や対象に合う試験、Wikiなら読者が意味・根拠・Unknownを再構成できるかが候補です。pstackのverifyガイドは、実際の対象を使う確認と、確認できない範囲を残す姿勢の参考になります。［[E-LT-VERIFY](../../people/lauren-tan/evidence.jsonl)］

**成立条件：** 目的に合う観測へアクセスできること。形式検査や説明だけしか見えない時には、その範囲を超えて完了・効果を認定しません。すべての低影響な変更へ重い試験を課す原則でもありません。

<a id="at-environment"></a>
## 能力を発揮できる環境と、任せる境界を合わせる

必要な資料・道具・再現できるデータ・失敗を調べる手段が不足すると、能力のあるAIでも推測に頼りやすくなります。pstackの検証・長時間作業のガイドは、環境、確かめられる終点、記録や介入可能性を考える材料です。［E-LT-VERIFY / [E-LT-OVERNIGHT](../../people/lauren-tan/evidence.jsonl)］

**成立条件：** 対象に応じた環境と観測が実際に用意されていること。長時間動く設定やagent数だけを、結果の質や無停止の稼働へ読み替えません。環境を整えるための権限がなければ、利用できる範囲・不足・回復方法を示します。

<a id="at-authority"></a>
## 確かめられる能力と、有効な委任を区別する

OpenAIのDots発表は、接続アプリの権限、行動の許可・承認・禁止を扱うCustom Rules、行動のreviewを説明しています。これは製品の発表時の説明であり、この会話や全Runtimeで同じ機能が有効という証拠ではありません。［[E-LT-DOTS-LAUNCH](../../people/lauren-tan/evidence.jsonl)］

**Arkへの適用案：** 今回の対象・承認範囲・Humanの訂正やSTOPを保持し、有効な承認内では必要な検証まで進める。品質確認を追加権限へ変えず、既存の承認を毎回取り直す仕組みにもしません。具体的な契約はAGENTSへ戻ります。

<a id="at-parallelism"></a>
## 並列化では、共有するものを先に見分ける

独立した仕事は分離できる一方、同じファイル・状態へ書く仕事には衝突があります。pstackの共有状態に関する原則は、不要な共有を減らしてから、必要な共有に順序や書込主体・競合制御を設ける考え方です。［[E-LT-SEPARATION](../../people/lauren-tan/evidence.jsonl)］

**成立条件：** 実際の共有対象と変更経路を把握できること。担当名を分けただけで衝突がなくなったとはしません。Arkでは、各所有先を保ち、更新直前の版を確認し、競合を解消してから反映することが適用候補です。複数ラインの存在は、常時同時稼働や長期効果を証明しません。

<a id="at-correction"></a>
## 訂正が、どの判断を変えるか辿れるようにする

これはWiki設計に関するAIの提案です。資料の追加だけでなく、どの主張を支持し、何を証明しないかを残すと、訂正の影響を辿れます。

例えば公式発表日が訂正された場合、Laurenページの公開順と日数を見直します。それだけでpstackの検証方法やHumanの「母」という意味を削除する必要はありません。因果を示す新しい一次資料が得られた場合は、製品史のUnknownと関係する説明を再評価します。

反応・訂正の記録は[共有Feedback](../../../references/feedback/README.md)、条件付きの再利用判断は[Lessons](../../../references/lessons/README.md)、成功の意味と成立条件は[Success Cases](../../../references/success-cases/README.md)が所有します。この概念ページは、対象についての理解と比較を持ち、同じ経験本文を重複保管しません。

<a id="at-application"></a>
## この概念を最初に試す問い

今回のWikiでは、「元会話を渡さずに、Laurenの重要性と製品史の未確認を説明できるか」を一つの観測にできます。人物紹介を暗記できることより、別の問いから適切な根拠へ戻り、訂正の影響を判断できるかを見ます。

執筆者の自己点検と、独立した読者による確認は別です。この初版では後者・実利用・継続効果は未確認です。追加の読者確認を自動送信や恒久監視として開始するものではありません。

根拠IDのリンク先は[Laurenのevidence.jsonl](../../people/lauren-tan/evidence.jsonl)です。ファイル内で表示された根拠IDを検索してください。[根拠の読み方](../../people/lauren-tan/README.md#evidence-guide)に取得経路と限界があります。ここに二重の台帳は作りません。

新しい根拠・反例・HumanのFeedbackが適用条件を変える時に、このページを更新します。別の問いへ役立たずLauren紹介の言い換えだけになるなら、人物ページへ統合する余地を保ちます。[Wiki入口](../../README.md)へ戻る。
