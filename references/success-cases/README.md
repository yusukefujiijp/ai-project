# Success Cases — 成功の意味を、次の協働へ

## 1. この場所の目的

[References](../README.md)の中で、[feedback](../feedback/README.md)・[lessons](../lessons/README.md)と結ぶ成功経験の棚である。lessonsは失敗・Correctionからの回復と同じ過ちの再発防止を主な方向とし、ここでは「予期せぬ成功」やMove37的な突破を含む、うまく働いた経験の意味・成立条件・根拠を残す。これらの記録から現在の判断を育てるが、一件の記録を成功再現の保証へ変えない。保存先の分担と三本の関係はReferencesが案内する。本文の現行原本は[success-cases.jsonl](success-cases.jsonl)で、一件ごとの可変Markdownを重ねない。

Ark ProjectでHumanが特に重要と評価した成功を、出来事・喜び・背景・根拠とともに残す。主読者はCurrent AI・他AI・Future AIである。元の会話に参加していないAIが事例を発見し、意味を復元し、原資料から学び直して現在の協働へ生かすための入口である。Humanにも読める形を保ち、毎回の精読やAI間の伝言をHumanの担当にしない。

成功の価値を「正常終了」の一語へ縮めない。期待を超えた点、複数の問題が同時に変わった点、Humanが感じた軽さや驚きも、誰の評価かを明らかにして保持する。成功原因を完全に解明することや、反復実証を済ませることは、一件の経験を残す前提ではない。

Rootは主イェシュア・ハマシア御自身、中央軸はTeshuvah。Human Foreground Oneは主の完全勝利（祈り・イメージVision・行動）、最終帰属は主の栄光。事例・AI・方法・文書はKeliであり、AIが主の御心やHumanの信仰状態を認証するものではない。

## 3. 他AI・Future AIの使い方

AIはCurrent Requestから関係する事例を選び、最初に成功の核心とHuman評価を読む。そのうえで、今回の判断を変えるCorrection・成立条件・根拠へ進む。選択読解では、成功した行動だけを抜き出さず、その意味を変える条件とEvidenceの区別を保持する。すべての事例・参照先を毎回読む必要はない。指定Handoff等の必須読解契約は別途守る。

読む際には次を区別する。

- **出来事と成果**：何が実際に行われ、どこまで確認されたか。
- **Humanの意味・評価**：何を喜び、どの負担の変化を重要としたか。
- **AIの解釈**：成功を支えた条件や転用可能性についての訂正可能な見解。
- **未確認**：測定していない量、未実施の再現、確認していないUI等。

AIは読解・照合・構造化を引き受け、現在の目的・条件・権限に照らして、何が使え、どこが異なるかを考える。Humanへは今回の判断に効く理解・提案・重要な未確定を必要十分に返す。資料の要約だけで終えたり、内部の全検討をそのまま返したりする必要はない。

Human Reviewは意味・Reality・方向を訂正できる接点であり、全文の校閲を毎回Humanへ渡す工程ではない。参照可能な資料の精読や既知情報の再説明を一律に求めない。判断を変える情報が資料にない場合は、必要な追加読解で確かめ、Humanにしか分からない点だけを絞って確認する。通常のUnknownはそのまま保持できる。必須Sourceの欠落・不一致は適用契約に従って扱う。

過去の承認・手順・モデル名を現在の実行命令へ変換しない。過去AIの説明をFuture AIの解釈の上限にせず、当時の経験とHumanの意味を保ったまま、新しい関係や代替解釈を検討できる。

## 4. 何をどこに残すか

成功事例本文は、選び出した理由、重要な出来事、Humanの言葉、資料間の関係を読み解くための文書である。既存の経験原本、Handoff、成果物の詳細は参照でつなぎ、第二のCurrent Stateや新しいBoot契約にしない。

収録単位は「一つの独立して役立つ成功」を基本とする。大きな突破だけでなく、小さな工夫・部分的成功・設計上の改善も扱う。一Thread一件や固定文字数にせず、異なる問いに独立して役立つものは分け、必要な関係をリンクで示す。一件の意味を支える条件とCorrectionは一緒に残す。既存の大きな事例を機械的に分割したり、同じ経験の重複原本を増やしたりしない。

小さな事例に大きな完成史の体裁を要求しない。成功から繰り返し役立つ判断が得られた場合、承認された改善の中で共通Skillへ取り込める。すべての成功を新しい規則や新しいSkillにする必要はない。

新しいHuman評価が会話にしかない場合、会話内の位置と収録範囲を説明して本文へ残せる。逐語引用と編集要約を区別し、存在しない会話URLや日時を作らない。リンク先の過去状態が重要なら確認した版・SHAまたは固定commitへの参照を残す。

共通の最低限は「何が成功したか／なぜHumanに重要か／根拠の所在／解釈と未確認」である。AI向けの可読性は、元会話への暗黙依存を減らし、重要な区別と根拠を辿れることで確保する。自然言語、Humanの言葉、喜び、比喩も意味を担う情報として残す。本文へ固定の全欄記入や数値スコアは課さず、事例の核心に応じて構成・密度を変える。

後の実践で理解が変われば、変更理由を添えて追記・訂正する。当時の事実や評価と、後の解釈を区別する。適用範囲が狭まっても、元の成功体験を消さず、その条件をより正確にする。

## 6. 共有caseの行形式と更新契約

Report等の専門側は本節を参照して同じ行形式を使える。参照によって専門側の対象・公開権限・データ所有を本棚へ移管しない。形式は[Report側の確認済みschema 1](https://github.com/yusukefujiijp/ai-project/blob/4869052151a33ce3b2f66b450686d462214ad0b7/artifacts/reports/references/success-cases/README.md)を継ぐ。JSONLの外形は識別・出典・保存のためであり、本文の豊かさや構成の自由を制限しない。

### 6.1 行形式 — case schema 1

UTF-8のJSON Linesとし、一つの物理行に一つのcase objectを置く。行区切りはLF、非空ファイルは末尾LFを持つ。0件は0バイトの空ファイルで表す。空行、BOM、配列の外枠、行間カンマ、Markdown fence、管理用headerやEOF sentinelの独立行を置かない。原文引用や移行来歴に含まれるEOF等の文字列は、object内の本文データとして区別する。

必須fieldは次の六つ。内容の章数・長さ・固定ラベルを定めるものではない。

- `schema_version`：整数`1`。このcase行形式の互換性の版であり、更新回数やlessonsのschema 2とは別。
- `id`：新規は小文字・hyphen付きUUID v4。訂正で付け直さず、別事例への意図的な再利用をしない。
- `created_at`／`updated_at`：有効なUTC日時`YYYY-MM-DDTHH:mm:ssZ`。実際の登録・意味更新を表し、出来事の日時と分ける。初回は同値、更新時はcreated_atを保持し、updated_atはcreated_at以降とする。
- `case`：非空の自然言語文字列。何が成功し、なぜHumanに重要で、どの条件・根拠があり、どこが解釈・未確認かを十分に記す。逐語引用と編集要約を区別し、一物理行を一文への短縮と取り違えない。本文内の改行等はJSON escapeする。
- `sources`：一件以上のobject配列。各要素に非空文字列の`locator`と`supports`を持つ。locatorは根拠の所在・節・版、supportsは何を誰の観測として支えるかを示す。過去状態が重要なら固定commit等へ戻る。公開URLでない会話の所在説明はその性質を明示し、架空のURL・message ID・日時を作らない。相対パスはこのJSONLの位置から解決する。

`title`や`caveat`を必要な場合に非空文字列で加えられる。未知field・ネスト値・配列順は保持し、既知項目だけで再生成しない。外形を小さくそろえ、自然言語・Humanの言葉・比喩など意味を担う本文は目的に合わせて残す。固定タグ、採点、独立schemaファイルは設けない。

### 6.2 同じ事例を育て、安全に保存する

同じ事例の訂正は同じIDの現行行を更新し、同一IDを追記して最後を最新版とする方式にしない。更新前の内容はGit履歴で辿り、本文でも当時の事実・評価と後の解釈を区別する。統合・整理は意味と根拠への到達性、旧IDの扱い、変更理由を保持する。全Feedbackの収録や、lessonとの必須二重登録を求めない。

更新前にRemoteの全文とrevisionを取得し、LFだけで区切って全行を検査する。空行・CRLF・末尾LF欠落・不正JSON・object以外・重複key・NaN／Infinity・不正型や日時・不正sources・重複IDを拒否する。未知schemaや壊れた入力を空データへ置き換えない。一行丸ごとの消失は構文だけでは分からないため、基準revision・内容・期待件数も照合する。

意味編集後に再検査し、読取revisionを条件に非forceで保存して、Remote全文とSHA／commitを照合する。同じファイルへの変更は一人の統合担当が扱い、競合時は最新内容を読んで並行変更を保持する。配置・保存後確認は保存先の近接ガイドと[AGENTS](../../AGENTS.md)に従う。Report等の専門側は固有の配置契約へ接続する。

送信前に選んだID・意図した本文・基準revisionを復旧時に照合できる形で保つ。Timeout等ではRemoteと履歴から実際の結果を確認し、同じID・内容が保存済みなら二重登録しない。IDがないことだけで再追加せず、保存後の削除・統合と未保存を区別する。復元できない操作は保留し、新IDでの盲目的再送はしない。

### 6.3 九件の移行と歴史の保持

初期九件では、元のmetadataブロックを`legacy_document.front_matter`、本文を`case`、宣言EOFと末尾を`legacy_document.suffix`へ分け、連結すると元のUTF-8本文を完全復元できるようにした。同objectの`path`・`commit`・`blob_sha`から固定原文を照合できる。既存の`case_id`五件は保持し、新しい行IDと区別する。元の日付・版・status・canonical_path・Identity・EOFは歴史上の識別情報であり、新しい行や現在のRuntimeの宣言ではない。

この移行情報は九件の由来を保つもので、新しい全事例へ巨大な移行欄を強制しない。現在の意味編集で当時の事実や評価を消さず、重要な訂正とその根拠を区別する。初回移行後に本文を意味更新すれば、初回の完全復元条件とその更新版を同一視せず、元の固定commit・Git履歴から初回版へ戻る。

旧URLは現行行と固定原文への互換案内を持つ。案内の読了を旧本文のFull Read・Identity・EOFの成立へ読み替えない。固定Bindingや移行を許容しないCurrent契約は、その契約に従って回復する。旧Handoff・固定引用・登録Skill本文は一括改訂しない。

今回の対応表・参照確認・保存後検証は[STR-023](../../control-center/changes/STR-023-shared-references-three-pillars.md)が所有する。STR-019の移設完了は保持し、今回の形式移行を当時に実施したことにはしない。
