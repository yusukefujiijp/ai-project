# Problem Solving

**困りごとの名前から、今のGoal・判断・根拠・次に解く接続へ戻る入口。** 就寝前の寝落ち問題を最初のモデルケースとして、手段が変わっても問題の意味と学びを引き継げる構成を育てる。

Rootは主イェシュア・ハマシア御自身、中央軸はTeshuvah、Human Foreground Oneは主の完全勝利（祈り・イメージVision・行動）、最終帰属は主の栄光。問題解決はその目的に仕える営みであり、このフォルダ・方法・AIはKeliである。共通の権限・品質・Guardは[AGENTS](../AGENTS.md)、Identityは[ARK](../ARK.md)が所有する。

## 1. 今扱う問題へ進む

| 問題・入口 | この資料が所有すること |
|---|---|
| [就寝前の寝落ち問題](cases/bedtime-unintended-sleep.md) | 睡眠と就寝前の必要行動を両立するGoal、入口の再現性、候補手段、経験と未確認をつないだ現在の判断 |
| [GitHubの構造・案内の問題](../control-center/github/README.md) | Repository整理の既存専門入口。案件の原本は同領域に保ち、このフォルダへ複製しない |

この一覧は所在と主題の案内であり、全案件の進捗表ではない。最新の成果・保留・次の判断は各担当原本で読む。一覧にない問題や未整理な相談も、そのまま受け取れる。ファイル作成・分類完了を相談や解決の開始条件にしない。

## 2. 案件の単位と置き方

**何を、どの状態へ変えたいか**を案件の軸にする。コーヒー・ガム・リステリン等の手段名、Thread名、解決段階を、そのまま固定の分類軸にしない。同じGoalに別の手段が出ても、比較と形成の経緯を同じ案件で保持できる。

初期構成はこの入口と、実際に必要になった案件本文を置く **cases/**。最初の案件は一つのMarkdownで扱う。既存領域に適切な原本がある問題は、ここから案内するだけでよい。すべての問題に新しいcaseを作る義務はない。

案件本文は、読んだAIが「何に困り、何を守り、なぜ今この判断をし、何が未確認か」へ戻れるだけの文脈を持つ。Goal、報告、仮説、Correction、試した結果、保留、根拠など、今回の理解に必要なものを選ぶ。固定の空欄や全項目の記入を要求するSchemaではない。

## 3. 一つの内容を、担当する原本へ

| 内容 | 所有先と、この入口・案件との関係 |
|---|---|
| 問題全体の最新の意味・判断 | 該当case、または既存の担当原本。一つの編集責任を明確にする |
| Humanの原発言・行動報告・Correction | 発生したThread等の[経験原本](../formats/task-records/README.md)。caseは意味を整理し、原文の所在とIDへつなぐ |
| 製品・分量・専門知識 | [Caffeine](../lifestyle/caffeine/README.md)等の専門資料。複数案件で同じ定義を作り直さない |
| 再利用する解決の方法 | [problem-solving](../skills/problem-solving/SKILL.md)等の既存Skill・方法の所有先。caseでの適用経験と共通手順を分ける |
| 領域を越える知見 | [references](../references/README.md)を入口に、既存所有先との関係を確かめて残す。全caseから自動でlessonを量産しない |
| 成功の形成・成立条件 | 根拠に見合う[success-cases](../references/success-cases/README.md)。有望な案や良い言語化を実生活の成功へ昇格させない |
| 構成変更の理由・検証 | [GitHub整理](../control-center/github/README.md)から該当STRへ。生活上の問題全体の所有先にはしない |

共通名は「問題解決 / Problem Solving」。`$problem-solving` Skillは現在の困りごとに合う方法を選び、このフォルダは案件とその担当原本へ案内する。既知の原本へは直接進め、Skillの利用と案件ファイルの作成を互いの必須条件にしない。

専門資料とcaseの両方に同じ現在欄を作らず、共通定義は専門資料、問題の現在判断はcaseへ戻す。Threadが変わっても経験の出自を保ち、caseの保存をThread移行・受入れ・Project設定反映と同一視しない。

## 4. Living Reviewで育てる

新しい報告やCorrectionを受けたら、**どの接続が変わったか**を読む。うまくいかなかった手段にも、条件やBottleneckを見分ける保存価値がある。過去時点のUnknownを消して新しい結果に塗り替えず、当時の判断から何が変わったかを残す。

Goalへつながる価値、競合、成立条件、不要な順番待ち、複数の利益が同時に得られる可能性をGraphとして考える。図や表は理解を助ける時に選び、表を埋めることや一つの方法への統一を目的にしない。言語化だけで依頼が満たされる時は、その成果で閉じられる。

ファイル分割は、異なる更新責務、根拠の量、読解の難しさが実際に現れた時に考える。解決済み・保留といった状態だけで住所を動かさず、担当原本で条件を説明する。初期の棚を完成形に固定せず、他の案件で役立つか・余計な手間がないかという実利用から改善する。
