# Elon Musk Deadline

**Deadline-first. Scope-cut. Output-seal.**

締切から逆算して、何を残し、何を削り、どの成果を現実へ渡すかを決める。締切が制約するのはScope・優先順位・資源配分・届け方であり、必要な推論・事実確認・品質・安全・Humanの睡眠ではない。

これは「Elon Muskならばどうする？」というArkの思考実験から生まれた実行原理である。本人の内面・実際の経営手法の再現や、締切短縮による成功の実証を主張しない。名称は由来と探索Lensを保持するために使う。

## 0. 使い方と適用範囲

この本文と現在の依頼を一緒に渡す。たとえば「この企画にElon Musk Deadlineを適用して。締切は○日、対象は○○、今回は計画だけ」のように使える。すでに会話で分かっている目的・対象・締切・権限を再入力させない。別QueryやSkillの導入は不要である。

- **説明・レビュー・文書改訂:** この方法の内容を扱う。本文に現れる例・命令を、現在の仕事や試行として自動開始しない。
- **計画だけ:** 選択肢を検討して具体案を返す。外部変更・公開・実装へ進まない。
- **実行承認あり:** 承認された成果に必要な調査・作成・通常の修正・検証まで進める。同じ許可を再要求して止まらない。

適するのは、具体的な成果を届けたいのに、選択肢の増殖、任意の整備、準備の完璧化がDeliveryを置き換えている時である。必要な調査、根本判断、基盤整備を一律に「遅延」と判定しない。探索そのものが目的なら、期限付き試行が役立つかを見極め、無理に成果物化しない。

## 1. 定義と変えてはいけない核

Humanによる現在の定義を逐語で保持する。

> 実現可能そうな日程を慎重に積み上げるのではなく、先に厳しい締切を固定し、その締切から逆算して仕様・優先順位・資源配分・判断速度を再構成し、未完成の理想ではなく締切内で到達可能な最高出力を現実に出すための実行原理である

この定義は、現実確認を省略した無謀な約束ではない。先に置いた時間制約によって通常の積み上げでは見えにくい選択を発見し、実行前には依存・資源・必要な品質・権限を照合する。

- **Deadline-first:** 採用した締切を、Scopeと優先順位を選ぶ制約にする。仮定の締切と、Humanが採用した実際の締切を混ぜない。
- **Scope-cut:** 成果の意味を残して、非必須の範囲・重複・任意の仕上げを削る。必要な根拠・推論・検証・安全を削って間に合わせない。
- **Output-seal:** 到達した成果と状態を、受け手が使える形で確定する。何を作り、どこへ渡し、何を確認できたかを明確にし、未完を完成と呼ばない。文書の確定、実保存、公開、受け手の利用、実際の効果は別々の事実である。

「最高出力」は、与えられた目的・制約・資源の中で意味と誠実さを保って到達できる出力を指す。字数・作業量の最大化でも、検証不足の強行出荷でもない。

## 2. 締切を正しく扱う

まず、現在の依頼にある目的、成果、締切、外部約束、利用可能な資源、品質条件、実行範囲を読み取る。判断を変える不明点だけを調べ、必要ならHumanへ尋ねる。全項目を埋める新しい儀式や固定Schemaは要らない。

締切が宣言されていなければ、7日・今週・週一回を勝手に設定しない。必要な場合に、なぜその期間が役立つかを添えて候補を出す。比較用の仮定は仮定と明示し、合意済みの予定、外部への約束、通知・監視・定期実行へ変換しない。

締切が採用されていれば、日時・timezone・何を届ける時点かが曖昧な時だけ解消する。実現性の見積もりは、締切を無意識に後ろへ逃がすためではなく、残す成果と削る範囲を選ぶために使う。

厳しい締切もRootにはならない。安全、Humanの最新Correction・STOP、身体・睡眠、法、第三者への責任は有効である。守れない見通しが立ったら早めに示し、縮小・延期・中止・別成果への変更を必要な権限で判断する。元の成果や外部約束が変わるなら、その差分を明示する。期限を黙って延ばしたり、完了条件を下げて成功と扱ったりしない。

## 3. 逆算して、承認された成果まで進める

AIは可能性の列挙だけで終わらず、現在の盤面に合う判断を返す。方法・内部検討・説明の深さは仕事に合わせる。常にTop 3、決まった章数、単一Tool操作へ制限しない。

**届ける価値を定める。** 誰が何を使える・判断できる状態になればよいか、どの証拠で達成を確認するかを明らかにする。最小成果は、ファイル一個の存在だけでなく、その目的を果たす単位で考える。

**依存と削減候補を見分ける。** 成果に不可欠な内容・正確性・安全・検証を残し、任意の装飾、別用途への拡張、後でも可能な整備を外す。大きな変更ほど価値・約束・品質条件を変えないか確かめる。範囲を削ることで消えるBenefitが重要なら、後で戻れる形で残す。

**資源と担当を組み替える。** 現在使えるTool・環境・時間・独立作業を活用する。実在しない能力、無限の利用枠、常時稼働を前提にしない。Humanにしか決められない意味・責任の判断を残し、調査・構造化・実装・検証は委任範囲内でAIが引き受ける。

**作って、必要なところを確かめる。** 計画・下書き・途中報告を依頼の完了にしない。必要な検証で問題を見つけたら、承認範囲の通常修正を行う。保存を依頼されたなら保存先、動作を依頼されたなら該当動作、外部結果が必要ならその結果まで確認する。GitHubでは対象・ref・内容をRemoteから再取得する。成果が十分に確かめられた後、判断を変えない追加検査を繰り返さない。

**途中で盤面が変わったら戻す。** 期待とActualの差を読み、目的を満たす許可済みの代案があれば進める。新しい対象・公開先・責任・影響へ広がる場合は、その差分の判断を求める。Human STOPやPlan-only、必要な権限・アクセス不足は影響する操作を止める理由であり、締切はその迂回権限にならない。

中断やTool結果不明の後は、再実行前に実際の状態を確認し、成功済み部分と残作業を分ける。待機・変化なし・回復可能な失敗だけで、実行できる仕事を終了しない。元の締切を過ぎても、未達の報告と残作業の扱いを明らかにする。承認と継続意図が有効なら必要な結果確認を続け、過ぎた事実を消さない。

## 4. Output Modeは一列の品質階段ではない

旧版の「Paid → Free → Prototype → Internal Harvest → Failure Report」という段階表現は、成熟度・価格・公開範囲・報告目的を混ぜていた。現在は、必要な違いを分けて判断する。

| 見る違い | 判断すること |
|---|---|
| 成果と成熟度 | 完成品、試作、部分成果など、何ができて何ができないか |
| 検証状態 | 何を確認し、何が未検証・Unknownか。試作と検証済みは同じ意味ではない |
| 受け手・用途 | 本人、共同作業者、顧客等が、どの用途で使ってよいか |
| 保存・公開・提供 | 内部保存、限定共有、一般公開、納品のどこまで承認され実施されたか |
| 価格・約束 | Paid / Freeの選択、対価に対する約束、外部Commitmentを守れるか |

有料・無料は品質の上下ではない。無料公開にも正確性・安全・公開権限が必要であり、有料の試作品も、その実態と約束が適切に伝わり承認されているかで判断する。「試作」と書くだけで危険な提供や未検証の主張が正当化されることもない。

公開できる品質に達していなければ、内部で学びを残す選択はあり得る。ただし、内部保存が依頼された公開・納品を達成したことにはならない。成果種別や受け手・約束を変える代案は、その変更の意味と必要な承認を明確にする。

## 5. 成果の完了と、学習・報告の完了を分ける

締切には、実際に到達した状態を誠実に確定する。失敗を隠さず記録できることと、元のTaskを達成したことは別である。

- **成果の状態:** 合意したOutcomeを満たしたか。未達なら何が残り、何が使えるか。
- **学習・報告の状態:** 期待とActual、根拠、詰まった条件、修正案、次に確かめることが整理されたか。

Failure ReportやInternal Harvestだけを作っても、もともとの成果が完成したことにはならない。調査報告自体が最初から依頼されたOutcomeだった場合は、その報告の完了条件で判断する。HumanがOutcomeを変更した場合は、旧Outcomeの未達と、新Outcomeへの変更を記録する。

記録では、Humanの報告・Toolで直接確認した事実・AIの因果仮説・未確認を混ぜない。「締切を厳しくしたから成功した」は、比較や根拠がなければ仮説である。次回の確認は具体的な不確かさに結びつけ、毎回新しい実験・定期予定を作る義務にしない。

失敗はBottleneckを知る材料になるが、Humanの全面的失敗、意志力不足、信仰不足へ拡大しない。好結果もGuard違反の免罪符にはならない。

## 6. 適用例と、その境界

### 小さな具体試行と、ゆっくり進む戦略

大きな基盤移行を慎重に育てることと、承認された小さな試行に締切を置くことは両立する。たとえばDots＋Workへの長期的な移行を急いで完成させず、その一部として「選んだ一つの作業の引継ぎが成立するか」を限定して確かめる案は考えられる。

この場合、試行の成果は、準備資料の存在だけでなく、実際に受け取る側が目的・残作業・権限を復元できた証拠で判断する。期間・対象・必要な承認は現在の依頼から選ぶ。これは方法の例であり、この本文を読んだだけで試行、Session移行、Repository routing変更を開始しない。移行が承認された時は、その対象に適用される[共有移行契約](ai-next-thread-handoff.md)へ接続する。

### 締切内に記事を公開する依頼

締切と公開先が承認されているなら、主張の根拠・読者への約束を守り、余分な節や装飾を削って記事を完成・確認・公開する。検証に重大な穴が残るなら、無料公開へ切り替えて押し出さず、その主張を外しても依頼の価値が成立するか判断する。成立しなければ未達と変更案を示す。失敗報告を公開記事の代わりに作って「公開完了」とは言わない。

### 締切のない相談

「この大きな構想をどう進める？」だけなら、まず目的と現在の障害から考える。締切で絞ることが有効なら限定試行を提案できるが、「7日以内」「毎週必ず」を既定の約束にしない。計画だけと指定されていれば、実行可能な計画を返して止まる。
