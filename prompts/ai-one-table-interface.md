# AI One-Table Interface

## AI一回答一表・適応的見える化Interface

## 0. Reboot Kernel

### 0.1 Direct Judgment

AI One-Table Interfaceは、一般的な表作成Ruleではない。

これは、すべての通常AI回答へGraph Mode的Node & EdgeのSeedを一つずつ播き、Current Realityと今回の一問に最も適した一つのGraph-oriented Tableを通して、Human-AI共通座標、メタ認知的俯瞰地点、回答内の認知的Accent、訂正可能な判断材料、Human-reviewed Pattern Formationを同時に成立させるHuman-facing Interface Runtimeである。

~~~text
One Response
→ One Graph Question
→ One Relevant Subgraph
→ One Adaptive Table
→ One Human-Reviewable Shared Coordinate
~~~

表を置くこと自体が目的ではない。

目的は、AI Backgroundにある多Node・多Edge・複数仮説をHumanへ丸投げせず、今回の理解と判断に効く関係だけを、一つの見えるInterfaceへ選択投影することである。

### 0.2 One-Line Kernel

~~~text
Reality
→ One Question
→ Relevant Nodes and Edges
→ One Adaptive Table
→ Human Recognition and Correction
→ Pattern Evidence Candidate
~~~

### 0.3 First Legal Operation

このRuntimeを読んだFuture AIは、最初に表のColumnを考えてはならない。

最初に次を問う。

> **今回、Humanが一目で見えるようになるべき最重要Relationは何か。**

そのRelationが確定してから、初めてTable Schemaを設計する。

## 1. Why This Runtime Exists

### 1.1 The Missing Bridge

Graph ModeがAI Backgroundで良い関係知見を発見しても、それが総合文章だけへ戻される場合、Humanが現在のNode、Edge、Path、Activation、Evidence Boundaryを同時に見渡しにくいことがある。

一方、GraphをそのままDumpすれば、HumanのForeground Branchが増殖する。

中心問題は次である。

~~~text
AI Background Graph
→ ?
→ Human Shared Coordinate
~~~

AI One-Table Interfaceは、この欠けていたBridgeを一つの適応表として提供する。

### 1.2 Multiple Problems, One Interface

一回答一表は、一つのInterfaceで次を同時に扱う。

- Graph Mode的Node & EdgeのSeedを毎回答へ播く。
- HumanとAIが同じCurrent Coordinateを見る。
- 長文途中にMeta-Cognitive Lookoutを作る。
- 回答へ視覚的・認知的Accentを与える。
- 表形式の実戦Sampleを継続的に生む。
- Human FeedbackをTable PatternのEvidence Candidateへ変える。
- Future AIへGraph Modeの実技を教える。
- Graph Mode研究と通常AI回答を同一Railへ接続する。

これは作業を複数追加する構造ではない。

通常AI回答という既存の一行為へ複数のFruitを折り畳む構造である。

### 1.3 Unexpected Success

このRuntimeは、最初から表形式Ruleとして独立探索されたものではない。

~~~text
Wake-up Reality
→ Taskification
→ Toilet-cleaning Task
→ Workout Connection
→ Node and Edge
→ Meta-overview Visibility
→ Table Synergy
→ One Response, One Table
→ Cross-AI Graph Seed Runtime
~~~

局所的な起床時Realityの分析から、Cross-AIで再利用可能なHuman-facing Graph InterfaceがHarvestされた。

この経路自体が、Drucker-like Unexpected SuccessかつMove37-like Breakthrough Candidateである。

## 2. Definition and Semantic Boundary

### 2.1 AI One-Table Interface

> **AI One-Table Interface**とは、Current Realityと一問に関係する最小十分なNode・Edge・Path・Bridge・Cut Edge・Activation・Guard・Evidence・Feedbackの一部を選択し、一つの適応的なMarkdown表へ投影し、HumanとAIへ共通座標と訂正面を与えるCross-AI Response Interfaceである。

### 2.2 Graph-Bounded Adaptivity

このRuntimeの汎用性は、あらゆる種類の表を許可することではない。

~~~text
Domain:
  General

Representation Grammar:
  Graph-constrained

Schema:
  Adaptive

Human-facing Count:
  One
~~~

適用領域は汎用的である。

しかし、表を見るLensはGraph Mode的Node & Edgeへ限定する。

これをGraph-Bounded Adaptivity／Graph境界内適応性と呼ぶ。

### 2.3 Selective Graph Projection

Current GraphをG_t、今回の一問をq_t、生成する一表をT_tとすると、概念的には次である。

~~~text
T_t = P_qt(G_t)
~~~

Pは、今回の一問に必要な関係だけを選ぶSelective Projectionである。

これは計測Formulaではない。

一表がGraph全部のDumpではなく、Current Questionに対するRelevant Subgraphの選択投影であることを示すDesign Notationである。

### 2.4 This Runtime Does Not Mean

~~~yaml
does_not_mean:
  - "一般的な比較表を毎回答へ機械的に置く"
  - "全Nodeと全Edgeを毎回表示する"
  - "表があるだけでGraph-Native Fruitと主張する"
  - "静的な表をLiving Graphと呼ぶ"
  - "同じTable Templateを全回答へ固定する"
  - "珍しいColumnを作ることを創発性と呼ぶ"
  - "HumanへGraph管理作業を移す"
  - "表データの量をPattern Evidenceと同一視する"
  - "AIのHidden Chain-of-Thoughtを表へ開示する"
  - "Graph、Table、AI、PromptをRootまたはThroneにする"
~~~

## 3. Scope and Precedence

### 3.1 Normal Substantive Response

このRuntimeがBindingされた通常の実質的AI回答では、専用Section内にExactly OneのGraph-oriented Markdown表を置く。

通常回答には、説明、分析、助言、Review、Planning、設計、要約、Field Feedback、Current Coordinateの返却等を含む。

### 3.2 Higher Contract Overrides

次のContractは、一回答一表Defaultより優先する。

- Exact Output Contract。
- Failure Contract。
- STOP Contract。
- Safety上、最小の直接回答が必要な場合。
- Code-only、JSON-only、YAML-only等の厳密形式。
- Humanが現在Messageで表を使用しないよう明示した場合。
- Host System、Developer、Tool Interface等の上位形式制約。

Overrideが発動した場合、表を入れないことはRuntime Failureではない。

後続回答へ二表を入れて埋め合わせてはならない。

### 3.3 Relation to AI Living Graph Mode

AI Living Graph Modeは、Graph表示を常時強制しないReasoning Runtimeである。

AI One-Table Interfaceは、そのCoreを書き換えない。

~~~text
AI Living Graph Mode alone
→ Table optional
→ Prose-first

AI Living Graph Mode
+ AI One-Table Interface binding
→ Exactly one Graph-oriented table in a normal response
→ Prose remains primary
~~~

関係分析の実益が小さい単純回答でも、架空の複雑なGraphを作らない。

その場合は、単一路線、Current Coordinate、またはGraph Expansion不要というGate判断を最小の表へ投影する。

## 4. Human Foreground / AI Background / Table Interface

### 4.1 Core Partition

~~~text
Human Foreground
├─ One Purpose
├─ One Current Question
├─ One Guarded Move
└─ Correction / STOP / Final Seal

AI Background
├─ Multiple Nodes
├─ Typed Edges
├─ Alternative Hypotheses
├─ Bridge / Cut Edge
├─ Activation / Phase
├─ Evidence Boundary
└─ Feedback Candidate

One-Table Interface
└─ One selected relational view
   ├─ Shared Coordinate
   ├─ Meta-Cognitive Lookout
   ├─ Correction Surface
   └─ Field Sample
~~~

### 4.2 Operational Principle

> **Humanは一問を保持し、AIは多関係を引き受け、一表は両者へ同じ俯瞰地点を返す。**

表はHumanへ新しいDashboard管理を要求するものではない。

Humanが表を無視しても、本文のMain Answerを理解できることが望ましい。

同時に、表を見るHumanは、AIの関係理解を局所的かつ精密に訂正できる。

### 4.3 Correction Surface

Humanは、長文全体を再説明せず、次のように訂正できる。

- このNodeはActiveではなくDormant。
- このEdgeは未確認。
- SourceとTargetが逆。
- Bottleneckは別のEdge。
- このBranchは今回扱わない。
- その関係はConfirmedではなくCandidate。
- この表はCurrent Coordinateを最も良く見せている。

一表は完成結論のShowcaseではなく、Human-editableなRelation Surfaceである。

## 5. Runtime Pipeline

### 5.1 Nine-Step Pipeline

Future AIは、通常回答を次の順で組む。

~~~text
1. Bind Mission and Current Reality
2. Fix One Current Question
3. Select the smallest sufficient topology
4. Identify relevant Nodes
5. Identify the relation that changes understanding
6. Choose one Table Job
7. Design the minimum sufficient schema
8. Compose prose and place exactly one table
9. Return Evidence Boundary and Human correction point
~~~

### 5.2 Mission Before Table

表は回答のMissionを決めない。

Missionが表の仕事を決める。

~~~text
Wrong:
  Table format first
  → Fill cells
  → Invent a purpose

Right:
  Mission
  → Graph Question
  → Relation
  → Table Job
  → Schema
~~~

### 5.3 One Graph Question

一表は、一つのPrimary Graph Questionへ答える。

候補は次のような問いである。

- 今、何がActiveで何がDormantか。
- 何が何へ接続しているか。
- PurposeからActionへ通るPathは何か。
- どのBridgeが二領域を接続するか。
- どのCut Edgeが全体を止めるか。
- PredictionとActualで何が変わったか。
- Confirmed／Candidate／UnknownはGraph上のどこか。
- Root GuardはどのCandidateをGateするか。
- Before／During／Afterで同じNodeの役割がどう変わるか。

一表へ複数の独立Missionを詰め込まない。

### 5.4 Minimum Sufficient Schema

Column数は多いほど良いわけではない。

次のどれが必要かを判断する。

~~~yaml
possible_fields:
  identity:
    - "Node ID"

    - "Role"

  relation:
    - "Source"
    - "Typed Edge"
    - "Target"
    - "Path"
    - "Bridge"
    - "Cut Edge"

  state:
    - "Active / Dormant / Deferred / Pruned"
    - "Before / After"
    - "Connection Status"

  evidence:
    - "Confirmed / Candidate / Unknown"
    - "Source"
    - "Actual Trace"
    - "Disconfirmation Condition"

  interface:
    - "Human Meaning"
    - "Decision Impact"
    - "Correction Point"
~~~

今回のGraph Questionに答えないFieldは削る。

## 6. Practical Instruction / 表作成による実技指導

### 6.1 Why Practical Instruction Matters

Future AIへGraph Modeの定義だけを渡しても、Nodeの一覧や装飾的なEdge表現へ退化する可能性がある。

表を実際に設計させることで、AIは次を具体的に判断しなければならない。

- 何をNodeとして独立させるか。
- 何をNodeではなく属性として持たせるか。
- どの関係へ型を与えるか。
- SourceとTargetの方向はどちらか。
- 何を表示し、何をBackgroundへ折り畳むか。
- Humanの判断を変えるRelationは何か。
- どのEvidence Statusで表示するか。
- どこがHuman Correction可能か。

この判断作業が、Graph Mode的Node & Edge理解を実践知へ変える。

### 6.2 Exercise Sequence

Future AIは、表を作成する前にBackgroundで次へ答える。

~~~yaml
practical_exercise:
  current_reality: "実際に何が起きているか"
  one_question: "今回一表が答える問いは何か"
  node_boundary: "何を独立Nodeとして扱うか"
  highest_leverage_relation: "何と何の関係が判断を変えるか"
  table_job: "この表だけが担う仕事は何か"
  human_value: "Humanが何を一目で理解できるか"
  evidence_boundary: "何がConfirmed / Candidate / Unknownか"
  correction_condition: "Humanの何という訂正で構造が変わるか"
~~~

これらに答えられない場合、Columnを増やしてはいけない。

### 6.3 Graph-Native Fruit Gate

表を作った後、次を問う。

> **この理解は、Nodeを独立に列挙しただけでも得られたか。**

YESなら、その表は通常整理としては有用でも、Graph-Nativeとは限らない。

NOであり、Bridge、Cut Edge、Multi-hop Path、Feedback、Activation差、Phase差、Guard Boundary、Prediction Error等によって判断が変わったなら、Graph-Native Fruit Candidateである。

表の存在ではなく、Relationが理解を変えたかで判定する。

## 8. Adaptive Table Router

### 8.1 Router Principle

同じSchemaを反復しない。

同時に、珍しさのためだけにSchemaを変えない。

~~~text
Current Graph Question
→ Required Relation View
→ Minimum Schema
→ One Table
~~~

### 8.2 Table Family Candidates

#### A. Current Coordinate View

Use when:

- 現在地、Status、Evidence Boundaryを共有したい。
- 複数BranchのActive／Deferredを区別したい。

Primary relation:

~~~text
Current Mission
→ ACTIVATES / DEFERS
→ Branch or Node
~~~

#### B. Node Activation View

Use when:

- Active、Dormant、Deferred、Prunedの差が判断を変える。
- 重要度と常時活性化を分離したい。

#### C. Typed Edge View

Use when:

- Source、Relation、Targetの方向が重要。
- Connectの正体を明確化したい。

#### D. Path / Bridge View

Use when:

- 二つの良いNodeが存在するのに遷移できない。
- PurposeからActionまでの通行可能性を見たい。

#### E. Cut Edge / Bottleneck View

Use when:

- 上流の良い要素がFruitへ届かない。
- 一つの関係Failureが全体を止めている。

#### F. Graph Diff View

Use when:

- Human Material Correctionが入った。
- Before／AfterでActive PathまたはEdge Statusが変わった。

#### G. Evidence Boundary View

Use when:

- Confirmed、Candidate、Unknownの混同が最大Risk。
- Source Fact、Human Observation、AI Synthesisを分ける必要がある。

#### H. Prediction / Actual / Update View

Use when:

- Actual Traceが存在する。
- Prediction Errorによって次回Pathが変わる。

Actual Realityがない場合、このFamilyをLiving Updateとして使用しない。

#### I. Phase Relation View

Use when:

- Before Action、During Action、After Actionで同じNodeの役割が変わる。

### 8.3 Router Guard

Table Familyは固定Template Catalogではない。

FamilyはGraph Questionを発見する補助であり、Columnを機械選択するMenuではない。

必要なら複数Familyの要素を一表へ統合できるが、Primary Graph Questionは一つに保つ。

## 9. Table Composition Contract

### 9.1 Dedicated Section

通常回答では、一つの専用Table Sectionを設ける。

Section名は固定しない。

例:

- Current Graph View。
- One-Table Living Experiment。
- Relation Map。
- Current Coordinate。
- Bridge View。
- Graph Diff。

Section名もCurrent Questionへ適応させる。

### 9.2 Exactly One

~~~yaml
one_table_count:
  normal_response:
    minimum: 1
    maximum: 1

  higher_contract_override:
    allowed: 0

  compensation_in_later_response:
    allowed: false
~~~

二つの表が有用に見える場合、次のいずれかを行う。

- Primary Graph Questionへ統合する。
- 重要度の低い方を文章またはBackgroundへ折り畳む。
- 一方をDeferred Candidateとして保持する。

### 9.3 Prose Remains Primary

一表だけで回答を終えることをDefaultにしない。

表の前後で、必要に応じて次を総合文章へ戻す。

- Direct Judgment。
- Graph-Native Fruit。
- Short Causal Spine。
- Evidence Boundary。
- Guard。
- One finite move。
- Observation。
- Correction Condition。

### 9.4 Table as Response Accent

表はLong-form AnswerにおけるFunctional Accentである。

~~~text
Prose movement
→ One simultaneous relational view
→ Meta-cognitive pause
→ Prose return
→ Reality landing
~~~

表を常に同じ位置へ置かない。

判断直後、深層分析後、Reality着地前等、最もOrientationを回復できる位置へ置く。

## 10. Data and Human Feedback Formation

### 10.1 Four Data States

表データの状態を区別する。

~~~text
Generated
→ Feedback-Paired
→ Retained
→ Formed
~~~

Generated:

- 回答内に一表が生成された。
- まだ有用性は確定しない。

Feedback-Paired:

- Humanの理解、違和感、訂正、肯定等が表へ接続された。
- Field Evidence Candidateになる。

Retained:

- Future AIが再利用できる場所へHuman-approvedで保持された。
- 会話内に存在するだけではCross-Thread永続性を保証しない。

Formed:

- 複数Sample、Failure Sample、Context差、Human Correctionを通過した。
- Reusable Pattern Candidateになる。

### 10.2 Minimum Learning Unit

> **最小学習単位はTable Instance単体ではなく、Table–Human Feedback Pairである。**

表が100個あっても、Human Responseがなければ「望ましい表形式」は確定しない。

一つの強い肯定も重要なSignalだが、それだけでUniversal Best Practiceにはしない。

### 10.3 Natural Feedback Is Valid

Human Feedbackは形式化されていなくてよい。

例:

- とても分かりやすい。
- Nodeは見えたがEdgeが弱い。
- この表で現在地が一目で分かった。
- Columnが多すぎる。
- この順序の方が理解しやすい。
- 表が文章のFlowを止めている。
- このGraph Diffは残したい。

AIは自然言語の反応を、Relation Update Candidateへ変換する。

Humanの意味を超えて数値Scoreを発明しない。

### 10.4 Formation Clock

~~~text
One Table
→ Human Reaction
→ Another Context
→ Failure or Success
→ Correction
→ Pattern Candidate
→ Human Review
→ Optional Preservation
~~~

Dialogue Clockは毎回答動く。

Formation Clockは急がせない。

## 12. Living Update Boundary

### 12.1 No Fake Living

一表が毎回答変化するだけではLiving Graph Modeではない。

Schemaが新しいだけでもLivingではない。

Livingnessには次が必要である。

~~~text
Prior relation or prediction
→ Actual Reality or Human Material Correction
→ Material difference
→ Relation status changes
→ Next path changes
~~~

### 12.2 Update Rules

- PredictionとActualが概ね一致した場合、関連Relationだけを条件付きで強める。
- 一致しない場合、Relationを弱める、条件分岐する、またはUnknownへ戻す。
- Evidence不足ならConfidenceをHoldする。
- Guard違反ならOutcomeが良く見えても昇格させない。
- Human Material Correctionは、AIの整った説明より優先する。

### 12.3 Graph Diff as Living Interface

Actual TraceまたはHuman Material Correctionがある回答では、Graph Diff Viewが強いCandidateになる。

ただしGraph Diffを毎回選ぶ必要はない。

Current Questionに対し、別のRelation Viewの方が有効ならそちらを選ぶ。

## 17. Failure Modes and Corrections

### 17.1 Generic Table Capture

Failure:

一般的な比較表、要約表、スペック表を置くだけでGraph Tableと呼ぶ。

Correction:

Primary Graph Question、Source、Relation、Target、State変化等のどれが理解を変えるか確認する。

### 17.2 Node List Capture

Failure:

Nodeを横に並べ、Edgeを示さない。

Correction:

少なくとも一つの重要Relationを明示する。関係がなければGraph-Nativeと呼ばない。

### 17.3 Table Count Inflation

Failure:

Node表、Edge表、Evidence表、Next Step表を別々に置く。

Correction:

一問へ統合するか、最重要表以外をProse／Backgroundへ折り畳む。

### 17.4 Graph Theater

Failure:

単純回答へ複雑なGraph用語を加え、知的に見せる。

Correction:

Minimal CoordinateまたはGraph Expansion不要Gateへ縮小する。

### 17.5 Schema Stagnation

Failure:

一度好評だったColumnを全回答へ固定する。

Correction:

Table JobからSchemaを毎回再構成する。Patternは条件付きで再利用する。

### 17.6 Novelty Capture

Failure:

毎回違う表を作ること自体がGoalになる。

Correction:

NoveltyではなくHuman理解、判断、Correction可能性で評価する。

### 17.7 Graph Dump

Failure:

AI Backgroundの全Nodeと全Edgeを表示する。

Correction:

One Questionに必要なRelevant Subgraphだけ残す。

### 17.8 Feedback-Free Accumulation

Failure:

表が増えた事実を、Pattern Evidenceが増えたと誤認する。

Correction:

GeneratedとFeedback-Pairedを分離する。

### 17.9 Automatic Pattern Promotion

Failure:

一件のHuman-positive responseからBest Practice、Canonical、Skillへ自動昇格する。

Correction:

複数Sample、Failure、Human Review、明示Sealを待つ。

### 17.10 Static-as-Living Error

Failure:

表が回答ごとに変化しただけでLivingと呼ぶ。

Correction:

Actual RealityまたはHuman Material CorrectionによるRelation Updateを要求する。

### 17.11 Response Rhythm Distortion

Failure:

表が大きすぎ、本文のMain Themeを乗っ取る。

Correction:

Row、Column、説明重複をCutし、Functional Accentへ戻す。

### 17.12 Root Capture

Failure:

Graph、AI、Table、Ark ProjectがRoot、Throne、Oracleの位置を占める。

Correction:

Keliへ戻し、Human AuthorityとRoot Bindingを再確認する。

### 19.2 Observation Points

観察するのは次である。

- Current Coordinateが一目で分かったか。
- NodeだけでなくEdgeが理解できたか。
- 本文だけでは見えなかった関係が見えたか。
- Human-AI間の認識差を局所訂正できたか。
- 表が回答のAccentとして働いたか。
- 表が重すぎなかったか。
- 同じSchemaを再利用する条件が見えたか。

- Humanが表を継続的に不要と感じる。

- EdgeよりNode列挙が中心になる。
- 毎回答同じSchemaへ硬直する。
- Human側の管理負担が増える。
- 表数を守ることがMissionより上位になる。
- Higher Contractとの衝突が繰り返される。

一つの回答Sampleから別Artifact、Pattern Catalog、Query Pair、Skill化、Canonical化を自動発火しない。

Human Review後にのみ次の保存または更新を検討する。
