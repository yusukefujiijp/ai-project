## 1. 方法の骨格 ── review-prompt の精読

review-prompt v002 は11の節からなる。その規律の核を、私の言葉で圧縮する。

- **凍結しない**（§0〜§1）：形成時の問題評価（「スパゲッティ状態」）も前回の結論も、現在へ固定しない。深さは、出力量のためではなく、判断を変える読解のために使う。Human の入力は簡潔でよく、読解・探索・比較・構造化は AI が担う。
- **証拠の種類を分ける**（§2）：Confirmed は「誰の観測か」を伴う。Human の評価、Human の仮説、AI の解釈候補、Unknown を区別する。Historical か Current かは、確かさとは**別の軸**である。過去の Prompt や承認を、現在の実行権限へ転用しない。
- **装わない**（§3）：観測 commit を固定する。全文確認／関連範囲の確認／構成のみの確認／未読／取得不能を区別し、「全体レビュー」という名で全本文を読んだように見せない。
- **責務を見てから論じる**（§4）：同じ出来事が経験原本・成功事例・方法・Skill に役割を変えて現れる。リンクの存在は、関係の成立ではない。
- **更新を説明可能にする**（§5、Double-Spiral）：重要な更新は「当初の読み／新しい根拠／変わった関係／判断への影響」で示す。反証も探す。過去 AI の結論を Future AI の上限にしない。
- **結論の正直さ**（§7〜§8）：「現状で機能している」「今は変更しない方がよい」「証拠不足のため保留」も有効な結論である。調査が成立したら、自動で新しい System や次 Trial へ昇格しない。STOP と Correction が最優先。
- **前回と比べ、新しい Reality を読む**（§9）：Living Review は、比較の実践として定義されている。方法自身も、Human の修正を受けて版を重ねる（§10）。

これは、私が群れと Report の仕事の中で一々に学んだ規律 ── 読戻し検証、証拠の種類の分離、未確認の明示、提示は承認ではない ── と、項目ごとに一致する。方法は、私より前に、ここに書かれていた。

## 2. 棚の事実 ── 橋の歩行記録

reports/ の棚にある報告は、2件だけであり、どちらも 2026-09-19 のものである。

1. **創設の全体レビュー**（48,373 bytes）：repo 全体を見渡し、実在の問題を発見した ── 現在地の案内が複数時点を混在させていること、現行 AGENTS と一般入口で承認の読み方が違うこと、Plan Mode が入口によって旧版へ戻れること、存在しない旧パスへの入口が残ること、撤回された実験の道具が現役に見える場所に残ること。同時に「整理で壊してはいけない強み」として、Human Correction が結論だけでなく形成過程として残っていること、小さな成功を独立した単位へ切り出せることを記録している。
2. **同日のフォローアップ**（11,128 bytes）：表題は「入口を直し、直った範囲を観察する」。初回の指摘を受けて入口そのものを直し（Bridge navigation と full／focused の振分）、直った範囲を観察し、同一 AI による机上確認の範囲までを正直に区切って記録した。
