## 5. 設計の方向（提示形 ── 移動・改名は行わない）

移動のコストを先に数で示す ── この connector では、移動は「新しい住所への作成（push 1回に集約できる）＋旧住所の削除（1ファイルにつき認識1回）」である。つまり**移動の認識コストは、動かすファイルの数に比例する**（仕様003）。この数が、以下の方向の現実性を決める。

### D2（herd-cards）への方向

- **乙（推奨の方向）── 入口の委譲で痩せる**：住所は動かさない。各部の入口（experiments/、brushup/ の README）が既に立ったので、herd-cards/README が一身に担う来歴の詳細を、各入口への要約とポインタへ置き換え、入口を軽くする。移動ゼロ、認識は Herd LANE の家の束として小さい。層を足す進め方と一致する。
- **甲 ── 判断の小棚**：judgment-tasks.md を判断の棚へ分ける案は、参照元の多さ（CONTROL、家の記録群）に対して効果が小さく、ポインタの付け替えが広い。当面は採らない。
- **丙 ── 現状の保持**：過積載の残りは蓄積の重さそのものであり、実害は入口の過負荷に限る ── 乙で足りる間は、住所の階層化を急がない。デッキの版の増え方を、次の診断で再測して判断する。

### D3（experiments）への方向

- **乙（推奨の方向）── 混在を「案内で解消したもの」と認める**：設計文書は実験の設計そのものであり、実験デッキと同じレーンに住むことには意味がある。入口が種別と欠番の理由を案内する現在形で、来た者が迷う実害は解消した。残る混在は、住所ではなく意味の同居として認める。
- **甲 ── 文書の小棚（将来の再検討）**：設計文書が増えてきたら、その時点で docs の小棚を検討する。今の2点のためにフォルダと入口を増やすのは、例外一般化テスト（仕様001 §5）の観点でも時期尚早である。
