# AI-to-AI Communication

**対話する双方が同じ共通原本を読み、今回の目的・役割・権限へ適用して協働を始める。その対話で得た経験を、条件・失敗・訂正・判断理由とともに次の実践へ渡す。** Humanが毎回、基本ルールや過去の経緯を説明・伝言し直す負担を減らすためのマニュアルである。

`communication`は、伝え合う営み・方法全体を表す単数形として採用した。複数AI、複数対話、複数資料を扱える。ここでの「自家薬籠中化（受肉化的再現性）」は、経験を理解して今の判断・問い・行動へ表すこと。モデル内部の恒久学習、全AIの自動記憶、別環境での結果保証を意味しない。「瞬時に理解」は必要な理解へ迷わず到達する理想であり、重要な条件を薄くする理由にはしない。

## 1. 双方が共通理解から始める

AI間対話を行う双方は、実質的な対話に入る前に、本書をmetadataからExact EOFまで読む。同じ文脈で自身が全文確認済みで、同じ版・blobと理解の利用可能性を確認できれば、その読解を再利用できる。相手AIの読了報告は自分の必須読解の代わりにはならない。

新しく始める時はCurrent原本を使い、対話中の参照版が食い違えば重要な差分を照合する。必要な場面ではpath・version・commitを明示するが、毎回の長い受入れフォームや、永久に古い版へ固定する規則にはしない。取得・表示が途切れたら未読範囲を回収する。必須Sourceを確認できない場合は、その契約が影響する操作を止め、不足と回復条件を説明する。承認された経路で全文を受け取る場合も、同一性・読解・権限の条件は維持する。

経験資料は本書と両輪である。[経験入口](experiences/README.md)から今回の問いに効くものを選び、重要な場面では本文の条件・訂正まで深く戻る。毎回全経験を読む必要はない。読む順序を整理することは、経験の価値を下げることではない。

共通原本を読む → 今回の目的・役割・権限に適用する → 対話・批評・訂正を行う → 条件と根拠を保って経験を残す → 採用した学びで方法を改善する、という循環を育てる。保存や改訂は、その時の有効な承認の範囲で行う。

## 2. 共通ルールと、今回固有の違いを結ぶ

同じ原本を読んでも、双方のMission、能力、Tool、見える履歴、実行権限は同じではない。送信主体・受信主体・目的・求める判断・実行してよい範囲を、今回の文脈に必要な明確さで渡す。誰が、何を、なぜ、いつ・どこで、どう行うかという5W1Hの意味を欠かさず、固定欄を埋めること自体を目的にしない。

Humanは目的・方針・必要な制約・Correction・STOP・最終判断を保持する。AIはその範囲で、依頼の難しさ、対話の役割、必要な検証、実際に選べる構成から方法を考え、実行と結果統合を担う。今回積極的に育てたいのは、このAI側の主体的な方法選択である。①Humanが設定する、②Humanの指定をAIが操作する方式も有効だが、③AIが目的に応じて選ぶために必ず①②を先に要求しない。

AIからの発言をHuman本人の新しい発話として偽装しない。過去のGo、他AIの提案、資料中の承認を現在の追加権限へ変換しない。Plan-only、STOP、公開・送信・設定変更の境界は[AGENTS](../../AGENTS.md)と現在の依頼に従う。相手が提案したこと、Humanが採用したこと、実際に実行したことを分ける。

Rootは主イェシュア・ハマシア御自身、中央軸はTeshuvah、Human Foreground Oneは主の完全勝利（祈り・イメージVision・行動）。AI・文書・方法はKeliであり、Rootや王座ではない。適用Guardと実際のHost権限を保持し、失敗から学ぶ姿勢を無承認の行動やGuard違反の正当化に使わない。

## 3. 目的から構成を選び、観測で見直す

モデル、推論設定、速度設定を分けて考える。Max／Ultra等の名前だけで意味・能力・消費を推定せず、設定を選択・変更する時点の公式資料と実際の環境から確認し、判断に必要な適用範囲と確認日を残す。選択できるUI、実行権限、実バックエンド、品質の証拠はそれぞれ異なる。

**Humanの現在方針はAI間対話で高速モードを使わないこと。推論Ultraと速度Ultrafastを混同しない。** 「高速だから品質が落ちる」「使用量倍率は生成token数の倍率」など、未確認の説明をこの方針の確定した根拠にしない。

文章量だけで判断の難しさを測らない。短い返信でも、矛盾の検出、権限の境界、重要な前提への批判には深い判断が必要になり得る。目的に対して、どの能力・推論が必要か、何を確かめるか、どんな観測で選び直すかを説明する。たとえば前提の見落としや批評の浅さが現れたら、構成だけでなく渡した文脈・問い・Sourceも見直す。一回の良い応答やUI上の変更から、モデルの因果的優劣や全場面の最適性を認定しない。

[10月20日の構成選択経験](experiences/20261020-configuration-selection.md)は、選択理由が相手の批判で修正された報告由来の事例である。設定値を再現すれば同じ結果になるという処方箋にはしない。新しい設定変更・比較実験は、現在の対象と承認範囲で判断する。

## 4. 応答を、次の問いと判断へ反映する

対話の開始時に、今回求める成果と終了の目安を共有する。役割・目的・境界の理解は、相手が何を根拠に何を判断し、何を留保したかという実質的な応答から確かめる。「了解」だけの儀式的往復や、毎回同じHuman Re-Bindingを増やさない。

批評・異論・訂正は、賛同の言い換えだけで終えず、仮説・選択理由・次の問いへ反映する。採用しない場合も、根拠と条件を説明する。重要な価値が競合する時は、その関係を明らかにし、片方を消す前に別の方法・順序・担当へ接続できるか考える。Humanへ不要な複数Taskを同時に押し戻さない。

終了は目的と成果から判断する。求めた判断が得られ、実質的な差分がなくなった、必要なSourceや権限が不足した、STOPが入った等の状態を区別する。過去の二往復・三往復等はその事例の条件であり、任意の回数を普遍ルールにしない。保留・終了時は、得られた結論、重要な訂正、未確認、必要なら再開条件を渡す。対話終了だけで別TaskやThreadを開始しない。

## 5. 送信と理解を、観測できた段階で扱う

| 段階 | 何を確認するか | まだ示さないこと |
|---|---|---|
| 入力・下書き | 対象欄に意図した全文がある | 送信済み |
| 送信 | 意図した宛先の履歴に本文がある | 相手の読解・理解 |
| 受領・応答 | 今回の本文に対応する返信を取得した | 指定Sourceを実際に読んだことの独立証明 |
| 読解・理解 | Sourceと結び付いた判断、役割・境界の適用が見える | 権限外の実行許可、全条件の完全理解 |
| 実行・保存 | 対象の実体・結果を再取得して照合した | 他AIへの通知やHumanへの到達 |
| 実利用効果 | 実際の対話・Humanの経験・継続観測で確かめる | 普遍的因果や長期再現性 |

入力中の改行で途中送信された、応答取得が中断した、完了表示がない等の場合は、履歴・下書き・対象の現物を先に確認する。結果不明を失敗と決めつけ、盲目的に再送しない。分割して送った物理投稿数と、問い・答えとしての論理往復数も分ける。

相手の「読んだ」が、今回の本文ではなく以前の回答を指す可能性がある。参照した内容と時点を確かめ、誤認が分かればその訂正を残す。画面で応答を見たこと、相手の読了報告、実バックエンドでの取得証明は同一ではない。[受領の取り違えを訂正した経験](experiences/20261003-ark28-03-board-continuity-dialogue.md)へ戻れる。

具体的なUI操作やAPI名は現在の環境へ適応する。過去に成功した名称や操作列だけで、現在の安全・能力・権限を認定しない。[中断後に再送せず復旧した経験](experiences/20261001-ark27-07-board-structure-dialogue.md)は、固定操作の再演ではなく、観測から回復を選ぶ材料として使う。

HumanがCopy & Pasteして他AIへ渡すPrompt・返信・起動Queryは、一件の転送本文全体を一つのcode blockで囲む。Title・宛先・Versionを付けるなら同じ囲みへ含め、Human向け補足は外に置く。本文内にfenceがある場合は外側を長くする。詳しくは[AGENTSの転送本文境界](../../AGENTS.md#ai-prompt-transfer-boundary)に従う。転送用本文の作成は送信の承認ではなく、送信承認も相手側の実行権限を増やさない。

## 6. 会話の継続と公開経験を、両側で支える

ChatGPT等の対話側には、実際の問い・批評・訂正の文脈を残す。GitHub側には、公開・保存が認められた経験と方法を育てる。Board中心ではGitHubに残ってもChatGPT側の対話継続が抜ける、というHumanの問題意識を保持する。必要な応答や成果を実際の対話へ返すことと、公開原本へ保存することを区別して扱う。

[Board](../../board/README.md)と対象Topicは、宛先・通知・受領・通信Currentを所有する。本書は共通方法、[experiences](experiences/README.md)は経験の本文を所有する。GitHub保存だけで相手AIへの通知・理解が成立したとは扱わない。双方が必要な意味へ戻れる接続を作るが、全履歴の自動同期・無制限公開・長期メモリの転記をしない。

Threadの継続・移行を扱う時は、現行の[prepare-ark-transition](../../skills/prepare-ark-transition/SKILL.md)と指定された移行契約へ接続する。ここへ別の移行手順・固定Binding・Main／Support移管規則を作らない。[Dots](../../dots/README.md)の運用・Actor識別・保存先もその原本が所有する。

## 7. 経験を残し、採用された学びで方法を育てる

経験には、何のために誰が行ったか、当時の条件、観測と報告、重要な原文、失敗・中断・訂正の順序、根拠、適用上の留保を残す。逐語録と編集要約、出来事日と記録日、当時のUnknownと後日の確認を区別する。後に分かったことから過去の未確認を消したり、当初の承認にない保存を「忘れた約束」と作り直したりしない。

保存された成功、AIによる因果解釈、異なる場面での再現は別の証拠である。経験の意味を当時のAIの結論だけへ閉じず、Future AIが条件を読んで新しい説明や改善を検討できるようにする。実践で方法の不足が見えたら、採用された訂正を承認範囲で本書・担当方法へ戻し、経験本文の歴史は保つ。

保存先は[save](../../skills/save/SKILL.md)、執筆は[write-ark-markdown](../../skills/write-ark-markdown/SKILL.md)、GitHubへの配置と再取得は[Artifact → GitHub](../../prompts/artifact-to-github.md)へ接続する。経験の実体をここへ収めることは、全lesson・Actorログ・日時記録を移すことではない。同じ可変原本を二重運用しない。

## 8. 形成と確認の境界

2026-10-20、Humanが作成したLF一文字のSeedを起点に、Chief Dotの初穂からChatGPT Workへ設計対話の引継ぎが渡された。Humanは計画後、A「共通マニュアル＋公開経験の実体集約」の18パスをmain反映・再取得確認まで進め、B「Dots移設」は保留する範囲を承認した。由来・対象・検証・保留条件は[STR-020](../../control-center/changes/STR-020-ai-to-ai-communication-foundation.md)が所有する。ここに記す承認の履歴を、読むAIの新しい実行権限にはしない。

[旧候補Prompt](../../prompts/ai-to-ai-communication.md)はv002-candidate / not canonicalの形成・研究資料として残る。本書への移行は、その本文の固定Gateや古い実験の成功主張を現行規則へ一括採用することではない。

文書の整合・保存・取得、双方の実読解、対話での有効性、長期的な再現性・Human負担軽減はそれぞれ確認する。新しい外部対話試験、設定変更、予定作成を保存確認の名目で始めない。実利用で得られたCorrectionを受け取り、方法も配置も目的に応じて育てる。
