# AI活用の日時記録

**AIと何を相談し、調べ、考え、作り、試し、どこまで分かったかを、日付から辿れる場所です。** YusukeJPの生活全体の日記ではありません。ChatGPT、Work、Dots、Claude、Grokなど、利用するAIを限定せず、今回の記録を許可され、GitHubへ保存できるAIが参加できます。読むだけのAIも、ここから仕事の原本へ戻れます。

一行に一つの意味のある活動を、日本語を基本に書きます。大きな成功だけでなく、小さな相談、調査、計画、失敗、回復、訂正も残せます。「何をしたか」と「結果・まだ分からないこと」が伝わることを優先し、会話全文や全Tool操作は転記しません。

## 1. いつ、何を書くか

保存が許可された仕事の一区切り、途中の重要な変化、または `$saveスキル` の依頼時に、AIが記録候補を拾います。Humanに毎回日記を書かせたり、記録項目を入力させたりしません。

- 一つの相談で三案を比べたなら、通常は「比較して何が分かったか」を一行にまとめます
- 調査、実装、確認でそれぞれ独立して役立つ結果があれば、複数行に分けられます。一回答一行や一日一行には固定しません
- 「調べた」「保存した」だけで終えず、対象と結果を書きます。計画提示は計画提示、部分成功は部分成功として残します
- 同じ活動が既に記録されていれば再追加しません。新しい結果や訂正があれば、その差分を残します
- 記録する活動がない日は空ファイルを作りません。未記録を「何もしなかった」と解釈しません

**Plan Mode、会話内だけ、保存禁止、STOPの最中には書き込みません。** 後で保存が承認された場合、その時点で計画や相談の成果も記録できます。一般的な継続委任はその範囲で使いますが、このREADMEを読むだけで新しい保存権限が生まれるわけではありません。

自動とは、許可された範囲でAIが記録判断・記入・確認を担うことです。全AIが起動時に必ず読む、自動で全会話を収集する、時刻どおり常時実行する仕組みを意味しません。SkillのないAIも、このガイドと利用できる保存手段で同じ記録を扱えます。

## 2. 書き方の例

以下はすべて架空の説明例です。実績ファイルへコピーしません。sourcesの会話識別子も説明用で、実在する証拠ではありません。

### 相談と計画を、実行済みにしない

```jsonl
{"schema_version":1,"id":"10000000-0000-4000-8000-000000000001","recorded_at":"2026-10-03T09:00:00Z","recorded_by":"Work / 例示Thread","summary":"共有記録の置き方をHumanと比較し、日別JSONL案を提示した。今回は計画までで、ファイル作成はしていない。後から記録保存のみ承認されたため、この相談を残す。","sources":[{"locator":"example:conversation/planning","supports":"架空例：提案内容と後続の記録保存承認"}]}
```

### 失敗と回復を、必要なら分ける

```jsonl
{"schema_version":1,"id":"10000000-0000-4000-8000-000000000002","recorded_at":"2026-10-03T09:10:00Z","recorded_by":"dot-example","summary":"資料の保存要求後に応答が途切れた。保存の成否はまだ分からず、再送せずに保存先を確認する方針とした。","sources":[{"locator":"example:operation/save-1","supports":"架空例：要求と応答欠落の観測。保存失敗を証明しない"}]}
{"schema_version":1,"id":"10000000-0000-4000-8000-000000000003","recorded_at":"2026-10-03T09:12:00Z","recorded_by":"dot-example","summary":"先ほどの応答欠落を受けて保存先を再取得した。同じIDと本文が存在したため、保存済みと確認し、二重追加せず終了した。","sources":[{"locator":"example:remote/fixed-revision","supports":"架空例：保存済みIDと本文の照合結果"}]}
```

### 細分化し過ぎない／生活を補わない

「検索した」「ページを開いた」「見出しを読んだ」を三行にせず、「二つの資料を比較し、違いと未確認点を説明した」と結果を一行にまとめます。Humanから運動相談を受けた場合は「AIが選択肢を説明した」と書けますが、未報告の運動実施や改善を付け足しません。

## 3. 置き場所と一行の形式

`records/YYYY/MM/YYYY-MM-DD.jsonl` に置きます。日付は **その行を記録した日時のAsia/Tokyo日付**。日を跨いだ作業や後日の復元も記録日へ追加し、過去の活動日へ黙って埋め戻しません。出来事日時が分かれば別に残します。

UTF-8・一行一JSON object・LF区切り・最終行末もLFとします。管理行、配列の外枠、空行、行間カンマ、Markdown fence、EOFはデータファイルに入れません。文字列内の改行は必要なら `\n` にエスケープします。

必須項目は次の六つです。

| 項目 | 意味 |
|---|---|
| schema_version | 整数1。内容の更新回数ではなく形式の版 |
| id | 小文字の標準UUID。一活動の安定ID。同じ保存の再試行では変えない |
| recorded_at | この行の記録を作成したUTC時刻、YYYY-MM-DDTHH:mm:ssZ。公開時刻・出来事時刻と区別する |
| recorded_by | 記録に責任を持つAIの識別。例：dot-0000、Work / Ark27:08。モデル名やGitHub authorから本人を推定しない |
| summary | 対象、行ったこと、結果・未確認が分かる非空の文章。別AIの活動なら誰の実行・報告かも示す |
| sources | 一件以上の根拠。各要素に非空のlocator（所在）とsupports（何を支えるか）を持つ |

`recorded_by` は既に分かる呼称・Thread識別を使い、記録のためだけに新Actorを作りません。不明なら「記録担当AI（安定ID未確認）」など、その限界を明記します。これは本人認証の仕組みではありません。

sourcesは、確認した成果原本・commit・Board返信・会話のメッセージ識別子などへ戻れる形にします。版で意味が変わる資料は固定commit URLを使います。会話IDなど他AIが取得できない根拠は、そのアクセス制約もsupportsに記し、公開URLを作りません。根拠の所在だけで本文を独立に確認済みとは扱いません。

必要な行だけ次を追加できます。

- `occurred_at`：根拠のある出来事UTC時刻。日しか分からない、長い活動で一意に決まらない場合は省略。記録時刻を代入しない
- `task_id`：既存案件の識別子。記録のためだけに新Taskを作らない
- `reconstructed: true`：過去の資料から後で復元した活動。直接観測と混ぜるなら行を分けるか、全体を復元として出所を説明する
- `corrects`：訂正する既存行のUUID。新しいIDの行を追加し、理由・正しい内容・根拠を書く。別日なら対象ファイルもsourcesで示す

後続の正しい結果が加わるだけなら、過去の「当時は未確認」を誤り扱いして訂正しません。真の誤記は訂正行で扱います。過去行を黙って書き換えず、通常追記では既存の行順・本文・未知fieldを保持します。

## 4. 他の記録との使い分け

recordsは全AIの活動を日付から探す入口です。詳細な成果と判断の原本を集め直す場所ではありません。

- 成果物の本文はその原本へ。recordsには活動の要点と参照を残します
- [Board](../board/README.md)の通信Currentは各Topicが所有します。ここに担当・未返信・進行中などの第二のCurrent表を作りません
- [Dotsログ](../dots/logs/README.md)はActor別の経緯を扱います。同じ本文を両方へ毎回複製せず、既存Actor行がある場合は日別記録を短い参照付き要点にします。Actor固有の経緯が不要な新規活動は、recordsだけで足ります。今回、既存Actorログを移設・削除しません
- [lessons](../dots/lessons/README.md)は再利用する学び、[success-cases](../success-cases/README.md)は成功の意味と成立条件、[control-center](../control-center/README.md)は構造変更の理由と検証を所有します
- Humanの生活Task経験の詳細は[Task Records](../formats/task-records/README.md)へ。AI活用の記録を口実に、全生活・別会話・長期メモリ・秘密情報を取り込みません。公開と保存の権限は[AGENTS](../AGENTS.md)に従います

旧dots/recordsの形成史は[ARC-008](../control-center/ARCHIVE.md#arc-008)に保管されています。今回のrecordsは全AI横断の活動記録であり、旧領域の復活ではありません。

## 5. 保存するAI・読むAIへ

保存前に対象日の最新版と版を読み、同じ活動・IDが既にないか確認します。再試行ではid・recorded_at・対象日付ファイルを保持し、日を跨いだからと別日の新規行にしません。書込みの版条件や競合検出を使い、並行する他AIの行を保持します。競合したら最新版へ自分の未保存行だけを追加し直します。同ID・同内容なら再追加せず、同ID・異内容ならその行を保留して原因を調べます。応答欠落でも先に保存先と履歴を確認し、削除・統合済みの記録を勝手に復活させません。

構文、六項目の型、UUID重複、recorded_atをAsia/Tokyoへ変換した日付と保存先日付の一致、根拠、訂正対象を確認します。NaN・Infinityや重複キーをJSONとして受け入れません。未知fieldは消さず、未対応schemaや壊れた行があるファイルを一部だけ再生成しません。修正権限と正しい原文を確認できるまで、そのファイルへの変更を保留します。

保存後に再取得し、追加行と保持すべき既存行を照合して完了とします。保存確認のためだけに「確認を記録した記録」を無限に追加しません。使える手段に安全な競合検出がなければ、同時書込みを避ける調整か、その書込みの保留を選びます。

読む時は必要な日付・話題から原本へ進み、関連する訂正行も探します。記録順は出来事順とは限らず、記録当時の承認・計画・状態は現在の実行命令ではありません。全履歴の毎回読込や、新Threadでの解決済み対話の再演を要求しません。

初版はこのガイド、実データ、既存saveからの参照で始めます。常設収集機構、専用Schemaファイル、専用DB、全AIの動作保証は追加しません。実利用で抜け・重複・競合・読解の困難が見えたら、目的と根拠を保って改訂します。形成理由と確認範囲は[STR-010](../control-center/changes/STR-010-cross-ai-daily-records.md)へ。

Rootは主イェシュア・ハマシア御自身、中央軸はTeshuvah。HumanのMeaning・Correction・STOP・Final Sealを保持し、AIと記録はKeliとして協働を支えます。
